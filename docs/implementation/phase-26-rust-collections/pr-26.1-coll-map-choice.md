# PR 26.1 — Key the relation cache with a BTreeMap so latest-version lookup is a range query

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 26 — Rust collections · **Crates touched:** `pg-sink` · **Est. size:** S ·
> **Depends on:** PR 25.5 · **Unlocks:** PR 26.2

`RelationCache` stores `HashMap<(u32, i64), Arc<CachedRelation>>` (`relcache.rs:36`), but its hottest
read is an inherently *ordered* question: `latest_for(oid)` filters the **whole** map by oid and then
runs `max_by_key` over the survivors (`relcache.rs:46-52`) — an O(n) full-map scan executed once per
streamed change (`consume.rs:524`, `stream_txn.rs:242`, `stream_txn.rs:399`). Because the key is the
tuple `(relation_oid, schema_version)`, every version of one table is already a *contiguous* slice
under tuple `Ord`; a `BTreeMap` turns that scan into
`range((oid, i64::MIN)..=(oid, i64::MAX)).next_back()` — O(log n), and no `max_by_key` at all. The
tree has **0** `BTreeMap` occurrences in any `.rs` file today, while **5** `BTreeSet` uses already
exist (`reload_export.rs:169-172`, `ddl.rs`, `preflight.rs`) — so the ordered-container idiom is
blessed here; only the map half is missing.

## Why — learning objectives

- **`BTreeMap` range queries on a composite key** — `(oid, i64::MIN)..=(oid, i64::MAX)` is the exact
  oid slice *because* tuple `Ord` compares the first element first; `.next_back()` on that range is
  "the highest `schema_version` for this oid" with no filtering and no scan.
- **Access pattern picks the map, not habit** — `HashMap` is the correct default (point lookups,
  order irrelevant), and `get(oid, version)` is exactly that; the moment a *second* read asks an
  ordered question about the same keys, the ordered container wins both.
- **The versioned cache key is a design decision, not an implementation detail** — keying on
  `(relation_oid, schema_version)` makes a DDL bump a **new entry** rather than a mutation, so
  in-flight batches at the old version still resolve (`relcache.rs:1-8`, pg-sink §3.5).
- **Declining a dependency is part of applying the rule** — the rule's third answer (`IndexMap`)
  is right for insertion-order iteration and wrong here; saying so with evidence is the deliverable.

  external call sites (`latest_for` on the change path, `oid_for` on the DDL-cut path). Read the

- `docs/walrus-pg-sink.md` §3.5 — the homogeneous-file rule: a DDL bump cuts a fresh Parquet file, so
  every file carries exactly one `schema_version`. That is *why* multiple versions of one oid coexist
  in this cache at the same time, which is what makes the range non-trivial.

**Explicitly deferred** (do *not* build these here)

- **`oid_for` stays a linear `.values().find(...)` scan.** It answers a `(schema, table) → oid`
  question, which the `(oid, version)` key order cannot serve; a secondary index is a separate
  ticket. Note the free side-effect and mention it in the PR body: under `BTreeMap` this scan becomes
  **deterministic** (ascending oid) where it was previously arbitrary hash order.
- Do **not** touch `crates/loader/src/duck.rs:40`'s `parquet_cols: RefCell<HashMap<i64,
  Arc<Vec<String>>>>` — that is a pure point-lookup cache keyed by `schema_version`, where `HashMap`
  is already the right answer under this very rule.
- Do **not** touch `InflightMeter.by_stream` (`memory.rs:27`) — that is PR 26.3's subject.
- No `.sql` file and no `.sqlx` offline-cache entry changes (there is no Docker locally to
  regenerate the cache; see Hints).

**Conflict — resolve explicitly, do NOT apply the rule blindly.** The rule offers **three** answers
and one of them is `IndexMap` from the `indexmap` crate. walrus has **zero** third-party collection
dependencies (`grep -rn 'indexmap' Cargo.toml crates/*/Cargo.toml` ⇒ **0**), and CONTEXT §6 requires
every new dependency to clear `cargo deny`'s advisories / 8-license allow-list / bans. Adding a crate
to buy *insertion-order iteration* — which nothing in `RelationCache` asks for — would also trip
`anti-premature-optimize` and `perf-profile-first` from this same corpus. **Required resolution:** use
std `BTreeMap`, add no dependency, and record the `IndexMap` decline as a one-line comment in
`relcache.rs` so the next reader does not re-litigate it. A PR that adds `indexmap` fails this ticket.

```rust
// crates/pg-sink/src/relcache.rs — signatures are unchanged; only the container and one body move.

use arrow::datatypes::SchemaRef;
use common::{PgRelation, TypeDescriptor};
use std::collections::BTreeMap; // was: HashMap (PR 26.1)
use std::sync::Arc;

#[derive(Debug, Default)]
pub struct RelationCache {
    /// Ordered by `(relation_oid, schema_version)`. Tuple `Ord` compares the oid first, so **every
    /// version of one table is a contiguous range** — which is exactly what `latest_for` needs, and
    /// what a `HashMap` could only answer with a full scan.
    ///
    /// `IndexMap` (indexmap crate) was considered and declined: nothing here iterates in insertion
    /// order, and a new dependency would have to clear `cargo deny` for no measurable gain.
    by_key: BTreeMap<(u32, i64), Arc<CachedRelation>>,
}

impl RelationCache {
    /// Unchanged: an exact point lookup. `BTreeMap::get` has the same signature as `HashMap::get`.
    pub fn get(&self, oid: u32, schema_version: i64) -> Option<Arc<CachedRelation>> {
        todo!("body is untouched: self.by_key.get(&(oid, schema_version)).cloned()")
    }

    /// The cached shape for `oid` at its **highest** `schema_version` — used to stamp streamed
    /// changes after a DDL bump (PR 2.33), so a change always lands in the latest-shape file.
    pub fn latest_for(&self, oid: u32) -> Option<Arc<CachedRelation>> {
        // Replaces `.iter().filter(...).max_by_key(...)` — an O(n) scan of every cached relation at
        // every version — with an O(log n) descent to the end of this oid's own slice.
        todo!(
            "self.by_key
                 .range((oid, i64::MIN)..=(oid, i64::MAX))
                 .next_back()
                 .map(|(_, r)| r.clone())"
        )
    }

    /// Unchanged (deferred): a `(schema, table)` question the `(oid, version)` order cannot serve.
    /// Now iterates in ascending key order, so its answer is deterministic rather than hash-random.
    pub fn oid_for(&self, schema: &str, table: &str) -> Option<u32> {
        todo!("body is untouched: self.by_key.values().find(...).map(|r| r.relation.oid)")
    }
}
```

## Hints & gotchas

- **Use the inclusive upper bound, not `oid + 1`.** `range((oid, i64::MIN)..(oid + 1, i64::MIN))` is
  the tempting half-open form and it **panics on overflow** (debug) or wraps (release) when
  `oid == u32::MAX`. `..=(oid, i64::MAX)` has no edge case and reads as what it means.
- **`i64::MIN`, not `0`.** `schema_version` is a bare `i64` (CONTEXT §2: `SchemaVersion` is
  deliberately still un-newtyped). Nothing in the type forbids a negative version, and a lower bound
  of `0` would silently skip one if a test or a hydrate ever produced it.
- **`.next_back()` needs a double-ended iterator** — `btree_map::Range` is one, so this compiles.
  Do not reach for `.last()`: on a `DoubleEndedIterator` it is O(range length), which reintroduces
  the scan you are deleting. Clippy's `double_ended_iterator_last` will tell you the same thing.
- **`BTreeMap` requires `K: Ord`, and `(u32, i64)` already is** — no derive, no wrapper type, no
  `Ord` impl to write. If you find yourself writing one, you have the wrong key.
- **`#[derive(Default)]` still works.** `BTreeMap` implements `Default`, so `RelationCache::default()`
  — used by `relcache_test.rs` and the bootstrap path — needs no change.
- **`Arc<CachedRelation>` is what makes the clone cheap.** `latest_for` returns `r.clone()`, an
  `Arc` bump, not a schema copy. Keep it that way; do not "optimise" it into returning a reference —
  the callers at `consume.rs:524` and `stream_txn.rs:242` outlive the borrow.
- **Do not add a dependency.** Any new crate must clear `cargo deny` (advisories, the 8-license
  allow-list, bans) in the `supply-chain` CI job. `indexmap` would pass that gate and still be the
  wrong answer — the decline is on design grounds, and the comment must say so.
- **`unwrap`/`expect` are `deny` in production** via `[workspace.lints.clippy]`; `clippy.toml`
  re-allows them under `#[cfg(test)]`, so the new sibling-file assertions may use `.unwrap()` freely.
- **Tests are a sibling file, not an inline module.** `relcache.rs` ends with
  `#[cfg(test)] #[path = "relcache_test.rs"] mod tests;` — add your cases to `relcache_test.rs`; do
  not open a `mod tests {}` block.
- **`clippy::all` + `warnings` are already `deny` workspace-wide**, so an unused `HashMap` import
  after the swap is a hard CI failure, not a warning. Delete it in the same edit.
- **No `.sqlx` regeneration is possible on this machine** (no Docker). This PR touches no SQL, which
  is the point — keep it that way.

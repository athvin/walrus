# PR 26.1 — Key the relation cache with a BTreeMap so latest-version lookup is a range query

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 26 — Rust collections · **Crates touched:** `pg-sink` · **Est. size:** S ·
> **Depends on:** PR 25.5 · **Unlocks:** PR 26.2

`RelationCache` currently wraps a private
`HashMap<(u32, SchemaVersionNo), Arc<CachedRelation>>` (`relcache.rs:36-38`), but PR 13.13 made the
wrapper a complete public collection surface: `iter`, `FromIterator`, `Extend`, and owned/shared/
mutable `IntoIterator` all expose the inner map's value iterators. Its hottest read is still an
ordered question: `latest_for(oid)` walks `self.iter()`, filters the **whole** cache by oid, and then
runs `max_by_key` (`relcache.rs:49-54`). That O(n) scan is used for each ordinary streamed change
(`consume.rs:810-816`) and on both streamed-transaction materialisation paths
(`stream_txn.rs:262`, `stream_txn.rs:437`).

The tuple key already sorts every version of one table into a contiguous slice. A `BTreeMap` makes
the lookup
`range((oid, SchemaVersionNo(i64::MIN))..=(oid, SchemaVersionNo(i64::MAX))).next_back()`: O(log n),
with no filter or max scan. The conversion is not only a private field edit, however. It also changes
the concrete iterator types in the public collection API, makes all value iteration follow ascending
`(oid, schema_version)` key order, and removes `HashMap::reserve` from `Extend` because `BTreeMap`
has no capacity/reserve API. Those mechanically required changes are part of this ticket and are
tested explicitly.

There are **0** `BTreeMap` occurrences in Rust today and **5** `BTreeSet` occurrences in `pg-sink`
source/tests (`reload_export.rs` and `tests/reload_export.rs`). There is exactly **1** `max_by_key`
in `relcache.rs`, the one in `RelationCache::latest_for`, and there is no `indexmap` dependency. The
ordered-container idiom is therefore established without adding a crate; this task supplies the map
half where a range query actually needs it. (`memory.rs` has a separate `max_by_key` owned by PR
26.3; it is not this task's baseline or scope.)

## Why — learning objectives

- **`BTreeMap` range queries on a composite newtype key** — tuple `Ord` compares oid first and
  `SchemaVersionNo` second; because `SchemaVersionNo` derives `Ord`, the inclusive `i64::MIN` to
  `i64::MAX` bounds describe exactly one oid's full version slice. `.next_back()` selects the
  highest version without traversing that slice.
- **Access pattern picks the map, not habit** — exact `get(oid, version)` and inserts move from
  average constant time to logarithmic; that cost buys the range query on the
  per-change path and ordered traversal everywhere the collection API is used.
- **A wrapper's iterator types are part of the conversion** — `iter()` and the three
  `IntoIterator::IntoIter` associated types currently name `hash_map::{Values, ValuesMut,
  IntoValues}`. They must move together to their `btree_map` counterparts while preserving item
  types, ownership, and lifetimes.
- **Capacity strategy is container-specific** — PR 13.13 used an input iterator's lower size hint
  to call `HashMap::reserve`. `BTreeMap` allocates tree nodes and exposes no reserve operation, so
  dropping that hint is an intentional performance trade, not an omitted optimisation.
- **The versioned cache key remains authoritative** — a DDL bump adds a new `(oid,
  schema_version)` entry rather than mutating the old one, allowing in-flight batches at the prior
  version to resolve and bootstrap hydration to reconstruct the history.
- **Declining a dependency is part of applying the rule** — `IndexMap` is for insertion-order
  iteration. This cache needs sorted-key ranges, so adding `indexmap` would answer the wrong
  question and enlarge the dependency surface.

**In scope**

- Replace the `HashMap`/`hash_map` import with `BTreeMap`/`btree_map`, and change `by_key` to
  `BTreeMap<(u32, SchemaVersionNo), Arc<CachedRelation>>`.
- Rewrite `latest_for` to range from `(oid, SchemaVersionNo(i64::MIN))` through
  `(oid, SchemaVersionNo(i64::MAX))`, call `.next_back()`, and clone the selected `Arc`. It must
  return the same cached entry as the valid-key invariant did before, return `None` for an unknown
  oid, and contain no `filter` or `max_by_key`.
- Change the inherent `iter()` return type and all three `IntoIterator::IntoIter` associated types
  from `hash_map` value iterators to the corresponding `btree_map` value iterators. Preserve their
  method bodies, yielded item types, ownership, and lifetimes. Update `iter()`'s documentation to
  state that traversal follows ascending `(oid, schema_version)` key order.
- Remove only `self.by_key.reserve(iter.size_hint().0)` from `Extend` (and simplify the now-
  unnecessary local iterator binding if desired). Preserve key projection, `Arc::new`, overwrite-
  on-duplicate-key behaviour, and `FromIterator`'s delegation to `extend`.
- Keep the bodies of `get`, `oid_for`, `len`, `is_empty`, `upsert_from_relation`, `hydrate`,
  `FromIterator::from_iter`, and the three `IntoIterator::into_iter` methods byte-identical to the
  immediate predecessor. `iter()`'s delegating body also stays identical; its signature/doc change.
- Document next to `by_key` why tuple ordering makes one oid's versions contiguous and why
  `IndexMap` was considered and declined.
- Add sibling tests for: three oids inserted out of order/interleaved; isolation from a neighbouring
  oid with a larger version; the full `u32`/`i64` boundary-safe range; and the concrete
  `btree_map` iterator types plus ascending-key order across inherent, shared, mutable, and owned
  iteration. Keep all six predecessor tests.

The iterator-order change is observable but does not violate the predecessor's documented
"unspecified order" promise; this PR tightens it to sorted-key order. Consequently the untouched
`oid_for` body now chooses the lowest `(oid, version)` among otherwise ambiguous duplicate
`schema.table` values instead of hash-randomly choosing one. Unambiguous matches are unchanged, and
the predecessor promised no tie order; do not add a secondary name index here. The key remains a
projection of each value. PR 13.13's public mutable iterator can technically let a caller replace an
`Arc` and violate that invariant; hardening that older API is not part of this map choice. Tests and
production construction must use valid projected keys.

**Explicitly deferred** (do *not* build these here)

- Do not redesign or remove `iter`, `FromIterator`, `Extend`, or any `IntoIterator` impl to hide the
  concrete-type migration. Do not add a walrus-owned iterator wrapper or change the three item types.
- Do not add a `reserve` substitute, collect into a temporary sorted vector, or introduce bulk-load
  machinery. `BTreeMap` has no capacity API; its logarithmic insertion cost is the accepted side of
  the range-query trade.
- `oid_for` remains its existing `.iter().find(...)` scan. A `(schema, table) -> oid` secondary
  index is a separate task; only its newly deterministic traversal order is acknowledged here.
- Do not touch `crates/loader/src/duck.rs`'s `parquet_cols` point-lookup `HashMap`, the DDL
  controller's version `HashMap`, or `InflightMeter.by_stream`; their access patterns differ and
  later roadmap tasks own the latter.
- Do not change any relation-cache public method signature except the unavoidable concrete iterator
  return/associated types. Do not change hydration atomicity, error text, exact point lookups,
  duplicate-key replacement, or `Arc` identity/clone behaviour.
- No dependency, root/member manifest, `Cargo.lock`, `.sql`, or `.sqlx` offline-cache change.

**Conflict — resolve explicitly, do NOT apply the rule blindly.** The rule offers `IndexMap` for
insertion order, but no relation-cache requirement asks for insertion order and an insertion-ordered
map cannot answer this sorted tuple range. walrus has no `indexmap` dependency, and adding one would
also trigger the repository's dependency-policy review. Use `std::collections::BTreeMap`, add no
crate, and record the decline in the field documentation. The move from average O(1) to O(log n)
point lookup/insertion and the loss of `reserve` are accepted specifically because `latest_for`
moves from an O(n) full-cache scan to an O(log n) range descent.

## Hints & gotchas

- Use `SchemaVersionNo(i64::MIN)` and `SchemaVersionNo(i64::MAX)`, not bare integers. The newtype
  derives `Ord`, so `(u32, SchemaVersionNo)` already satisfies `BTreeMap`'s key bound.
- Use the inclusive upper bound. A half-open `(oid + 1, ...)` bound overflows at `u32::MAX`; the
  full-version inclusive tuple range has no oid arithmetic and states the intended slice directly.
- Use `i64::MIN`, not `0`. The wrapper's type permits negative values even if production normally
  assigns positive versions, and the range should express the type's complete domain.
- Use `.next_back()`, not `.last()`. `btree_map::Range` is double-ended; `next_back` selects the
  high end directly, while `last` walks the iterator and gives back the scan this task removes.
- The four concrete iterator types are public API. This repository has no consumer that names the
  old `hash_map` types, but the task deliberately migrates them rather than pretending the field
  swap is contained. Keep the yielded `Arc` reference/value types and lifetimes exact.
- `BTreeMap` has no `reserve`; simply delete the capacity hint. Do not emulate it. `Extend`'s lower
  size hint was never a correctness condition, while collision replacement and atomic hydration
  through `extend` are protected behaviour.
- Ordered value iteration is by the hidden key, even though callers receive only values. Keep each
  key equal to `(cached.relation.oid, cached.schema_version)`. The public mutable iterator predates
  this task and can theoretically break that projection; do not expand this PR into an API redesign.
- `oid_for` keeps its body. Its scan becomes deterministic in ascending key order, but adding the
  reverse `(schema, table)` index or choosing newest oid semantics is explicitly deferred.
- `Arc<CachedRelation>` keeps the clone cheap and preserves entry identity. Do not return a borrow or
  clone the underlying relation/schema.
- Tests belong in sibling `relcache_test.rs`. `.unwrap()`/`.expect()` are allowed there by
  `clippy.toml`, but remain denied in production.
- Do not add `indexmap` or touch SQL/offline metadata. The standard-library tree is the selected
  data structure and requires no dependency or SQLx regeneration.

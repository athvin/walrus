# PR 26.3 — Pop spill candidates from a BinaryHeap instead of rescanning the meter for the max

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 26 — Rust collections · **Crates touched:** `pg-sink` · **Est. size:** M ·
> **Depends on:** PR 26.2 · **Unlocks:** PR 26.4

`BinaryHeap` and `std::cmp::Reverse` appear **0** times anywhere in the tree, yet walrus has a
textbook repeated-max-extraction site: `spill_if_over_ceiling` loops
`while self.meter.over_ceiling()` (`stream_txn.rs:200`) and **every** iteration calls
`InflightMeter::largest_open()` — an O(n) `max_by_key` over `by_stream: HashMap<(TableId, u32), u64>`
(`memory.rs:65-70`, the module's only `max_by_key`). Shedding *k* streams therefore costs O(k·n).
Priorities never *rise* during one shed episode — the loop calls `release`, never `add` — so a heap
snapshot built once per episode gives O(n) to build and O(log n) per pop. The bigger win is
determinism: `max_by_key` over a `HashMap` breaks ties by iteration order, which is randomised per
process, so "which stream gets spilled when two are the same size?" is untestable today. A total
order on `(bytes, table_id, xid)` makes the victim deterministic and unit-assertable.

## Why — learning objectives

- **`BinaryHeap` is a max-heap; `Reverse` flips it** — O(log n) `push`/`pop`, O(1) `peek`. Wrapping
  values in `std::cmp::Reverse<T>` gives a min-heap with no custom `Ord` impl. This ticket wants the
  max, so it uses the heap directly — but you must be able to say what the `Reverse` flip would do
  and when the shed order would want it.
- **Tuple ordering *is* the comparator** — `(bytes, table_id, xid)` derives lexicographic `Ord` for
  free, so "largest first, ties broken by table then xid" needs no `impl Ord`, no
  `sort_by`, and no `Ordering` boilerplate. Putting `bytes` first is the whole design.
- **A heap snapshot is not a replacement for the accounting store** — `BinaryHeap` supports neither
  arbitrary removal nor priority updates, so the authoritative `HashMap` stays; the heap is built,
  drained, and dropped inside one shed episode. Knowing *when a heap is legal* is the real lesson.
- **Memory backpressure in the sink** — the shed order is flush-committed → spill the largest open
  `(table, sub-xid)` buffer speculatively to S3 → pause polling, and freeing memory is deliberately
  separable from advancing the slot (`architecture.md` §1.3/§1.5).

  is `spill_if_over_ceiling` with different names — the `Reverse` min-heap idiom, and above all the
  closing **Note**: "`BinaryHeap` does not support efficient arbitrary removal or priority updates."

- `crates/pg-sink/src/memory.rs:1-18` — the module doc: the aggregate ceiling exists because
  `logical_decoding_work_mem` bounds the *source's* reorder buffer, not the sink's Arrow buffers, and

- `crates/pg-sink/src/memory_test.rs:1-50` — the sibling-test style, including

- `docs/architecture.md` §1.3 — `max_inflight_bytes` as an aggregate process-wide ceiling distinct

## Scope

**In scope**

- Add `InflightMeter::spill_order(&self) -> BinaryHeap<(u64, TableId, u32)>` — a **snapshot** of the
  current `by_stream` contents as `(bytes, table_id, xid)`, i.e. a max-heap that pops the largest
  stream first with a deterministic `(table_id, xid)` tie-break. Document it as per-episode and
  read-only with respect to `by_stream`.
- Rewrite `largest_open` so `memory.rs` contains **no** `max_by_key`: fold the same tuple into a
  plain `.max()` (`self.by_stream.iter().map(|(&(t, x), &b)| (b, t, x)).max().map(|(_, t, x)| (t, x))`).
  This keeps `decide()` working and gives it the *same* deterministic tie-break as the heap.
- Rework `spill_if_over_ceiling` (`stream_txn.rs:195-302`) to build `spill_order()` **once**, before
  the `while` loop, and `pop()` a candidate per iteration instead of re-calling `largest_open()`.
  Return early when `!self.meter.over_ceiling()` so the snapshot is never built on the happy path.
- Keep the loop's existing arms intact: a popped candidate with no owner (PR 26.2's index) is stale
  accounting ⇒ `self.meter.release(key); continue;`; an uncached shape still `continue`s; a
  zero-row batcher still `continue`s. `break` when the heap is exhausted.
- New `memory_test.rs` cases: (a) `spill_order()` pops **strictly descending** by bytes; (b) an exact
  byte tie is broken deterministically by `(table_id, xid)` — the same input produces the same victim
  on every run; (c) `spill_order().peek()` and `largest_open()` agree; (d) `spill_order()` on an
  empty meter is empty and does not panic.
- Optionally add a `stream_txn_test.rs` case asserting that a shed episode which must spill **two**
  streams spills them in descending-bytes order.

**Explicitly deferred** (do *not* build these here)

- **No long-lived heap.** Do not add a `BinaryHeap` field to `InflightMeter` or `StreamDemux`, and do
  not try to keep one in sync with `add`/`release`.
- **No `keyed_priority_queue` (or any other) dependency**, and no lazy-deletion / tombstone
  bookkeeping. The rule names both as escape hatches; neither is justified here and both would have
  to clear `cargo deny`.
- **Do not rework `open_floor()`** (`stream_txn.rs:452`, `.values().map(..).min()`). One min over a
  small map, called once per checkpoint — there is no repeated extraction to amortise.
- Do not change the shed **order** (`ShedAction::FlushCommitted` → `SpillOpenTxn` → `PausePoll`) or
  `Backpressure`'s hysteresis. Only the *selection* of the spill victim changes, and only its
  tie-break is observably different.
- No `.sql` file and no `.sqlx` offline-cache changes.
- This ticket assumes PR 26.2 has already replaced the shed loop's ownership lookup with the `owner`
  index; do not re-introduce a `changes` scan.

**Conflict — resolve explicitly, do NOT apply the rule blindly.** The rule's own note says
`BinaryHeap` "does not support efficient arbitrary removal or priority updates" — and `InflightMeter`
does **both**: `add` (`memory.rs:40`) mutates an existing key's byte count, `release`
(`memory.rs:46`) removes an arbitrary key. A heap therefore **cannot** replace `by_stream`.
**Required resolution:** `by_stream` remains the single authoritative accounting store; the heap is a
short-lived *snapshot* built at the top of one shed episode, drained by that episode's loop, and
dropped when it ends. The invariant that makes it correct is narrow and must be written into the
code as a comment: *inside the drain loop, priorities only ever fall, because the loop calls
`meter.release` and never `meter.add`*. A popped candidate is therefore a hint, re-validated against
the live meter and the owner index before use — never a source of truth. A PR that stores a heap as
a field, or that reads bytes from the popped tuple as if it were current, fails this ticket.

```rust
use std::collections::{BinaryHeap, HashMap};

impl InflightMeter {
    /// A **one-shot snapshot** of spill candidates, largest first: `(bytes, table_id, xid)`.
    ///
    /// `by_stream` stays the authoritative accounting store — this heap is built at the top of one
    /// shed episode, drained by it, and dropped. It is deliberately NOT kept in sync with
    /// [`InflightMeter::add`] / [`InflightMeter::release`], because `BinaryHeap` supports neither
    /// priority updates nor arbitrary removal. The narrow invariant that makes the snapshot safe:
    /// inside the drain loop priorities only ever FALL (the loop calls `release`, never `add`), so a
    /// popped candidate is at worst stale-and-already-gone, which the caller re-validates.
    ///
    /// Ordering is the derived lexicographic `Ord` on the tuple: bytes descending, then `table_id`,
    /// then `xid` — a total order, so the victim is deterministic (a `HashMap` `max_by_key` breaks
    /// ties by randomised iteration order, which no test can pin).
    pub fn spill_order(&self) -> BinaryHeap<(u64, TableId, u32)> {
        todo!("self.by_stream.iter().map(|(&(t, x), &bytes)| (bytes, t, x)).collect()")
    }

    /// The largest in-flight `(table, xid)` stream — the best spill candidate. Same tie-break as
    /// [`InflightMeter::spill_order`], so `decide()` and the drain loop agree.
    pub fn largest_open(&self) -> Option<(TableId, u32)> {
        // WAS: .max_by_key(|(_, &bytes)| bytes) — correct, but its tie-break was hash order.
        todo!(
            "self.by_stream
                 .iter()
                 .map(|(&(t, x), &bytes)| (bytes, t, x))
                 .max()
                 .map(|(_, t, x)| (t, x))"
        )
    }
}
```

```rust
// crates/pg-sink/src/stream_txn.rs — the drain loop, restructured around one snapshot.

    async fn spill_if_over_ceiling(
        &mut self,
        cache: &RelationCache,
        sink: &ParquetSink,
    ) -> anyhow::Result<()> {
        // Happy path: never build the snapshot when we are under the ceiling (this function is
        // called from `on_change`, i.e. once per streamed row).
        if !self.meter.over_ceiling() {
            return Ok(());
        }
        // ONE snapshot per shed episode. Safe because the loop below only ever `release`s bytes —
        // it never calls `meter.add`, so no candidate's priority can rise while we drain.
        let mut candidates = self.meter.spill_order();
        while self.meter.over_ceiling() {
            // WAS: `let Some((oid, sub_xid)) = self.meter.largest_open() else { break };`
            //      — an O(n) rescan of the whole map on every single iteration.
            let Some((_bytes, oid, sub_xid)) = candidates.pop() else {
                break; // nothing left to spill this episode; the caller's backpressure takes over
            };
            // `_bytes` is the SNAPSHOT value and must not be treated as current accounting.
            let Some(top) = self.owner.get(&(oid, sub_xid)).copied() else {
                self.meter.release((oid, sub_xid)); // stale accounting; nothing buffered
                continue;
            };
            todo!("body unchanged from PR 26.2: take_stream, forget_stream, latest_for, TableBatcher, put_with_kind, staged.push");
        }
        Ok(())
    }
```

## Hints & gotchas

- **Put `bytes` first in the tuple.** `(u64, TableId, u32)` derives the ordering you want for free;
  `(TableId, u32, u64)` would sort by table and silently spill the wrong buffer. There is no
  `impl Ord` to write — if you find yourself writing one, the tuple is in the wrong order.
- **`BinaryHeap<T>` needs `T: Ord`, and `(u64, u32, u32)` already is.** No `#[derive]`, no wrapper.
  If you later need "smallest first", that is `BinaryHeap<Reverse<…>>` — but not in this PR.
- **`.collect()` into a `BinaryHeap` is O(n)**, not O(n log n): it uses `Heap::heapify` rather than
  n pushes. Building the snapshot per episode is genuinely cheap; building it *per iteration* would
  throw the whole win away, which is why the DoD pins it outside the loop.
- **`peek()` returns `Option<&T>`** — destructure with `.map(|&(_, t, x)| (t, x))`, and remember it
  is O(1) while `into_sorted_vec()` is O(n log n). The test only needs `peek`.
- **Do not iterate a `BinaryHeap` expecting sorted order.** `.iter()` yields *heap* order, which is
  not sorted; only `pop()` (and `into_sorted_vec`) give the ordering. A test that iterates will pass
  by luck on three elements and fail on thirty.
- **The early `return Ok(())` matters.** `spill_if_over_ceiling` is called from `on_change`, i.e.
  once per streamed row. Without the guard you would allocate a heap on every row in the common case
  where nothing needs shedding.
- **Termination.** Each loop iteration either pops a candidate or breaks, and the heap is finite, so
  the loop terminates even if the meter never drops below the ceiling — strictly better than today,
  where a key that can never be spilled had to be released to make progress. Keep the stale-accounting
  `release` anyway: it is what stops `total` from drifting upward forever.
- **`unwrap`/`expect` are `deny` in production**; the popped `Option` must be handled with
  `let … else { break }`, never `.expect("heap non-empty")`. `clippy.toml` re-allows both in the
  sibling test file, so `assert_eq!(h.pop(), Some((900, 2, 101)))` is fine there.
- **`clippy::all` + `warnings` are `deny` workspace-wide.** Watch for `clippy::type_complexity` on
  `BinaryHeap<(u64, TableId, u32)>` — three elements is under the default threshold, but if you
  extend the tuple, introduce a named struct with `#[derive(PartialEq, Eq, PartialOrd, Ord)]` rather
  than an `#[allow]`.
- **Tests are sibling files** (`memory_test.rs`, `stream_txn_test.rs`), never inline `mod tests {}`.
  `memory_test.rs` already touches the private `total` field (`empty.total = 1`), which works because
  the sibling file is compiled as a child module — the same trick is available to you.
- **No new dependency.** `keyed_priority_queue` would solve priority updates, but this design does
  not need them, and every new crate must clear `cargo deny` (advisories, 8-license allow-list,
  bans). Decline it in the PR body, citing the snapshot invariant.

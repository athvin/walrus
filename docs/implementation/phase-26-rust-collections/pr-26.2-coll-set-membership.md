# PR 26.2 — Index streamed-change ownership in a set instead of rescanning every open transaction

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 26 — Rust collections · **Crates touched:** `pg-sink` · **Est. size:** M ·
> **Depends on:** PR 26.1 · **Unlocks:** PR 26.3

At baseline `1664214`, the memory-shed loop still answers a pure membership/ownership question by
walking every open transaction and then walking each transaction's buffered changes:
`self.open.iter().find(|(_, t)| t.changes.iter().any(...))`
(`stream_txn.rs:227-235`). The `.any(` at `:233` is the **only** production `.any(` in the Rust
tree, and it runs inside `while self.meter.over_ceiling()` (`:222`), when memory is already under
pressure. `release_txn_meter` separately rebuilds the same distinct stream-key set from
`txn.changes` (`:494-498`) on every whole commit/abort.

The ordered `Vec<StreamedChange>` must remain the row source of truth. PR 11.7 already removed the
deep-cloning spill drain: commit `af31538` introduced
`std::mem::take(&mut txn.changes).into_iter().partition(...)`, and test commit `9a50bb7` pinned the
survivors' relative order. This PR therefore promotes membership to an incrementally maintained
per-transaction `HashSet`, adds a demux-level owner `HashMap`, and moves that **existing clone-free,
order-preserving partition** into `StreamedTxn::take_stream`. It must not reintroduce the old
`retain` + `c.clone()` implementation.

## Why — learning objectives

- **A set/map used as an index, not as row storage** — `Vec<StreamedChange>` retains commit order;
  `HashSet<(oid, sub_xid)>` records which streams are buffered, and
  `HashMap<(oid, sub_xid), top_xid>` resolves their owner in average O(1).
- **Index maintenance is part of the data structure** — claim, spill, whole commit, and whole abort
  must update the buffer key set, owner map, and `InflightMeter` together. A stale index is worse
  than the scan it replaces.
- **Ownership-aware refactoring without cloning** — moving the current `mem::take` + `partition`
  code behind `take_stream` keeps both halves in their original order and moves each row exactly
  once.
- **Recognising the quadratic shape** — `outer.iter().find(|x| inner.iter().any(|y| ...))` is the
  rule's linear-membership anti-pattern nested one level deeper. Build the tuple lookup once and
  maintain it at mutation boundaries.
- **Why the flat key is unique** — Postgres xids are process-global, so one
  `(relation_oid, sub_xid)` stream can belong to only one open top-level transaction.
- **Subtransaction lifetime is not transaction lifetime** — a sub-xid abort leaves its in-memory
  rows and accounting present until commit-time survivor filtering; a whole-txn abort releases all
  remaining keys immediately.

    begin_lsn: Lsn,
    /// Buffered changes in commit order; this remains the row source of truth.
    changes: Vec<StreamedChange>,
    /// Exactly the distinct `(oid, sub_xid)` streams currently represented in `changes`.
    keys: HashSet<(u32, u32)>,
    staged: Vec<StagedSpill>,
    aborted: HashSet<u32>,
}

impl StreamedTxn {
    fn new(begin_lsn: Lsn) -> Self {
        todo!("the current constructor plus keys: HashSet::new()")
    }

    fn push_change(&mut self, change: StreamedChange) {
        self.keys.insert((change.oid, change.sub_xid));
        self.changes.push(change);
    }

    /// Move one stream out without cloning and preserve the relative order of rows and survivors.
    fn take_stream(&mut self, oid: u32, sub_xid: u32) -> Vec<StreamedChange> {
        let (rows, keep): (Vec<StreamedChange>, Vec<StreamedChange>) =
            std::mem::take(&mut self.changes)
                .into_iter()
                .partition(|c| c.oid == oid && c.sub_xid == sub_xid);
        self.changes = keep;
        self.keys.remove(&(oid, sub_xid));
        rows
    }
}

        while self.meter.over_ceiling() {
            let Some(key @ (oid, sub_xid)) = self.meter.largest_open() else {

                    continue;
                };
                (txn.begin_lsn, txn.take_stream(oid, sub_xid))
            };
            self.forget_stream(key);

        }
        Ok(())

## Hints & gotchas

- **PR 11.7 owns the drain algorithm.** `af31538` deliberately removed deep clones under memory
  pressure; `9a50bb7` proves stable survivor order. `take_stream` is an extraction of that exact
  algorithm plus `keys.remove`, not permission to resurrect its predecessor.
- **The existing order test bypasses `on_change`.** Its manual setup is valuable because it builds
  a deterministic spill candidate without spilling during construction, but after this PR it must
  call `claim_stream` rather than `meter.add` directly or the owner map will correctly report no
  holder.
- **There are four ownership transitions:** `on_change` claims; a spill takes/forgets one stream;
  whole commit releases all remaining streams; whole abort releases all remaining streams. A
  sub-txn abort deliberately performs no ownership transition.
- **`self.owner.get(&key).copied()` must finish before `self.open.get_mut(&top)`.** Copy the `u32`
  owner out so the immutable map borrow does not cross the transaction mutation.
- **Owner and meter lifetime must not drift.** Centralise them in `claim_stream`/`forget_stream`.
  A metered key with no owner can make `largest_open` return the same stale candidate forever;
  stale branches must release it.
- **The per-txn key set tracks buffered streams, not staged spills.** A successful extraction removes
  the key before batching/PUT. Staged objects are already out of memory and are governed by the
  existing `staged`/`aborted` logic.
- **A sub-txn abort is not a release.** Its rows remain in `changes`, its key remains owned and
  metered, and `survivors` excludes them at top-level commit. Releasing early undercounts actual
  buffered memory.
- **`(oid, sub_xid)` is unique across open txns** because Postgres xids are process-global. Record
  this in the field invariant; without it, a flat owner map would not be sound.
- **The uncached-shape path intentionally drops drained rows.** The meter and owner have already
  been cleared, matching the current can't-happen-path behaviour. Repairing that operational policy
  is a separate task.
- **Do not touch `memory.rs`.** PR 26.3 will snapshot `largest_open` candidates and change the
  extraction strategy after this owner lookup exists.
- Production denies `unwrap`/`expect`, warnings, and clippy-all violations. Keep defensive
  `let ... else` branches; sibling tests may unwrap under `clippy.toml`.
- Tests stay in `stream_txn_test.rs` through the existing sibling-module wiring. The spill cases
  use the in-memory object store; do not introduce S3/compose fixtures.
- About 1,500 small `TupleValue::Text` rows are fast enough for this regression. Choose the ceiling
  between the total before and after the uniquely largest stream is removed, so exactly one spill
  is required.
- No dependency is needed: `HashMap` and `HashSet` from `std` are the complete collection surface.

# PR 26.2 — Index streamed-change ownership in a set instead of rescanning every open transaction

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 26 — Rust collections · **Crates touched:** `pg-sink` · **Est. size:** M ·
> **Depends on:** PR 26.1 · **Unlocks:** PR 26.3

The memory-shed loop asks a pure membership question with a nested linear scan:
`self.open.iter().find(|(_, t)| t.changes.iter().any(|c| c.oid == oid && c.sub_xid == sub_xid))`
(`stream_txn.rs:205-213`) — O(open × changes) work per shed iteration, inside a
`while self.meter.over_ceiling()` loop (`stream_txn.rs:200`) that only runs when memory is *already*
critical. It is the **only** `.any(` in the entire production tree (measured: **1**). The set that
answers the same question in O(1) is already built two hundred lines further down —
`let keys: HashSet<(u32, u32)> = txn.changes.iter().map(...)` at `stream_txn.rs:456` — but it is
rebuilt from scratch at commit/abort and thrown away. This PR maintains that key set incrementally
and adds a demux-level `owner: HashMap<(u32, u32), u32>` index, so "which top-level xid holds this
`(table, sub-xid)` buffer?" is a hash lookup, and `release_txn_meter` stops scanning `changes` too.

## Why — learning objectives

- **A set/map used as an *index*, not as storage** — the `Vec<StreamedChange>` stays the ordered
  source of truth; the index only answers membership. The skill is keeping the two in sync across
  every insert / `retain` / remove path, because a stale index is worse than no index.
- **Recognising the quadratic shape** — `outer.iter().find(|x| inner.iter().any(|y| …))` is the
  rule's Bad example with two loops instead of one; the fix is always "build the lookup once, key it
  by the tuple you were comparing".
- **Why the key is globally unique** — Postgres xids are process-global, so a `(relation_oid,
  sub_xid)` pair identifies exactly one buffering top-level transaction. That uniqueness is what lets
  a single flat `HashMap` replace the nested search, and it is the invariant a reviewer will check.
- **Speculative spill of an open streamed transaction** — which `(table, sub-xid)` buffer belongs to
  which top-level xid, why a whole-txn abort must forget every one of its keys, and why a
  *sub*-transaction abort must not (its rows stay buffered and are filtered at commit).

## Hints & gotchas

- **The index is only as good as its worst update path.** There are exactly five places that can
  change ownership: `on_change` (claim), the spill drain (`take_stream` + `forget_stream`),
  `on_stream_commit` (release all), whole-txn `on_stream_abort` (release all), and — deliberately —
  *nothing* on a sub-txn abort. Write them as the four helper calls in the skeleton and never touch
  `owner` inline; a stale entry sends a spill to the wrong transaction.
- **`self.owner.get(&key).copied()` then `self.open.get_mut(&top)` — two separate borrows.** Do not
  try to hold the `&StreamedTxn` from the lookup across the mutation; copy the `u32` out first. The
  existing code already does this dance (`.map(|(&k, _)| k)`), for the same borrowck reason.
- **`meter.release` and `owner.remove` must never drift apart.** That is why `forget_stream` does
  both. If you ever call one without the other, the shed loop can spin: the meter still counts bytes
  for a key nobody owns, `largest_open` keeps returning it, and `over_ceiling()` never clears.
- **A sub-txn abort is not a release.** `abort_subtxn` only inserts into `aborted`; the rows stay in
  `changes` and are filtered at commit (`stream_txn.rs:398`, `:382`). If you remove owner/meter
  entries there, the accounting under-counts real buffered memory — the exact bug this module exists
  to prevent.
- **`(oid, sub_xid)` is unique across open txns** because Postgres xids are process-global. Say so in
  the field doc; a reviewer who does not know that will (correctly) ask why a flat map is safe.
- **`StreamedChange` is `Clone` and `take_stream` clones the drained rows** — that matches today's
  `retain` body exactly. Do not "improve" it into a `drain`-based partition in this PR; behavioural
  parity is a DoD item and `Vec::extract_if` is PR 26.4's subject.
- **Do not touch `memory.rs`.** PR 26.3 rewrites `largest_open` and adds `spill_order`; touching it
  here creates a conflict for no gain, and the two probes are deliberately independent.
- **`unwrap`/`expect` are `deny` in production** (`[workspace.lints.clippy]`); the `let … else {
  continue }` shape in this function exists precisely because the code must never panic mid-stream.
  Keep every new fallible step in that shape. `clippy.toml` re-allows `.unwrap()` in the sibling
  test file.
- **`clippy::all` and `warnings` are `deny` workspace-wide**, so an unused `HashSet` import or an
  unread field after refactoring is a hard CI failure.
- **Tests are a sibling file** (`#[cfg(test)] #[path = "stream_txn_test.rs"] mod tests;`), and the
  spill tests are `#[tokio::test]` because `on_change` is `async`. Use the existing `mem_sink()`
  in-memory `object_store` fixture — do not reach for S3 or the compose stack for this.
- **Building 1500 changes in a test is fine and fast** (they are small `TupleValue::Text` rows) —
  but set the demux ceiling deliberately: `demux(u64::MAX)` disables spilling, a small ceiling forces
  it. The existing tests show both.
- **No new dependency.** A `HashMap`/`HashSet` from `std` is the whole fix; anything from crates.io
  would have to clear `cargo deny`'s advisories / 8-license allow-list / bans for no benefit.

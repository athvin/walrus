# PR 10.3 — Preserve the `duckdb::Error` source chain in `LoaderError::Duck`

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** loader

> **Phase:** 10 — Rust error handling · **Crates touched:** `loader` · **Est. size:** M ·
> **Depends on:** PR 10.2 · **Unlocks:** PR 10.4

`LoaderError::Duck(String)` (`error.rs:13`) is constructed **16 times** in
`crates/loader/src/duck.rs`, every single one of them as `format!("<op>: {e}")` — the underlying
`duckdb::Error` is stringified on the spot and its `source()` chain destroyed. A caller that
wants to know *which* DuckDB failure occurred (a `DuckDBFailure` FFI code vs an
`InvalidColumnName` vs a lock contention) has nothing but a message to regex. Tree-wide there are
only **5** `#[source]` attributes and 10 `#[from]` against **67** `#[error(…)]` variants, so this
is the crate that most needs the lesson. After this PR `Duck` is a struct variant
`{ op, #[source] source: duckdb::Error }`, the raw engine error survives all the way to the log,
and `std::error::Error::source()` on a loader failure returns `Some`.

## Why — learning objectives

- **`std::error::Error::source`** — what a "cause chain" actually is, and why `{:#}`/`{:?}`
  printers and `tracing` can render it only if you kept the link.
- **`#[source]` vs `#[from]`** — `#[from]` also generates the `From` impl (and so forces a 1:1
  type→variant mapping); `#[source]` only marks the cause, which is what you want when the
  variant also carries an operation label.
- **Struct-variant error payloads in thiserror** — `Duck { op, source }` lets
  `#[error("duckdb {op}")]` name the operation while the cause stays a first-class typed field,
  not text.
- **DuckDB failure modes in the loader** — append, transform, DDL and compaction all funnel
  through one variant today; the raw engine message is the only thing that distinguishes them in
  an incident.

## Hints & gotchas

- **`grep -c` counts lines, not occurrences.** `duck.rs:219-224` has three `describe {uri}` sites
  on three lines, so the 16 → 0 arithmetic holds; do not "merge" them into one and call the probe
  green.
- **The variant change is crate-wide.** `Duck` is built in five files, not one —
  `cargo check -p loader` after editing `error.rs` gives you the exact worklist. 29 sites total.
- **Do not reach for `#[from]` here.** `duckdb::Error` → `LoaderError` via `#[from]` would drop
  the `op` label and make every `?` in the loader silently produce a context-free error.
  `#[source]` + explicit `map_err` is the point of the rule.
- **`compaction.rs:51` is not a `map_err`.** It is `if let Err(e) = …`, and the cancellation
  branch returns `Ok(())` *before* the error is built — keep that ordering exactly, or a
  drain-time abort becomes a spurious failure.
- **thiserror does not nest Display.** `#[error("DuckDB: {op}")]` prints only the op; the cause
  appears when the *printer* walks `source()` (`{:#}` under anyhow, or `tracing`'s error field).
  That is why `as_common` must interpolate `{source}` explicitly on the exit path.
- **`duckdb::Error` is easy to fake in a test** — `duckdb::Error::InvalidColumnName(String)` or
  `QueryReturnedNoRows` construct with no engine. The sibling test must not open a real database.
- **DuckDB cold builds are slow.** The bundled engine compiles from source: expect ~20 min cold
  in CI (~3 min cached). Poll patiently rather than assuming the job hung.
- **`unwrap`/`expect` are denied in production**; `clippy.toml` re-allows them under
  `#[cfg(test)]`, so `error_test.rs` may use them and `error.rs` may not. Tests are sibling
  files, never inline modules.

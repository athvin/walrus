# PR 10.9 — Deny panic todo unimplemented and unreachable in production

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 10 — Rust error handling · **Crates touched:** `pg-to-arrow`, `pg-sink` ·
> **Est. size:** M · **Depends on:** PR 10.8 · **Unlocks:** PR 10.10

`[workspace.lints.clippy]` (`Cargo.toml:15-21`) denies exactly two panicking constructs —
`unwrap_used` and `expect_used`, since PR 7.7. The rest of the family is unlinted, and production
still contains **2 panic sites**: `unreachable!("is_null covers Null/UnchangedToast")` at
`pg-to-arrow/src/batch.rs:309`, sitting inside `append_value` — a function that *already* returns
`Result<(), Error>`, so the invariant is expressible as ordinary control flow — and
`unimplemented!(…)` at `pg-sink/src/backfill.rs:36`, the documented deferred-goal seam for parallel
CTID-range backfill. A `panic!` in the decode path does not fail one row, it aborts the pod
mid-batch and hands the operator a backtrace instead of a classified `ExitCode`. This PR closes the
family — `panic`, `todo`, `unimplemented`, `unreachable`, `panic_in_result_fn` all become `deny` —
removes the one removable site, and pins the one intentional site with a narrow, machine-checked
`#[expect]`.

## Why — learning objectives

- **The Result-vs-panic decision boundary** — when an "impossible" arm is really a type-system gap
  you can close (an exhaustive match), when it is a real error to return, and when it is a
  deliberate, documented stub; plus `clippy::restriction` lints and the `clippy.toml` test carve-outs
  that make denying them survivable.
- **pg-to-arrow's Tier-1 builder invariants** — why a decoder that receives a wire byte it did not
  expect must return `Error`, never abort the process: the sink is mid-`CopyBoth`, and a panic
  loses the batching state that the LSN watermark depends on.

  Read the header: this stub is *the point of the file*, not an oversight.

## Scope

**In scope**

- `[workspace.lints.clippy]` gains five denies: `panic`, `todo`, `unimplemented`, `unreachable`,
  `panic_in_result_fn`, each with a one-line comment saying what it buys.
- `clippy.toml` gains `allow-panic-in-tests = true`, matching the existing unwrap/expect carve-out.
- `crates/pg-to-arrow/src/batch.rs` — the `DataType::Binary` arm stops panicking (see Skeleton).
- `crates/pg-sink/src/backfill.rs:35` — `plan_ctid_ranges` gains an
  `#[expect(clippy::unimplemented, reason = "…")]` naming `docs/deferred-goals.md`, next to its
  existing `#[allow(dead_code)]` (exact shape in the Skeleton).
- Whatever narrow, file-level allows the **test** tree needs (see the conflict note below and the
  Hints) — measured, not guessed.

**Conflict with the rule — resolve it explicitly, do NOT apply the rule blindly**

The corpus treats `unimplemented!()` and `unreachable!()` as *legitimate* panic sites ("Unimplemented
code path → `unimplemented!()`", "Impossible state reached → `unreachable!()`"). walrus keeps exactly
one of each and both are documented. The required resolution is **deny-plus-narrow-`#[expect]`, not
deletion**:

- `backfill.rs:36`'s `unimplemented!` **stays**. It is the marked seam for a deferred architecture
  goal (`docs/deferred-goals.md`, PR 4.11) and deleting it would delete the documentation. It gets a
  scoped `#[expect]` with a `reason`, which is strictly better than today's silence: if the stub is
  ever implemented, the expectation goes unfulfilled and clippy tells you to remove the attribute.
- `batch.rs:309`'s `unreachable!` **goes**, because it is not really unreachable-by-design — it is a
  wildcard arm papering over a four-variant enum. Making the match exhaustive removes the panic
  *and* upgrades the invariant from a runtime message to a compile error, which is exactly the house
  convention (`common::Error::is_terminal` has no `_` arm on purpose).

**Explicitly deferred** (do *not* build these here)

- `clippy::indexing_slicing` and `clippy::arithmetic_side_effects` — ~36 candidate index sites and
  104 `as` casts. Those belong to Phase 17 (`num-`) and Phase 31 (`perf-`); denying them here would
  bury this PR.
- The 20 file-level `#![allow(clippy::unwrap_used, clippy::expect_used)]` headers in integration
  tests and benches stay exactly as they are.
- No new `common::Error` or `common::ExitCode` variant — the exit-code numbers are a documented
  public contract (`common/src/error.rs:105-121`).

## Skeleton

```toml
# Cargo.toml — [workspace.lints.clippy], appended below the existing unwrap/expect pair.
# All five are `clippy::restriction` (not in `all`), so no `priority` juggling — same as PR 7.7.
panic = "deny"              # a service never aborts the pod where it could return a classified error
todo = "deny"               # no unfinished code reaches main
unimplemented = "deny"      # the one sanctioned stub carries a scoped #[expect] (pg-sink/backfill.rs)
unreachable = "deny"        # "impossible" arms are usually a non-exhaustive match — make it exhaustive
panic_in_result_fn = "deny" # a fn that can already say "no" must not abort instead
```

```toml
# clippy.toml
allow-unwrap-in-tests = true
allow-expect-in-tests = true
allow-panic-in-tests = true
```

```rust
// crates/pg-to-arrow/src/batch.rs — inside `append_value`, the DataType::Binary arm.
// BEFORE: `is_null` gated an inner `match value { … _ => unreachable!(…) }`.
// AFTER:  match `value` directly. Exhaustive over all four TupleValue variants, no `_` arm, no
//         panic — a future variant becomes a compile error instead of a runtime abort.
DataType::Binary => {
    let b = downcast!(builder, BinaryBuilder, col);
    match value {
        // NULL and unchanged-TOAST both append a null on the validity bitmap.
        TupleValue::Null | TupleValue::UnchangedToast => b.append_null(),
        TupleValue::Binary(bytes) => b.append_value(bytes),
        // bytea text is `\x…` hex under text mode.
        TupleValue::Text(s) => b.append_value(&parse_bytea(s, col)?),
    }
}
```

```rust
// crates/pg-sink/src/backfill.rs:34-37 — the sanctioned stub, now machine-checked.

fn plan_ctid_ranges(_table: &str) -> CtidRangePlan {
```

## Hints & gotchas

- **Measure before you deny.** Enumerate the sites first and write the list down; flip to `deny`
  only once you know the shape of the fallout:

  ```console
  $ cargo clippy --all-targets --all-features -- \
      -W clippy::panic -W clippy::todo -W clippy::unimplemented \
      -W clippy::unreachable -W clippy::panic_in_result_fn 2>&1 \
      | grep -E '^(warning|  --> )'
  ```
- **`clippy.toml` has a carve-out for `panic` and nothing else.** There is no
  `allow-unreachable-in-tests` / `allow-todo-in-tests` / `allow-unimplemented-in-tests`. The tree
  has four `unreachable!` sites in tests — `crates/pg-sink/src/reload_test.rs:32` and `:59`,
  `crates/pg-sink/tests/replication_spike.rs:124`,
  `crates/pg-sink/tests/pgoutput_vectors.rs:598` — and they will need a file-level
  `#![allow(clippy::unreachable, reason = "…")]` (or a per-site `#[expect]`).
- **`allow-panic-in-tests` covers `#[test]` functions and `#[cfg(test)]` modules — not helpers in
  `tests/`.** That is exactly why every existing integration test already carries a file-level
  unwrap/expect allow "for setup + helpers". Expect the same pattern for the `panic!` sites in
  `crates/pg-sink/tests/pgoutput_vectors.rs` and `reload_pickup.rs` that live outside a `#[test]` fn.
- **`panic_in_result_fn` is the wildcard of the five.** Its exact treatment of assertion macros has
  changed across clippy releases; measure its blast radius separately before committing. If it turns
  out to fire across the compose-gated test helpers, prefer scoped test-file allows over dropping the
  lint — and if you do drop it, say so in the Cargo.toml comment and in the PR body rather than
  silently shipping four denies.
- **`#[expect]` fails when the lint does *not* fire**, which is the whole point — but that also means
  ordering matters: add the `deny` and the `#[expect]` in the same commit, or clippy will flag the
  expectation as unfulfilled.
- `#[expect(clippy::…)]` under plain `cargo build` (rustc, no clippy) must not emit
  `unfulfilled_lint_expectations` — modern rustc ignores expectations for tool lints it does not
  run, but verify it on the pinned toolchain, because `warnings = "deny"` makes a regression here a
  hard build failure, not a warning.
- Do **not** collapse `TupleValue::Null | TupleValue::UnchangedToast` into a `_` arm to save a line.
  The no-wildcard style is load-bearing across this codebase: it is what makes adding a fifth
  `TupleValue` variant a compile error in every decoder at once.
- `parse_bytea(s, col)?` already returns the right typed error for malformed `\x…` hex, so the
  rebuilt arm needs no new error variant. (If you would rather make the impossible arm explicit than
  silent, `value_err(col, &format!("{value:?}"), "Binary")` reuses the existing helper at
  `batch.rs:846` — but the exhaustive match is the better answer, because it cannot go stale.)
- Nothing here touches `.sql` or the `.sqlx` offline cache — good, because there is no Docker
  locally to regenerate it.

# PR 10.2 — Drop the redundant `map_err` boilerplate in `control` and propagate with `?`

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test,sqlx · **Test packages:** control

> **Phase:** 10 — Rust error handling · **Crates touched:** `control` · **Est. size:** M ·
> **Depends on:** PR 10.1 · **Unlocks:** PR 10.3

With `From<sqlx::Error> for ControlError` in place (PR 10.1), every one of the **49**
`.map_err(ControlError::from_sqlx)` / `.map_err(ControlError::Connect)` calls in
`crates/control/src` is now noise: `?` already performs exactly that conversion. `reload.rs`
alone carries 20 of them, `schema_registry.rs` 10, `manifest.rs` 6, `checkpoint.rs` 4,
`table_ownership.rs` and `replication_state.rs` 3 each, `ddl_manifest.rs` 2, `db.rs` 1. The crate
already leans on `?` heavily (38 `?;` sites), so this is pure deletion, not a rewrite — and once
the last hand-written call is gone, `from_sqlx` is reachable *only* through the `From` impl,
which is what makes the classification un-bypassable rather than merely available.

## Why — learning objectives

- **`?`'s implicit `From` conversion** — `expr?` already calls `From::from` on the error; an
  explicit `.map_err(SameConversion)` in front of it is dead weight that hides the real control
  flow.
- **When `map_err` is *not* redundant** — it earns its keep only when the conversion needs data
  the `From` impl cannot see (a schema/table name, a constraint name, an enum-parse message).
- **The walrus control-plane call shape** — every query in this crate funnels through one
  classified error type, so a reader can tell terminal from transient without reading each call
  site.

## Hints & gotchas

- **Tail expressions bite.** A function whose last expression is `…await.map_err(f)` returns the
  `Result` directly; deleting `map_err` there needs `Ok(… .await?)`. Four sites are like this
  (`checkpoint.rs:42`, `replication_state.rs:29`, `ddl_manifest.rs:79`, `reload.rs:180`) — a bare
  `.await?` will produce a type error, not a silent bug.
- **Clippy may now suggest `needless_question_mark`.** If `Ok(expr?)` is the *whole* body and the
  error types already match, clippy will (rightly) ask you to return `expr` — but `expr` here is
  `Result<_, sqlx::Error>`, not `Result<_, ControlError>`, so the lint should not fire. If it
  does, the conversion is a no-op and you have found a real simplification; take it rather than
  `#[allow]`-ing it. `clippy::all` is already `deny` workspace-wide, so this must be resolved,
  not muted.
- **Do not "tidy" the `Decode` sites.** `r.kind.parse().map_err(ControlError::Decode)?` converts
  a `ManifestKindParseError`, not a `sqlx::Error`. Adding a `From` for it is out of scope and
  would quietly widen the terminal-error surface.
- **The `.sqlx` cache cannot be regenerated here** (no Docker locally). This PR must not alter a
  single byte of query text — if `cargo sqlx prepare --check` fails in CI, you edited SQL by
  accident.
- **Tests are sibling files.** Nothing in this PR should add an inline `mod tests { … }`; the
  crate's 47-module Go-style convention is enforced by review.
- **`unwrap`/`expect` stay denied** in production by `[workspace.lints.clippy]` — resist
  "simplifying" a `?` into an `.unwrap()` in a spot that looks infallible.

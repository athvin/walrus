# PR 10.1 — Give `ControlError` a classifying `From<sqlx::Error>`

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** control

> **Phase:** 10 — Rust error handling · **Crates touched:** `control` · **Est. size:** M ·
> **Depends on:** PR 9.12 · **Unlocks:** PR 10.2

`ControlError` carries exactly one `#[from]` (`Migrate`, `db.rs:14`) and is otherwise built from
a `sqlx::Error` at **49** `map_err(…)` call sites. 43 of those route through the SQLSTATE-`23514`
classifier `ControlError::from_sqlx` (`db.rs:64`), but **6** — `manifest.rs:145,184,222,236,276`
and `db.rs:84` — call `ControlError::Connect` directly. So a CHECK-constraint violation raised by
a `file_manifest` write (`insert_ready`, `claim_ready`, `mark_failed`, …) is misclassified as the
*transient* `Connect` instead of the terminal `CheckViolation`, and `is_terminal()` (`db.rs:46`)
then returns the wrong answer — the caller retries a programming bug to the startup deadline.
After this PR there is one hand-written `impl From<sqlx::Error> for ControlError` that delegates
to the classifier, `?` does the conversion, and no call site can pick the unclassified path by
accident.

## Why — learning objectives

- **Hand-written `From<E>` vs thiserror `#[from]`** — `#[from]` generates a *dumb* conversion
  into one variant; when the conversion has to *decide* which variant, you write the impl
  yourself.
- **How `?` desugars** — `expr?` is
  `match expr { Ok(v) => v, Err(e) => return Err(From::from(e)) }`, so an available `From` impl
  is what makes the operator work at all.
- **Control-plane error classification** — SQLSTATE `23514` (CHECK violation) is a *terminal*
  invariant breach; a connection/pool failure is *transient* and worth retrying during a rollout.

## Hints & gotchas

- **`#[from]` on `Migrate` does not clash.** `sqlx::migrate::MigrateError` and `sqlx::Error` are
  different types, so thiserror's generated `From<MigrateError>` and your hand-written
  `From<sqlx::Error>` coexist. Adding `#[from]` to `Connect` *instead* would compile but would
  silently reinstate the misclassification — that is the whole bug. Do not do it.
- **The test double must implement four hidden methods.** `sqlx::error::DatabaseError` (sqlx 0.8)
  has `#[doc(hidden)]` `as_error`, `as_error_mut`, `into_error` plus the required `message()` and
  `kind()`. Returning `self` / `ErrorKind::Other` is fine for the non-`23514` case.
- **`kind()` is not what the classifier reads.** `from_sqlx` matches on `db.code()`, so the
  double's `code()` is the field under test; a mismatched `kind()` will not make the test lie,
  but keep them consistent so the fixture reads honestly.
- **`connect()`'s tail is an expression, not a `?` site.** Converting it needs `Ok(… .await?)` —
  a bare `.await?` at the end of a function body returning `Result<PgPool, _>` will not
  type-check.
- **`unwrap`/`expect` are denied in production** by `[workspace.lints.clippy]`; `clippy.toml`
  re-allows them under `#[cfg(test)]`, so the sibling test may use them, `db.rs` may not.
- **Tests are sibling files.** `db_test.rs` is wired in via
  `#[cfg(test)] #[path = "db_test.rs"] mod tests;` at the bottom of `db.rs` — never add an inline
  `mod tests { … }`.
- **No new dependency is needed.** If you reach for one, remember it must clear `cargo deny`
  (advisories + the 8-license allow-list) in the always-on `supply-chain` CI job.

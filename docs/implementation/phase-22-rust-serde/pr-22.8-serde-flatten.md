# PR 22.8 — Record why serde flatten is rejected and guard the wire structs against it

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 22 — Rust serde · **Crates touched:** `common` · **Est. size:** S ·
> **Depends on:** PR 22.7 · **Unlocks:** PR 23.1

`#[serde(flatten)]` appears **0 times** in walrus, and its one natural site is real: `SinkConfig`
(`pg-sink/src/config.rs:21`) and `LoaderConfig` (`loader/src/config.rs:13`) each re-declare the same
**five** fields `CommonConfig` (`common/src/config.rs:21`) already defines — `control_db_url`,
`object_store`, `telemetry`, `instance`, `startup_deadline` — and `CommonConfig`'s own doc comment
(`:7`, `:18`) claims the service configs "embed" it. They do not; they copy it. But every config
container carries `#[serde(deny_unknown_fields)]`, which `serde_derive` makes a **compile error**
alongside `flatten`, and that attribute is precisely what makes `unknown_key_is_rejected`
(`config_test.rs:75`) — and the ConfigMap typo guard its header documents
(`deploy/k8s/base/configmap.yaml:2`) — work. The second candidate, `SinkMeta`, is the hot path where
flatten's content-buffering deserializer would undo the amortized const/row splice that exists
because meta serialization measures **≈ 576 ns/row, ~91 % of `append_row/narrow_int4`**
(`docs/benchmarks.md:78-94`, `sink_meta.rs:142-150`). This is an archetype-**D** ticket: the count
stays 0, and the deliverables are the *reason* —
`docs/implementation/notes/serde-flatten-rejected.md` — plus a unit-test guard in `common` that
reads the five serde-bearing modules back at compile time so the 0 cannot drift silently.

## Why — learning objectives

- **Why `flatten` and `deny_unknown_fields` are mutually exclusive, and what flatten costs** —
  flatten has to forward keys it does not recognise to the inner type, which is the exact opposite
  of denying unknown keys; `serde_derive` rejects the pair at compile time. Flatten also switches
  the struct onto serde's buffering path (every key/value is collected into a `Content` map before
  the inner type sees it), which is why the rule's own Caveats say to keep it off hot
  deserialization paths.
- **Writing an evidence-backed ADR that declines a rule instead of applying it blindly** — "not
  relevant" is not a result. A decline is only a result when it names the site that *would* have
  used the technique, the property that would have been lost, the number that makes it a bad trade,
  and the condition that would re-open the decision.

  both stated there, and they are the two reasons this PR declines it. The `Pagination` example

  genuine decline rather than an inapplicable rule.

## Scope

**In scope**

1. **The ADR** — `docs/implementation/notes/serde-flatten-rejected.md`, covering, with file:line
   citations: what the rule asks for; the two candidate sites; the `serde_derive` compile error that
   blocks the config site; the property (`unknown_key_is_rejected`, the ConfigMap typo guard) walrus
   keeps instead; the benchmark that blocks the `SinkMeta` site; what walrus does instead (accept
   the five-field duplication, bounded by `validate()` in each crate); and the re-open condition.
2. **The guard** — a crate-wide unit test in `common`: new `crates/common/src/lib_test.rs` plus the
   `#[cfg(test)] #[path = "lib_test.rs"] mod tests;` hook in `crates/common/src/lib.rs`. It
   `include_str!`s the five serde-bearing modules — `config.rs`, `telemetry.rs`, `sink_meta.rs`,
   `pg_shape.rs`, `type_descriptor.rs` — and asserts each contains no flatten attribute, naming the
   offending module in the failure message.
3. **A pointer comment** (optional but preferred) on `CommonConfig` (`config.rs:18-21`) sending the
   next reader to the note, phrased so it does not trip the guard's needles — see **Hints**.

**Explicitly deferred** (do *not* build these here)

- **No de-duplication of the five shared config fields by any other means.** Not a `common:
  CommonConfig` nested key, not a `#[serde(rename)]` scheme, not a macro. Every alternative renames
  the `WALRUS_*` environment variables and therefore rewrites both ConfigMaps
  (`deploy/k8s/base/configmap.yaml`) and the e2e harness's env (`tests/e2e/src/lib.rs`). The
  duplication is accepted, deliberately, and the note says so.
- **No CI grep step.** The guard is a unit test — walrus prefers a unit-level probe over a
  `docker compose`-gated or pipeline-level assertion.
- **No `TupleValue` serde.** It is deliberately not `Serialize` (`pg_shape.rs:99-100`); this PR does
  not revisit that.
- **No `.sql` / `.sqlx` edits, no new dependency.**

**Conflict to resolve explicitly — do NOT apply this rule.** `#[serde(flatten)]` and
`#[serde(deny_unknown_fields)]` are mutually exclusive (the rule's own Caveats), and walrus already
chose the typo guard on **every** config container: 4 sites on `main` today — `CommonConfig`
(`config.rs:20`), `ObjectStoreConfig` (`config.rs:37`), `LoaderConfig` (`loader/src/config.rs:12`),
`SinkConfig` (`pg-sink/src/config.rs:20`) — and 5 once PR 22.1 adds `TelemetryConfig`. An
implementer who "applies the rule" by adding `#[serde(flatten)] pub common: CommonConfig` to
`LoaderConfig` produces a **compile error**, and an implementer who fixes that error by deleting
`deny_unknown_fields` silently converts every ConfigMap typo from a terminal startup failure into a
silently-ignored key. The deliverable here is the recorded decision plus the guard — not the
attribute.

## Hints & gotchas

- **The self-reference trap is the whole trick here.** A guard whose needle is the literal
  `"serde(flatten)"` becomes the first repo-wide hit for its own pattern, so the probe that
  certifies "still 0" reports 1 and the next reader cannot tell a guard from a violation. Build the
  needle with `concat!("serde(", "flatten")` — compile-time concatenation, no runtime cost, and the
  substring never appears in the file.
- **For the same reason, list the modules explicitly rather than walking a directory.** A
  `read_dir` over `src/` would scan `lib_test.rs` and fail against itself, and it would depend on
  `cargo test`'s CWD. `include_str!` is compile-time: a renamed module fails the **build**, which is
  the correct blast radius for a guard.
- **The pointer comment must dodge both needles.** "see `docs/implementation/notes/`
  `serde-flatten-rejected.md`" contains `serde-flatten` (hyphen) and `, flatten` never appears — it
  passes. Do not write `#[serde(flatten)]` inside a doc comment as an example; that is a guard
  failure, and the example belongs in the note.
- **Try the compile error once.** Add `#[serde(flatten)] pub common: CommonConfig` to `LoaderConfig`
  and run `cargo check -p loader`. `serde_derive` emits it at derive-expansion time, so it points at
  the attribute, not at a call site. Quote the real message in the note rather than paraphrasing.
- **Do not "fix" it by deleting `deny_unknown_fields`.** That attribute is the reason
  `unknown_key_is_rejected` (`config_test.rs:75`) passes and the reason a typo'd ConfigMap key kills
  the pod at startup instead of being ignored (`configmap.yaml:2`). PR 22.1 exists precisely to add
  the fifth site; removing one here would undo it.
- **`SinkMeta` has no `deny_unknown_fields`** — its leniency about unknown keys is a deliberate
  rolling-upgrade property (`sink_meta.rs:107-109`) — so serde would *accept* flatten there with no
  compile error. That site is blocked by the benchmark, not by the compiler, which is exactly why it
  needs a test guard rather than trusting the type system.
- **Cite the benchmark, don't re-run it.** `docs/benchmarks.md:78-94` already isolates the meta-JSON
  cost (`meta_json/serialize` 597.4 µs vs `meta_json/const` 21.01 µs → ≈ 576 ns/row) and
  `sink_meta.rs:142-150` records the amortization that followed. A D-ticket's job is to point at
  existing evidence.
- **A note is only done when it could change someone's mind.** `duckdb-lts-bump.md` is the bar: it
  states the premise, shows the measurement, and names what would re-open the question. "Not
  applicable" is not a finding.
- Unit tests are **Go-style sibling files** (`src/foo.rs` → `src/foo_test.rs` via
  `#[cfg(test)] #[path = "foo_test.rs"] mod tests;`) — 47 modules and zero inline `mod tests {}`.
  `lib.rs` → `lib_test.rs` follows the same rule; do not invent a `tests/` integration target for a
  guard this small.
- `unwrap`/`expect` are re-allowed in tests by `clippy.toml` but stay `deny` in production, and
  `clippy::all` + `warnings` are already `deny` workspace-wide — a guard that trips a lint is not
  green.
- The `.sqlx` offline cache **cannot be regenerated** (no Docker on this machine). Nothing in this
  PR touches a query.

# PR 28.14 — Add loader and comparison workflows to Criterion recipes

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Est. size:** S · **Depends on:** PR 28.13 · **Unlocks:** PR 28.15

criterion is properly adopted in walrus — **4** `harness = false` targets across 3 crates, 15
`black_box` sites, `Throughput::Elements` and `BenchmarkId` throughout — but the documented entry
point has **drifted away from the code**. `justfile:35-36` runs `cargo bench -p pg-sink -p pg-to-arrow`,
so the loader's two bench targets (`transform` and `append`, landed in PR 5.5 and baselined at
`docs/benchmarks.md:97`) are never executed by `just bench`, and `docs/benchmarks.md:29` still calls
the recipe "both crates". There is also **no** `--save-baseline` / `--baseline` workflow anywhere, even
though the bench-gated `mem-*` tickets in Phase 11 (CONTEXT §4: "adopt only if the committed criterion
baseline moves") depend on exactly that comparison existing. This PR reconnects the recipe to all
three crates and adds the two baseline recipes those tickets will call.

## Why — learning objectives

- **criterion baselines** — `--save-baseline <name>` stores an estimate set under `target/criterion`,
  `--baseline <name>` re-runs against it and prints the regression/improvement verdict; plus why
  `harness = false` is mandatory (it hands `main` to `criterion_main!` instead of libtest) and what
  `black_box` / `Throughput::Elements` actually buy you.
- **walrus's measured hot paths and its bench policy** — the per-cell `String` allocation in decode
  and the window dedup in the loader transform are the recorded targets; benches are **never** a CI
  gate, because shared runners are too noisy to time anything.

## Skeleton

```just
# justfile — replacing lines 32-36.

# Criterion micro-benches — sink decode (PR 5.4), Arrow batch building (PR 5.4), and the loader
# transform + Phase-A append (PR 5.5). Run on a quiet machine; results print to stdout. Never a CI
# gate (shared runners are too noisy) — CI only compile-checks the bench targets via
# `clippy --all-targets`. Baselines live in docs/benchmarks.md. The loader benches are the slow
# ones (in-memory DuckDB, the 1M grid takes minutes).
bench:
    cargo bench -p pg-sink -p pg-to-arrow -p loader

# Record the current numbers as a named criterion baseline (default `main`), so a later run can be
# compared against them. Baselines live under target/criterion/<bench>/<name>/ — gitignored, local
# to the machine that measured them. This is the mechanism the bench-gated Phase 11 `mem-*` tickets
# use: save on main, apply the change, then `just bench-compare`.
bench-baseline name="main":
    cargo bench -p pg-sink -p pg-to-arrow -p loader -- --save-baseline {{name}}

# Re-run the benches against a saved baseline and print the per-bench regression/improvement verdict.
bench-compare name="main":
    cargo bench -p pg-sink -p pg-to-arrow -p loader -- --baseline {{name}}
```

The `docs/benchmarks.md` edits, as literal replacement text (line 29 first, then the new subsection
appended after the "How to re-run" fence — keep its inner fence a plain three-backtick block, matching
the file's existing style):

    just bench                                   # all three crates, criterion defaults

    ### Comparing a change against a baseline

    Criterion's own before/after mechanism — no CI involvement, no committed artefacts:

    ```
    git switch main && just bench-baseline before   # record target/criterion/**/before
    git switch my-change && just bench-compare before
    ```

    `--baseline` prints `change: [-4.1% -2.8% -1.5%] (p = 0.00 < 0.05) Performance has improved.`
    per bench. Baselines live under `target/criterion/` (gitignored) and are only comparable **on
    the same machine, in the same session** — never quote a cross-machine delta. This is the gate
    the Phase 11 `mem-*` tickets (smallvec / arrayvec / thinvec / compact-string / arena) must clear
    before adding a dependency: if the committed baseline does not move, record the measurement and
    decline the change.

There is no Rust in this PR. The "guard" is the probe below: `just -n bench` must name all three
crates, and `grep -A1 '^bench:' justfile | grep -c 'p loader'` must return 1.

## Hints & gotchas

- **`just -n` is your probe.** `just --dry-run bench` prints the recipe body without running it —
  use it for every DoD assertion instead of actually benching, which takes minutes (the loader's 1M
  grid especially).
- **Just argument syntax**: `recipe name="default":` then `{{name}}` in the body. Follow the existing
  `bench-e2e scenario="mixed"` and `reload table flavor='reload'` recipes — do not invent a new style,
  and remember `just` arguments are positional.
- **The `--` matters.** `cargo bench -p x -- --save-baseline main` passes the flag to the *bench
  binary* (criterion), not to cargo. Drop the `--` and cargo will reject the unknown flag.
- **Baselines are not portable.** `target/criterion/<group>/<name>/` is machine- and
  session-specific; the methodology section already warns "Absolute numbers are machine-specific —
  compare deltas, not machines." Say so in the new subsection so nobody commits a delta measured on a
  CI runner.
- **Do not add a CI job.** This is the one hard prohibition in this ticket (see Scope). CI's only
  relationship with benches is `clippy --all-targets`, which type-checks the bench targets — that is
  already in the `gates` job and needs no change.
- Running `cargo bench` on the loader compiles DuckDB with the `bundled` feature. Cold, that is ~20
  minutes; warm, ~3. Budget for it, and do not conclude the recipe is broken because it is slow.
- Benches carry a file-level `#![allow(clippy::unwrap_used, clippy::expect_used)]` (they are
  `harness = false`, so not `cfg(test)`, and `clippy.toml`'s test allowance does not reach them).
  Leave those lines alone — removing one turns `clippy --all-targets` red, and `clippy::all` plus
  `warnings` are already `deny` workspace-wide.
- No new dependency here — but if you are ever tempted to add one, it must clear `cargo deny`
  (advisories, the 8-license allow-list, bans). Do not touch any `.sql` file or the `.sqlx` offline
  cache; there is no Docker on this machine to regenerate it.

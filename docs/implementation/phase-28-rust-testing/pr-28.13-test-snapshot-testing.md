# PR 28.13 — Snapshot loader transform and additive-DDL output

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** loader

> **Phase:** 28 — Rust testing · **Crates touched:** `loader` · **Est. size:** M ·
> **Depends on:** PR 28.12 · **Unlocks:** PR 28.14

The loader generates its most correctness-critical artefact — SQL — as **text**, and asserts none of
it. `TransformSql::render` (`crates/loader/src/transform.rs:178`) and `render_rebuild` (`:269`) expand
the 58-line `transform.sql` template into hundreds of characters of dedup window + three-branch
`MERGE` per table plan, and `apply_additive` (`ddl.rs:185`) concatenates DDL through **6**
`push_str(&format!(…))` sites. The 23 hermetic tests in `crates/loader/tests/transform.rs` assert row
*outcomes* through an in-memory DuckDB, so a Tier-2 plan change can silently rewrite the generated SQL
and still pass — the reviewer never sees the statement that changed. There are **0** insta references
and **0** `.snap` files in the repo today. This PR pins four rendered strings as committed snapshots,
so the next edit to `transform.sql` or `TablePlan` arrives in a PR as a reviewable unified diff.

## Why — learning objectives

- **Snapshot testing** — the approve-on-review workflow (`.snap.new` → review → commit), named
  snapshots, and when a committed `.snap` beats a hand-written `assert_eq!` of a 900-char string.
- **The loader's raw→mirror transform** — the dedup window (`QUALIFY row_number()` over
  `(commit_lsn, lsn) DESC`), the three-branch `MERGE`, and the per-PK max-applied guard — is exactly
  the kind of generated output whose *shape*, not just its effect, is the contract.

// crates/loader/src/ddl.rs — split the string building out of the execution. Everything inside the
// `for ch in changes` loop moves verbatim; only the `conn`/`Result` wrapper stays behind.

/// The DDL text [`apply_additive`] executes — pure, so it can be snapshot-tested (PR 28.13).
/// Empty when `changes` produces no statement (e.g. an empty slice).
fn additive_sql(table: &str, changes: &[AdditiveChange]) -> String {
    let mut sql = String::new();
    let mut cur = table.to_string();
    let mut structural = false;
    for ch in changes {
        todo!("the existing match arms, unchanged — AddColumn / RenameColumn / WidenColumn / \
               RenameTable / Comment");
    }
    if structural {
        sql.push_str(&user_view_sql(&cur));
    }
    sql
}

pub fn apply_additive(
    conn: &duckdb::Connection,
    table: &str,
    changes: &[AdditiveChange],
) -> Result<(), LoaderError> {
    let sql = additive_sql(table, changes);
    if sql.is_empty() {
        return Ok(());
    }
    conn.execute_batch(&sql)
        .map_err(|e| LoaderError::Duck(format!("apply additive DDL to {table}: {e}")))
}

## Hints & gotchas

- **The snapshot file name is derived, so pin it.** Always pass an explicit name
  (`insta::assert_snapshot!("tier1_orders_render", sql)`). Unnamed snapshots take the *test function*
  name, so renaming a test orphans its `.snap` and silently writes a new one. Run once and check the
  produced paths before you commit — the exact `<crate>__<module>__<name>.snap` spelling is insta's,
  not yours.
- **Bootstrapping the first run.** `INSTA_UPDATE=no` means a *missing* snapshot fails. Create them
  with `INSTA_UPDATE=always cargo test -p loader --lib` (or `cargo insta test --accept` if you have the
  CLI), then **read every line** before `git add`. An unread snapshot is worse than no snapshot: it
  freezes whatever the code currently does, bug included.
- **insta auto-detects CI** and defaults to not writing — setting `INSTA_UPDATE=no` explicitly is
  belt-and-braces, and it also protects anyone running the suite in a CI-like container locally.
- `assert_snapshot!` is for `Display`/`&str`; `render` returns `String`, so it is the right macro.
  Do **not** reach for `assert_debug_snapshot!` here — you would pin an escaped one-line blob that is
  unreadable in review, which defeats the point.
- Do **not** touch `crates/loader/sql/duckdb/templates/transform.sql` or any `.sqlx` file. There is no
  Docker on this machine to regenerate the offline cache, and the SQL is the thing under test.
- `insta` is a new dependency: it must clear `cargo deny` (advisories, the 8-license allow-list, bans).
  It is Apache-2.0 and pulls `similar`; `deny.toml:53` sets `multiple-versions = "warn"`, so a
  duplicate major is a warning, not a failure — but read the output rather than assuming.
- `unwrap`/`expect` are denied in production by `[workspace.lints.clippy]`; `clippy.toml` re-allows
  them under `#[cfg(test)]`, which is exactly what the sibling modules are. Keep `additive_sql`
  itself unwrap-free — it is production code.
- `clippy::all` and `warnings` are already `deny` workspace-wide. Extracting `additive_sql` may make
  `clippy::format_push_string` visible if a later phase promotes it; leave the arms verbatim so this
  PR's diff stays reviewable, and let Phase 33 deal with the lint.
- Unit tests in walrus are **sibling files**, never inline `mod tests {}` — 47 modules follow the
  pattern and PR 28.1's hygiene gate enforces it. Copy the trailer from `duck.rs:404-406` exactly.

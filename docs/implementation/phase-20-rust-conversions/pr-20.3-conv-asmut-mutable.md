# PR 20.3 — Record why AsMut has no write target and deny needless_pass_by_ref_mut instead

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 20 — Rust conversions · **Crates touched:** `pg-sink` · **Est. size:** S ·
> **Depends on:** PR 20.2 · **Unlocks:** PR 21.1

Exactly one `AsRef<…>` / `AsMut<…>` trait bound exists across walrus's `crates` and `tests`: the
legitimate read-only path input `crates/loader/src/duck.rs:71 TableDb::open(path: impl AsRef<Path>)`.
There are **zero `AsMut<…>` bounds** and no mutable write target to widen. All **15** `&mut` container
parameters in the production inventory either need their concrete container's own API — five
`String`/`Vec`/`BytesMut` roles plus seven reusable `String` scratch-buffer roles — or are **already**
the `&mut [T]` slice form the rule advocates at `crates/pg-to-arrow/src/batch.rs:441`/`:478`/`:512`.
The local `let mut builders` binding at `batch.rs:170` is not a parameter and is excluded. walrus has
no fixed-length byte-fill target, which is the shape `impl AsMut<[u8]>` serves: the wire builders in
`replication.rs` all *grow* a `Vec<u8>`, and the pgoutput `Reader` is read-only over `&'a [u8]`. So
this PR writes the deviation down as an ADR, pins the `AsMut` absence with a guard, and lands the
mutable-borrow gate walrus actually lacks — `clippy::needless_pass_by_ref_mut`, which today reports
exactly **1** site: `crates/pg-sink/src/reload_export.rs:304 async fn await_echo(&mut self, …)`, which
never mutates `self`.

## Why — learning objectives

- **`AsRef` / `AsMut` as generic borrowed-input bounds** — and when a concrete `&mut T` is the correct
  API, i.e. writing the deviation down instead of cargo-culting the rule.
- **walrus's mutable-borrow surface** — the pgoutput frame reader (`BytesMut::split_to`), reusable
  Arrow conversion scratch strings, the Arrow builder slices, and the reload echo-wait loop.

**The conflict, and how to resolve it** — read this before touching anything.

The rule asks for `impl AsMut<[u8]>` write targets. walrus's measured mutable-container surface (15
parameters) contains **no fixed-length byte sink**: 12 parameters need concrete
`String`/`Vec`/`BytesMut` operations, and 3 are already `&mut [T]`. The seven `scratch: &mut String`
parameters in `pg-to-arrow/src/batch.rs` form one reuse path whose leaves clear, grow, search, and
replace within the same `String`; generic `AsMut` would not improve that domain-specific handoff.
Per CONTEXT §3 this is archetype **D** — a documented deviation, not a revert and not a retrofit.
Concretely: **do NOT** put `AsMut` on `crates/common/src/sink_meta.rs:284`,
`crates/loader/src/plan.rs:142`, or the Arrow scratch path. The rule's own "When Not to Use" forbids
it, and `AsMut<String>` / `AsMut<Vec<T>>` widen nothing — they accept exactly the concrete type the
signature already accepts, at the cost of a generic instantiation. What lands instead is the ADR,
an `AsMut` absence guard, and the mutable-borrow gate walrus genuinely lacks.

## Hints & gotchas

- The guard file would match **itself** if it contained the literal `AsMut` + `<` sequence. Build the
  needle at runtime (two concatenated halves) — otherwise the test fails the moment you write it, and
  the "fix" of excluding its own path by name is brittle.
- Scope the compiled guard to `AsMut<` only. Phase 13's `api-impl-asref` work already left the
  legitimate `crates/loader/src/duck.rs:71 open(path: impl AsRef<Path>)`; a guard that denied both
  would reject that intended API. The broad `As(Ref|Mut)<` grep stays in the DoD as a measurement of
  **1** known `AsRef` plus **0** `AsMut`, not as the enforced assertion.
- `clippy::needless_pass_by_ref_mut` is a **nursery** lint. Denying it is safe here only because
  `rust-toolchain.toml` pins `channel = "1.95.0"` exactly (not `"stable"`), so a future toolchain
  cannot widen the lint under you. Say that in the ADR; it is the whole justification.
- Nursery lints are not members of `clippy::all`, so you do **not** need `priority = -1` on `all` —
  the same reasoning the `unwrap_used` / `expect_used` comment at `Cargo.toml:56-60` already records.
  Keep that comment style.
- The `grep -c 'needless_pass_by_ref_mut' Cargo.toml` contract counts comments as well as TOML keys.
  Refer to "this nursery lint" in the explanatory comment; spell the exact name only in the
  assignment so the post-change count is exactly **1**.
- Narrowing a receiver from `&mut self` to `&self` is source-compatible for the caller (a `&mut`
  reborrows as `&`), but it is **not** compatible with a caller that holds another `&mut` borrow of
  the same value across the call. There is exactly one caller —
  `export_next_chunk` at `crates/pg-sink/src/reload_export.rs:362` — so check that line and nothing
  else. Do not "helpfully" narrow `export_next_chunk` too; it mutates `self.chunk_no` / `self.cursor`.
- `await_echo` is private and `async`. The receiver guard therefore has to live in the **sibling**
  `crates/pg-sink/src/reload_export_test.rs` (`#[cfg(test)] #[path = …] mod tests;` — never an inline
  `mod tests {}`), where `use super::*` reaches it. The `Fn(&ChunkExporter, i64) -> Fut` bound is the
  cheapest way to assert the receiver without constructing a `ChunkExporter` (which needs a live
  Postgres connection).
- `clippy::all` and `warnings` are already `deny` workspace-wide and every member declares
  `[lints] workspace = true`, so the new lint takes effect everywhere with no per-crate edit — and it
  applies to `--all-targets`, i.e. tests and benches too. Expect it to fire somewhere unexpected; if
  it does, fix the receiver, and only fall back to an item-level `#[allow(...)]` with a one-line
  reason when the `&mut` is genuinely required by a trait signature.
- `unwrap`/`expect` are `deny` in production; `clippy.toml` re-allows them under `cfg(test)` and in
  integration `tests/`, so the new guard test may use them freely.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it.
- No new dependency: the guard is `std::fs` only. Anything else (a walkdir crate) would have to clear
  `cargo deny` — advisories, the 8-license allow-list, bans — for a 20-line recursive walk.

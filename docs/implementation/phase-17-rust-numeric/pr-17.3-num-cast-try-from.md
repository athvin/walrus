# PR 17.3 — Replace lossy as-casts with TryFrom and deny the four lossy cast lints

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** common,loader,pg-sink,pg-to-arrow,e2e

> **Phase:** 17 — Rust numeric safety · **Crates touched:** `common`, `loader`, `pg-sink`,
> `pg-to-arrow`, `e2e` · **Est. size:** L · **Depends on:** PR 17.2 · **Unlocks:** PR 17.4

Production carries **65** numeric `as` casts across 25 files, and not one lossy-cast lint is denied —
`[workspace.lints.clippy]` (`Cargo.toml:16-22`) sets only `all`, `unwrap_used`, `expect_used`. Run
the tree under `--force-warn clippy::pedantic` and the four *lossy* cast lints fire at **45 unique
sites**: `cast_possible_truncation` 15 (pg-sink 13, pg-to-arrow 2), `cast_sign_loss` 15 (pg-sink 6,
pg-to-arrow 4, loader 3, common 2), `cast_possible_wrap` 12 (pg-sink 7, loader 3, common 1, e2e 1),
`cast_lossless` 3 (common 3). Several are live truncation bugs rather than style: `snapshot.rs:347`
reads a catalog OID as `i64` and does `as u32`, `replication.rs:392` writes a `usize` message length
into a `u32` wire prefix with no check, and `schema.rs:125-126` narrows a 16-bit `numeric` typmod
half to `u8`/`i8` — a `numeric(200,0)` silently becomes a *wrong* Decimal128 type instead of falling
back to the lossless verbatim path. After this PR the four lints are `deny` in
`[workspace.lints.clippy]`, CI's `cargo clippy --all-targets --all-features -- -D warnings` is green
with them on, and every surviving `as` carries a scoped `#[allow]` plus a one-line reason.

## Why — learning objectives

- **`From` for infallible widening vs `TryFrom`/`try_into` for narrowing** — and when a documented
  `#[allow(clippy::cast_*)]` is the honest answer rather than a cop-out.
- **Postgres OIDs are unsigned 32-bit but arrive as `int8` from the catalog and as `Int32` on the
  pgoutput wire** — the sink sits on both encodings at once, which is exactly why the conversion has
  to be explicit at each boundary.

- `crates/common/src/error.rs:123-128` — `From<ExitCode> for std::process::ExitCode`, with the

- `crates/loader/src/lease.rs:21` and `:47`, `crates/pg-sink/src/reload.rs:323-324` — the

  report (`snapshot.rs`, `replication.rs`, `schema.rs`), `u64::from`/`i64::from` where the widening
  is infallible (`lsn.rs:80`, the three `cast_lossless` sites in `common`), and
  `try_from(...).unwrap_or(<bound>)` where saturation is the documented intent
  (`loader/src/lease.rs`, `pg-sink/src/reload.rs`).
- Every cast that survives gets a **scoped** `#[allow(clippy::cast_*)]` at the tightest possible
  scope (expression, statement or item — never a file-level `#![allow]`) plus one line saying why.
- Fix the `tests/e2e` sites so `--all-targets` stays clean.

**Explicitly deferred** (do *not* build these here)

- The `control` crate. Its only cast-lint hits are the allowed `cast_precision_loss`, so it needs no
  code change (it still inherits the new lints — that is fine and should stay green).
- Any `.sql` file or the `.sqlx` offline cache. SQL parameter types stay `int8`/`float8`; only the
  Rust-side conversion changes. There is no Docker on this machine to regenerate the cache.
- Domain newtypes for the OIDs being fixed here. `TableId`, `Oid`, `SchemaVersion` etc. are Phase 18
  (`type-newtype-ids`) and the remaining PR 8.4 slices 2-4. Fix the conversion, keep the type.
- Widening `numeric_precision_scale`'s return from `(u8, i8)` to a 16-bit pair. PG15+ allows scale
  outside `i8`'s range, and the honest fix is a type change with a Tier-1/Tier-2 mapping decision
  behind it. Here, an out-of-range half returns `None` (the existing, lossless
  unconstrained-→-VARCHAR-verbatim path) instead of a silently wrong Decimal128.

**Conflict — two carve-outs must be written down, not blanket-fixed.**

1. **`cast_precision_loss` stays ALLOWED** (it is *not* one of the four lints added). Its 11 sites —
   `crates/common/src/metrics.rs:396/417/423/429`, `crates/control/src/reload.rs:175/214/475`,
   `crates/control/src/table_ownership.rs:50/81` — are `u64 -> f64` into `metrics::gauge!().set()`
   (which takes `f64`) and into sqlx binds of `float8`. That is the API, not a defect. Do **not**
   deny this lint and do **not** "fix" those sites. PR 17.5 re-states this carve-out; keep the two
   descriptions consistent.
2. **`crates/common/src/lsn.rs:145` and `:152` keep `as`** under a scoped `#[allow]` with the
   existing comment intact. These are a deliberate bit-pattern reinterpretation: `pg_lsn`'s binary
   wire format is an 8-byte big-endian integer identical to `int8`, so the encoder is reused.
   `i64::try_from(u64)` there would *reject valid LSNs above `i64::MAX`* — a correctness regression
   dressed up as a safety fix. This is the rule's own "Reserve `as` for … exact semantics are
   required" case; say so in the comment.

```rust
    async fn send_query(&mut self, sql: &str) -> anyhow::Result<()> {
        let mut msg = Vec::with_capacity(6 + sql.len());
        msg.push(b'Q');
        // Frontend `Query`: Int32 length covering itself + the NUL-terminated string. `usize ->
        // u32` is a real narrowing on 64-bit; a >4 GiB query is a bug, so say so instead of
        // wrapping the prefix and desynchronising the protocol stream.
        let len = todo!("u32::try_from(sql.len() + 5).with_context(|| format!(\"query too long for the wire protocol: {} bytes\", sql.len()))?");
        msg.extend_from_slice(&len.to_be_bytes());
        msg.extend_from_slice(sql.as_bytes());
        msg.push(0);
        self.stream.write_all(&msg).await.context("send Query")?;
        self.stream.flush().await?;
        Ok(())
    }
```

```rust
// crates/pg-to-arrow/src/schema.rs

/// Decode a `numeric` `atttypmod` into `(precision, scale)`, or `None` for unconstrained (`-1`).
/// `numeric(p,s)` packs `((p << 16) | s) + VARHDRSZ`; subtract `VARHDRSZ` (4) before unpacking.
///
/// A half that does not fit `(u8, i8)` also returns `None` — the caller then takes the
/// unconstrained path (verbatim VARCHAR, §2.4), which is lossless. Truncating with `as` produced a
/// *wrong* Decimal128 precision instead, which is not.
pub fn numeric_precision_scale(atttypmod: i32) -> Option<(u8, i8)> {
    if atttypmod < 4 {
        return None; // -1 (unconstrained) or an invalid value
    }
    let packed = u32::try_from(atttypmod - 4).ok()?;
    // was: let precision = ((packed >> 16) & 0xFFFF) as u8;
    let precision = todo!("u8::try_from((packed >> 16) & 0xFFFF).ok()?");
    // was: let scale = (packed & 0xFFFF) as i8;
    let scale = todo!("i8::try_from(packed & 0xFFFF).ok()?  — see the deferred note on PG15 scales");
    Some((precision, scale))
}
```

```rust
    impl<'q> Encode<'q, Postgres> for Lsn {
        fn encode_by_ref(
            &self,
            buf: &mut PgArgumentBuffer,
        ) -> Result<sqlx::encode::IsNull, sqlx::error::BoxDynError> {
            // pg_lsn's binary wire format is an 8-byte big-endian integer — identical to int8, so
            // reuse i64's encoder. `as i64` preserves the bit pattern.
            //
            // DELIBERATE (PR 17.3): `i64::try_from` would REJECT every valid LSN above i64::MAX.
            // This is a reinterpretation, not a conversion — the rule's "exact semantics required"
            // carve-out.
            #[allow(clippy::cast_possible_wrap)]
            let raw = self.as_u64() as i64;
            <i64 as Encode<Postgres>>::encode_by_ref(&raw, buf)
        }
    }

    impl<'r> Decode<'r, Postgres> for Lsn {
        fn decode(value: PgValueRef<'r>) -> Result<Self, sqlx::error::BoxDynError> {
            let raw = <i64 as Decode<Postgres>>::decode(value)?;
            // Same bit-pattern carve-out in reverse; see `encode_by_ref`.
            #[allow(clippy::cast_sign_loss)]
            Ok(Lsn::new(raw as u64))
        }
    }
```

## Hints & gotchas

- **Do this in slices, not one commit.** Turn the four lints on locally *first*
  (`cargo clippy --all-targets --all-features -- -D warnings`), read the full list, then fix crate by
  crate: `common` → `pg-to-arrow` → `loader` → `pg-sink` → `tests/e2e`. The Cargo.toml edit lands
  with the last of them so the branch is never red for a whole afternoon.
- `#[allow(...)]` must sit on an **item, statement or expression** — you often need to bind the cast
  to a `let` first (see the `lsn.rs` skeleton). A file-level `#![allow]` defeats the whole PR.
- `.try_into()` frequently needs a type annotation or turbofish: `let n: u32 = x.try_into()?;`.
  Prefer the explicit `u32::try_from(x)` form — it reads better in a struct literal and never leaves
  inference guessing.
- `TryFromIntError` implements `std::error::Error`, so `?` composes with `anyhow` directly; with
  `.with_context(...)` you get the offending value in the message, which is what makes the
  `snapshot.rs` change worth doing.
- `clippy::cast_lossless` wants `u64::from(x)`, not `x.into()`, when the target is ambiguous. Both
  compile; the explicit one survives a later refactor.
- Careful with `usize` on 32-bit: `u32::try_from(usize)` is *not* a no-op cast that clippy will let
  you skip. Keep `try_from`; the compiler optimises the impossible branch away on 64-bit.
- **`unwrap`/`expect` are `deny` in production.** `unwrap_or(i64::MAX)` and `.ok()?` are fine;
  `.unwrap()` is not. `clippy.toml` re-allows both under `#[cfg(test)]` and in integration `tests/`.
- `tests/e2e` is a workspace member with `[lints] workspace = true`, and its `tests/*.rs` targets are
  linted by `--all-targets`. Do not forget `reload_scale.rs:103`; CI will.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it. `::int8` in the catalog queries and `int8`/`float8` binds all stay.
- The DuckDB-backed `crates/pg-to-arrow/tests/conformance.rs` is behind `--features conformance` and
  compiles the bundled DuckDB from source (cold ≈ 20 min). Run the cheap unit suites while
  iterating; let CI carry the conformance job.

# PR 17.5 — Gate float equality with clippy::float_cmp and validate the backpressure ratios as finite

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink,pg-to-arrow

> **Phase:** 17 — Rust numeric safety · **Crates touched:** `pg-sink`, `pg-to-arrow` ·
> **Est. size:** S · **Depends on:** PR 17.4 · **Unlocks:** PR 18.1

Production is already conformant on the letter of this rule — **0** `==` comparisons against float
literals anywhere in `crates/*/src` minus `*_test.rs`. Nothing enforces it: `clippy::float_cmp` is
allow-by-default and absent from `[workspace.lints.clippy]`, and it already reports **2** unique
sites, raised by **6** `assert_eq!` calls on `f64` in
`crates/pg-to-arrow/src/geometric_test.rs:5,37,50`
and `crates/pg-to-arrow/src/batch_test.rs:393,394,477`. The tree is also blind to float *special
values*: there are **0** uses of `is_nan`/`is_finite`/`is_infinite`/`total_cmp`/`partial_cmp` in the
whole repo, and `pub fn Backpressure::new` (`crates/pg-sink/src/memory.rs:109`) happily accepts a
`NaN` ratio — after which `tick`'s `>=` and `<=` (`:125`, `:128`) both return `false` forever and the
pause-poll backstop is silently disabled. That is an OOM-kill, not a rounding curiosity. This PR
turns the lint on, fixes the six call sites with a tolerance helper instead of suppressing them,
makes finiteness an explicit predicate at both boundaries, and adds a golden vector proving a
Postgres `float8` `NaN` / `Infinity` / `-Infinity` survives the decode path intact.

## Why — learning objectives

- **IEEE-754 `NaN` poisoning of `>=`/`<=`, `is_finite` as a boundary predicate, tolerance-based
  equality, and `total_cmp` for a panic-free total order** — four distinct tools, one of which
  (`total_cmp`) this PR deliberately does not need yet.
- **A silently-disabled backpressure backstop is an OOM-kill** — the sink's aggregate in-flight
  ceiling is only as good as the ratio that gates it, so the ratio has to be validated as a value,
  not assumed as a comment.

## Read first

- [`num-float-compare`](../../../.claude/skills/rust-skills/rules/num-float-compare.md) — take the
  `approx_eq` helper shape, the `NaN != NaN` fact, and the Key Point about epsilon choice (absolute
  vs relative). The tolerance helper this PR adds is used only on small, exactly-representable
  coordinates, so an absolute epsilon is defensible — write down *why* in its doc comment.
- `crates/pg-sink/src/memory.rs:99-137` — `Backpressure`, its two `f64` ratio fields, `new` (`:109`)
  and `tick` (`:118-132`). `:125`/`:128` are the two comparisons `NaN` poisons.
- `crates/pg-sink/src/config.rs:58-61` (the two ratio fields) and `:271-283` — the hysteresis band
  check `!(0.0 < resume && resume < activate && activate < 1.0)`. Work out for yourself what that
  expression does with `NaN` **before** you change it: it happens to reject, by short-circuit. The
  point of this PR is that "happens to" is not a contract.
- `crates/pg-sink/src/config.rs:180-185` — `SinkConfig::backpressure()`, the only production caller
  of `Backpressure::new`.
- `crates/pg-to-arrow/src/geometric.rs:95-120` — `Pt { x: f64, y: f64 }` with a derived `PartialEq`,
  and `parse_f64` (`:109`), the sole entry point for every geometric coordinate.
- `crates/pg-to-arrow/src/batch.rs:715-744` — `append_num`, the generic `s.parse::<T>()` path that
  `Float64Builder` goes through (`:285`, `:767`). This is where a Postgres `NaN` text value lands.
- The six offending assertions: `crates/pg-to-arrow/src/geometric_test.rs:5,37,50` and

**In scope**

- `Cargo.toml`: `float_cmp = "deny"` in `[workspace.lints.clippy]`, next to the four lossy-cast
  lints PR 17.3 added, with a comment naming the tolerance helper as the sanctioned alternative.
- A test-only tolerance helper module, `crates/pg-to-arrow/src/approx.rs` (declared
  `#[cfg(test)] mod approx;` in `lib.rs`), exposing `assert_approx_eq(a: f64, b: f64)` and
  `assert_pt_approx(got: Pt, x: f64, y: f64)`.
- Rewrite the six `assert_eq!`-on-float sites to use it. `Pt` keeps its derived `PartialEq` — the
  tests stop *using* it for float comparison, the type does not change.
- `Backpressure::new` becomes fallible —
  `pub fn new(activate_ratio: f64, resume_ratio: f64) -> Option<Self>`,
  returning `None` when either ratio is not finite. `SinkConfig::backpressure()` follows
  (`-> Option<Backpressure>`), documented as always `Some` once `validate()` has passed.
- `SinkConfig::validate` gains an explicit `is_finite()` check on both ratios **before** the band
  check, with its own `ConfigError::OutOfBounds` message — so a `NaN` is rejected because it is not
  finite, not because a comparison chain happened to short-circuit.
- A new golden vector in `crates/pg-to-arrow/src/batch_test.rs`: Postgres `float8` values `NaN`,
  `Infinity` and `-Infinity` round-trip through `append_num`'s `str::parse::<f64>` into the
  `Float64` array, asserted with `is_nan()` / `is_infinite()` / `is_sign_negative()` — never `==`.

**Explicitly deferred** (do *not* build these here)

- Changing the backpressure hysteresis *semantics* or the `f64` field types on `SinkConfig`. This PR
  adds a predicate and a lint; the band, the ratios and the defaults are untouched.
- `total_cmp` sorting. No float is sorted anywhere in walrus today; introducing a comparator with no
  caller would be dead code. The rule's `total_cmp` material is read, not applied.
- Denying `clippy::cast_precision_loss`. That carve-out was decided in PR 17.3 and stands:
  `u64 -> f64` into `metrics::gauge!().set()` and sqlx `float8` binds is the API, not a defect.
  `Backpressure::tick`'s own `as f64` casts are covered by it.
- Any `.sql` / `.sqlx` change, and any change to how DuckDB stores a `DOUBLE`.

**Conflict — the rule must NOT be applied by suppression.** `clippy::float_cmp` is reported at the
**expansion** site inside `core/src/macros/mod.rs`, not at the walrus `assert_eq!` line, so
`#[allow(clippy::float_cmp)]` cannot be placed at the anchor the compiler prints and a file-level
`#![allow]` would blanket-disable the lint in exactly the file that needs it most. Required
resolution: **fix all six call sites with the tolerance helper**, and never `assert_eq!` a bare `f64`
(or a struct/tuple of them) again. If you find yourself reaching for `#[allow]`, you are in the wrong
place.

const EPSILON: f64 = 1e-9;

#[track_caller]
pub(crate) fn assert_approx_eq(got: f64, want: f64) {
    todo!("assert!((got - want).abs() < EPSILON, \"{got} != {want} (tolerance {EPSILON})\")");
}

pub(crate) fn assert_pt_approx(got: Pt, x: f64, y: f64) {
    assert_approx_eq(got.x, x);

impl Backpressure {
    /// Build the hysteresis gate. `None` when either ratio is not finite: a `NaN` ratio makes both
    /// comparisons in [`Backpressure::tick`] return `false` forever, which silently disables the
    /// pause-poll backstop — i.e. an OOM-kill instead of a graceful spill (§1.3).
    pub fn new(activate_ratio: f64, resume_ratio: f64) -> Option<Self> {
        if todo!("!activate_ratio.is_finite() || !resume_ratio.is_finite()") {
            return None;
        }
        Some(Backpressure {
            activate_ratio,
            resume_ratio,
            paused: false,
        })
    }
    // `tick` is unchanged — its comparisons are now total because `new` is the only constructor
    // and it refuses non-finite input.
}

## Hints & gotchas

- **`assert_eq!(x, f64::NAN)` can never pass.** `NaN != NaN` by IEEE-754. If a test "needs" that
  comparison, it needs `is_nan()` instead — which is exactly what the new golden vector demonstrates.
- **`float_cmp` fires inside the macro expansion.** `cargo clippy` will point at
  `core/src/macros/mod.rs`, not at your line; read the `note:` trailer for the real call site, or run
  with `--message-format=short`. Do not chase the reported path.
- The lint also fires on `assert_eq!` of a **struct or tuple containing floats** (`Pt`,
  `(f64, f64, f64)`) via the derived `PartialEq` — that is why `geometric_test.rs:5,37` count.
  Compare fields, not aggregates.
- `#[track_caller]` on the helpers is what makes a failure point at the test line instead of at
  `approx.rs`. Without it the helper is materially worse than the `assert_eq!` it replaced.
- **PR 17.4 already deleted the `if ceiling == 0 { f64::INFINITY }` branch** at the old
  `memory.rs:119-123`. If your `grep -c 'f64::INFINITY' crates/pg-sink/src/memory.rs` reads **0**
  rather than the 1 recorded when this ticket was written, that is expected — not a regression, and
  not something to restore.
- `Backpressure::new` has exactly two call sites (`config.rs:181` and `memory_test.rs:55`), so the
  `Option` return is a cheap change. Resist widening it to `Result` — there is no error payload worth
  carrying, and `validate()` already produces the operator-facing message.
- Do **not** add the `approx` or `float-cmp` crate. Every new dependency must clear `cargo deny`
  (advisories, the 8-license allow-list, bans) and this is a five-line helper.
- `approx.rs` is a `#[cfg(test)] mod`, **not** a `foo_test.rs` sibling — it is shared test
  *infrastructure*, not the tests for a module. Keep the Go-style sibling convention for actual test
  files (47 modules use it; there are zero inline `mod tests {}`).
- `clippy::all` + `warnings` are `deny` workspace-wide, so an unused helper is a hard error. Wire
  both functions to real call sites in the same PR.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it. DuckDB's `DOUBLE` handling of `NaN`/`Infinity` is a read-back question
  for the conformance harness, not for this PR.

# PR 17.4 — Encode must-be-positive config bounds as NonZero types

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** loader,pg-sink

> **Phase:** 17 — Rust numeric safety · **Crates touched:** `pg-sink`, `loader` ·
> **Est. size:** M · **Depends on:** PR 17.3 · **Unlocks:** PR 17.5

There is not a single `NonZero*` anywhere in walrus — `grep -rn 'NonZero' crates/ tests/ | wc -l` is
**0**. The zero-forbidding invariant is instead re-litigated at runtime, three times over, and one of
the three re-litigations is missing entirely. `crates/pg-sink/src/config.rs:304` defines
`fn positive(field, v: u64)` and calls it five times (`:234-238`) — a post-parse check that runs
*after* figment has already built the struct. `crates/pg-sink/src/memory.rs:119` still carries a
defensive `if ceiling == 0 { f64::INFINITY }` branch downstream of that very check, because the type
`u64` cannot tell `Backpressure::tick` what `validate` already proved. And the loader's
`max_files_per_cycle: i64` (`crates/loader/src/config.rs:39`) has **no validation at all** —
`LoaderConfig::validate` only looks at `lease_ttl` — so `WALRUS_MAX_FILES_PER_CYCLE=0` yields a
Phase-A loop that claims zero manifests every cycle and quietly never advances. After this PR the
invariant lives in the type: serde rejects zero *at deserialization*, `InflightMeter::new` cannot be
handed a zero ceiling, and the defensive branch is deleted rather than commented.

## Why — learning objectives

- **`NonZeroU64::new` → `Option`, `.get()`, `NonZeroU64::MAX`, serde's zero-rejecting `Deserialize`,
  and the niche optimisation** that makes `Option<NonZeroU64>` exactly 8 bytes.
- **Pushing a CDC config invariant to the type level deletes the downstream defensive branch** — the
  backpressure ratio can no longer divide by a zero ceiling, so the `f64::INFINITY` escape hatch
  stops existing instead of merely being unreachable.

**In scope**

- `SinkConfig`: `max_rows`, `max_bytes`, `max_inflight_bytes`, `max_concurrent_reloads`,
  `reload_chunk_rows` → `NonZeroU64`. Delete `fn positive` and its five call sites.
- `BatchTriggers.max_rows` / `.max_bytes` → `NonZeroU64`; `should_flush` compares with `.get()`.
  `reload_export.rs:365-366`'s `u64::MAX` sentinels become `NonZeroU64::MAX`.
- `InflightMeter::new(ceiling_bytes: NonZeroU64)`; the field and `ceiling()` follow.
  `Backpressure::tick(total: u64, ceiling: NonZeroU64)` — **delete** the `if ceiling == 0` branch and
  the `f64::INFINITY` it returns.
- `ReloadControllerConfig.chunk_rows` and `ChunkExportConfig.chunk_rows` → `NonZeroU64`.
- `LoaderConfig.max_files_per_cycle` → `NonZeroI64`; `phase_a::TableCtx.max_files` follows;
  `control::claim_ready` still receives an `i64` via `.get()`.
- **`crates/loader/src/config.rs` gets a `poll_interval` / `compaction_interval` zero-check in
  `validate`** — `Duration` has no `NonZero` analogue and `tokio::time::interval(Duration::ZERO)`
  panics (`apply_loop.rs:18`). This is the one invariant that stays in `validate`, and it must be
  added there because this PR is the one that reads the file and notices.
- New sibling test cases: the niche-size assertion, the "zero is rejected at *deserialization*"
  assertion for both configs, and a Phase-A/meter case proving the deleted branch is unreachable by
  construction.

**Explicitly deferred** (do *not* build these here)

- Converting `Duration` fields (`lease_ttl`, `poll_interval`, `compaction_interval`, `max_fill`,
  `startup_deadline`, …). `Duration` has no `NonZero` analogue; their guards stay in `validate()`.
- `retention_lsn_lag` — `0` means "no retention", a legal setting. Leave it a bare `u64`.
- `reload_max_restarts: i32` — `0` is documented as legal ("fail on the first mid-export DDL",
  `config.rs:241-250`). Leave it.
- Any `.sql` change or `.sqlx` cache regeneration. `NonZeroI64::get()` binds the same `int8`; the
  query files and the offline cache are untouched (and there is no Docker here to rebuild them).
- Newtypes over the converted fields (`MaxRows(NonZeroU64)` etc.). That is Phase 18.

use std::num::NonZeroU64;

pub struct InflightMeter {
    ceiling_bytes: NonZeroU64,
    total: u64,
    by_stream: HashMap<(TableId, u32), u64>,
}

impl InflightMeter {
    pub fn new(ceiling_bytes: NonZeroU64) -> Self { todo!("field init; total: 0") }

    pub fn ceiling(&self) -> NonZeroU64 { self.ceiling_bytes }

    pub fn over_ceiling(&self) -> bool { self.total > self.ceiling_bytes.get() }
}

impl Backpressure {
    /// Update from the current total vs ceiling; returns whether intake should be PAUSED afterwards.
    ///
    /// `ceiling` is `NonZeroU64`, so the division is total — the old
    /// `if ceiling == 0 { f64::INFINITY }` escape hatch is gone with it (PR 17.4).
    pub fn tick(&mut self, total: u64, ceiling: NonZeroU64) -> bool {
        // `as f64` stays: `cast_precision_loss` is the documented carve-out from PR 17.3.
        let ratio = todo!("total as f64 / ceiling.get() as f64");
        if self.paused {
            if ratio <= self.resume_ratio {
                self.paused = false;
            }
        } else if ratio >= self.activate_ratio {
            self.paused = true;
        }
        self.paused
    }
}

## Hints & gotchas

- **`expect_used` is `deny` in production**, so the rule's `NonZeroU32::new(n).expect(...)` idiom is
  unavailable in `src/`. For the `Default` impl use either
  `NonZeroU64::new(100_000).unwrap_or(NonZeroU64::MIN)` (honest, but hides the constant) or —
  better — a `const`:
  `const DEFAULT_MAX_ROWS: NonZeroU64 = NonZeroU64::new(100_000).unwrap();` at item scope. `unwrap`
  in a `const` initialiser is evaluated at compile time; if clippy still objects, put the scoped
  `#[allow(clippy::unwrap_used)]` **on the const item** with a one-line "const-evaluated" reason.
- `NonZero*` has **no `Add`/`Sub`**. Anywhere you did arithmetic on these fields, `.get()` first and
  reconstruct only if the result must stay non-zero.
- `NonZeroU64::MAX` exists — use it for the `u64::MAX` sentinels at `reload_export.rs:365-366`. Do
  not write `NonZeroU64::new(u64::MAX).unwrap()`.
- `serde` implements `Deserialize` for `NonZero*` with a zero-rejecting error out of the box; you do
  **not** need a custom `deserialize_with`. That error message is the DoD's "strictly earlier failure
  point".
- The `#[serde(default)]` at the container level (`config.rs:20`) is what makes a one-key
  `Toml::string("max_rows = 0")` a complete document in the test — no env-var mutation, no
  `figment::Jail`, no new dev-dependency.
- **This is a wide, mechanical change.** `BatchTriggers` is constructed in seven places including
  three `*_test.rs` files. Let `cargo check -p pg-sink --all-targets` drive the list; do not try to
  find them by eye.
- `memory_test.rs:44` builds `InflightMeter::new(0)` and pokes the private `total` field. That case
  must be rewritten (see the Skeleton) — it is a sibling module, so private-field access keeps
  working.
- `Backpressure::tick` is currently exercised only from `memory_test.rs`; the production wiring lands
  later. That is fine — deleting the `ceiling == 0` branch is still the point, and the test suite is
  the only caller you have to update.
- `apply_loop.rs:18`'s `tokio::time::interval(ctx.poll_interval)` panic is real but is **not** a
  `NonZero` fix — `Duration` has no such type. It is fixed by the new `validate` check; say so in the
  PR body so nobody "fixes" it twice.
- `unwrap`/`expect` are re-allowed under `#[cfg(test)]` by `clippy.toml`, so
  `NonZeroU64::new(1).unwrap()` in sibling tests is fine.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it. `control::claim_ready` keeps its `i64` parameter; pass
  `ctx.max_files.get()`.

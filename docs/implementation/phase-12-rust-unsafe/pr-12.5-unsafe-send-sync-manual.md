# PR 12.5 — Correct the loader's Send/Sync claims and pin them with compile-time assertions

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** loader

> **Phase:** 12 — Rust unsafe-code policy · **Crates touched:** `loader` · **Est. size:** M ·
> **Depends on:** PR 12.4 · **Unlocks:** PR 12.6

Two production comments state the loader's threading invariant, and **both are factually wrong**.
`crates/loader/src/duck.rs:38-39` and `crates/loader/src/main.rs:104-105` say DuckDB's `Connection`
is `!Send` — but `duckdb-1.10504.0` carries `unsafe impl Send for Connection {}`
(`~/.cargo/registry/src/*/duckdb-1.10504.0/src/lib.rs:272`) and **no** `Sync` impl. The connection is
`Send + !Sync`, and it is the **`!Sync`** — a `RefCell<InnerConnection>` inside, mirrored by walrus's
own `RefCell` at `duck.rs:40` — that makes a future holding `&TableCtx` non-`Send`, which is what the
14 `clippy::future_not_send` sites in `loader` are actually reporting. walrus writes zero
`unsafe impl Send`/`Sync` (correct!) but has **zero mechanical checks** of the invariant either
(`grep -rnE 'fn assert_send|fn assert_sync|assert_impl' crates tests | wc -l` → `0`), so the prose
drifted with nothing to catch it. This PR fixes both comments and pins the real invariant with
compile-time assertions — **no `unsafe impl`, no new dependency**.

## Why — learning objectives

- **`Send`/`Sync` are unsafe auto-traits** — the compiler derives them structurally; a manual
  `unsafe impl` is a promise it cannot verify. The relationship that matters here: `&T: Send`
  requires `T: Sync`. That is why a `Send` connection inside a `!Sync` cell still yields a non-`Send`
  future the moment the future holds a `&TableCtx` across an `.await`.
- **Positive and negative trait assertions on stable, with no dependency** — a positive assertion is
  a generic `fn assert_send<T: Send>()` invoked inside `const _: fn() = || { … };`. A *negative* one
  needs the two-blanket-impl ambiguity trick (what `static_assertions::assert_not_impl_all!` does):
  the call resolves only while the type does **not** implement the trait.
- **walrus's loader concurrency model** — one `.duckdb` file per owned table, one apply worker per
  file, all running on a single-threaded `tokio::task::LocalSet` (`main.rs:106`, `:132`). The only
  value that legitimately crosses to another thread is the `InterruptHandle`
  (`compaction.rs:71-73`), which duckdb-rs declares `Send + Sync` and which the drain uses to abort
  an in-flight `CREATE OR REPLACE`.
- **Comments rot; assertions don't** — the artifact of this PR is not the corrected prose, it is the
  fact that flipping `TableDb`'s `RefCell` to a `Mutex` now breaks the build loudly instead of
  silently changing the runtime model.

    fn assert_send<T: Send + ?Sized>() {}
    fn assert_sync<T: Sync + ?Sized>() {}

    // `TableDb` moves into `TableCtx` (phase_a.rs:28) and thence into `spawn_local` (main.rs:132).

    // Shared between the health server (main.rs:58) and every worker.
    todo!("assert_send + assert_sync for std::sync::Arc<crate::health::LoaderState>");
};

// Negative assertion: resolves ONLY while `TableDb` is *not* `Sync`. If someone swaps the `RefCell`
// above for a `Mutex`, `TableDb` becomes `Sync`, BOTH blanket impls apply, and the method call below
// becomes ambiguous → compile error naming this line. (This is the trick behind
// `static_assertions::assert_not_impl_all!`, hand-rolled to avoid a new dependency.)
const _: fn() = || {
    trait AmbiguousIfSync<A> {
        fn some_item() {}
    }
    impl<T: ?Sized> AmbiguousIfSync<()> for T {}
    impl<T: ?Sized + Sync> AmbiguousIfSync<u8> for T {}
    let _ = todo!("<TableDb as AmbiguousIfSync<_>>::some_item");
};

## Hints & gotchas

- **`&T: Send` requires `T: Sync`.** That single rule is the whole story: `TableDb` being `Send` is
  irrelevant to `future_not_send`; the futures are non-`Send` because they hold a `&TableCtx` across
  an `.await` and `TableCtx` is `!Sync`. Get this right in the corrected comments — an
  almost-right comment is what created this ticket.
- **Do not "fix" the 14 `clippy::future_not_send` diagnostics.** They are pedantic-tier and not
  currently denied, so they do not fail CI. Making those futures `Send` would mean removing the
  `RefCell`s and moving to a multi-threaded runtime — a redesign, not a lint fix.
- The negative assertion is subtle: it works because *two* blanket impls exist and only one applies
  while the type is `!Sync`. Keep both `impl` lines and the `?Sized` bounds exactly as shown, and
  keep the items at the top of the closure body (statements-then-items ordering keeps clippy quiet).
  Add a comment saying it is `static_assertions::assert_not_impl_all!` hand-rolled — otherwise it
  reads as nonsense to the next person.
- `conn.interrupt_handle()` returns `std::sync::Arc<duckdb::InterruptHandle>`. Assert on
  `duckdb::InterruptHandle` itself; the `Arc` wrapper's `Send`/`Sync` then follows from it.
- `duckdb::InterruptHandle` is re-exported at `duckdb::InterruptHandle` (see
  `duckdb-1.10504.0/src/lib.rs:82`), so no extra path gymnastics are needed in the assertion.
- The assertion block must live **above** `#[cfg(test)] #[path = "duck_test.rs"] mod tests;`
  (`duck.rs:404-406`) so it is compiled in *production* builds, not only under `cfg(test)`.
- Tests in walrus are **Go-style sibling files**. Put the new test in the existing
  `crates/loader/src/duck_test.rs` (which already `use super::*;` and has `orders()`); do **not**
  create an inline `mod tests {}`.
- `unwrap`/`expect` are denied in production by `[workspace.lints.clippy]` but re-allowed in tests by
  `clippy.toml` (`allow-unwrap-in-tests`, `allow-expect-in-tests`) — the existing sibling test uses
  `.unwrap()` freely, so match that style *inside the test only*.
- `cargo test -p loader` links **bundled DuckDB** (`crates/loader/Cargo.toml:23`): a cold build is
  ~20 minutes, warm is ~3. Do not interpret a slow first run as a hang, and do not switch to
  `cargo check` as your only verification — the new test must actually run.
- Do not add `static_assertions`, `dtolnay/portable-atomic`, or anything else. Any new dependency
  must clear `cargo deny`, and there is nothing here that fifteen lines of stable Rust cannot do.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it.

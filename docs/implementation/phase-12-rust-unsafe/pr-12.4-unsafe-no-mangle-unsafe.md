# PR 12.4 — Deny unsafe_attr_outside_unsafe so exported symbols stay auditable

> **Phase:** 12 — Rust unsafe-code policy · **Crates touched:** *(workspace manifest only)* ·
> **Est. size:** S · **Depends on:** PR 12.3 · **Unlocks:** PR 12.5

There are **zero** `#[no_mangle]` / `#[export_name]` / `#[link_section]` attributes in the tree
(`grep -rn --include='*.rs' -E '#\[(unsafe\()?(no_mangle|export_name|link_section)' crates tests | wc -l`
→ `0`) and **no crate declares a `crate-type`**
(`grep -rn 'crate-type' crates/*/Cargo.toml tests/*/Cargo.toml` → no matches), so walrus ships two
plain binaries — `walrus-pg-sink` (`crates/pg-sink/Cargo.toml:11-14`) and `walrus-loader`
(`crates/loader/Cargo.toml:11-14`) — with no `cdylib`, no plugin ABI, and no exported symbol surface
at all. The rustc lint that catches the pre-2024 bare spelling is `unsafe_attr_outside_unsafe`,
reported `allow` by `rustc -W help` and absent from `Cargo.toml`. This PR closes the last of the four
edition-2024 unsafe gates for one line.

## Why — learning objectives

- **Why `#[no_mangle]` became an unsafe attribute in Rust 2024** — if two items in the same binary
  export the same symbol name, the linker silently picks one and discards the other. The survivor may
  have a different signature or different semantics: type-level undefined behaviour with **no**
  diagnostic from compiler or linker, and no `unsafe {}` anywhere at the call site. The
  `#[unsafe(...)]` wrapper makes that responsibility visible and greppable.
- **`unsafe(...)` on an attribute ≠ an unsafe block** — it does not change what callers must write.
  It marks the *attribute itself* as load-bearing for soundness: the author is accepting
  responsibility for symbol uniqueness and ABI correctness.
- **walrus's deployment shape** — two statically-linked binaries baked into container images. There
  is no plugin ABI to keep stable, which is precisely why this gate is free today and worth having
  before someone adds a `cdylib` in a hurry.

## Hints & gotchas

- The `unsafe(...)` wrapper does **not** require an `unsafe {}` at the call site — it annotates the
  attribute, not the function body. Do not "helpfully" mention unsafe blocks in the manifest comment;
  it would teach the wrong model.
- This lint is part of `rust_2024_compatibility`. Enable only this lint, as in PRs 12.2 and 12.3 —
  the group also contains drop-timing and scoping changes that need behavioural review.
- `#[unsafe(no_mangle)]` is accepted by rustc from 1.82 onward, and `rust-toolchain.toml:4` pins
  1.95.0, so the corrected spelling would compile if it were ever needed. It still would not pass
  PR 12.1's `forbid` — by design.
- A symbol collision is only dangerous when something *links* your symbols: plugin architectures,
  `cdylib`s, embedded firmware with custom linker scripts. walrus is none of these — say so in the
  comment so the lint's presence reads as prevention, not cargo-culting.
- Run the exact CI command (`.github/workflows/ci.yml:96`):
  `cargo clippy --all-targets --all-features -- -D warnings`. `--all-features` compiles
  `pg-to-arrow`'s `conformance` feature → bundled DuckDB C++ → minutes on a cold cache.
- Tests are Go-style sibling files (`src/foo.rs` → `src/foo_test.rs`), never inline `mod tests {}`.
  This PR adds no test; its probe is the manifest grep plus the reverted manual probe.
- `unwrap`/`expect` are denied in production by `[workspace.lints.clippy]` and re-allowed in tests by
  `clippy.toml` — untouched here.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache (no Docker on this machine to
  regenerate it). Add no dependency; any new one must clear `cargo deny`.

# PR 12.2 — Deny unsafe_op_in_unsafe_fn and multiple unsafe ops per block

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** —

> **Phase:** 12 — Rust unsafe-code policy · **Crates touched:** *(workspace manifest only)* ·
> **Est. size:** S · **Depends on:** PR 12.1 · **Unlocks:** PR 12.3

PR 12.1 built the wall (`unsafe_code = "forbid"`). This PR writes the rules that apply the day
someone deliberately steps outside it. Both lints that mechanically enforce *"one unsafe op, smallest
possible block"* are allow-by-default and absent from the workspace table: `rustc -W help` reports
`unsafe-op-in-unsafe-fn  allow`, and `cargo clippy -- -W help` reports
`clippy::multiple-unsafe-ops-per-block  allow`. Because both sit at `allow`, the existing
`warnings = "deny"` at `Cargo.toml:13` does not cover either. walrus is **edition 2021**
(`Cargo.toml:6`), where `unsafe_op_in_unsafe_fn` is not enabled by the edition. Edition 2024 enables
it as a warning by default, which walrus's `warnings = "deny"` would promote to an error. Denying it
now pre-pays that migration at literally zero cost, because there are **zero `unsafe fn`s** in the
tree to fix.

## Why — learning objectives

- **`unsafe_op_in_unsafe_fn`** — in edition 2021 an `unsafe fn` body is *implicitly* one big unsafe
  block, so every line inside looks equally suspect; in edition 2024 each unsafe operation needs its
  own `unsafe {}` (and its own `// SAFETY:`). Promoting the lint in 2021 is how you stage an edition
  migration one lint at a time instead of one big-bang `cargo fix --edition`.
- **Minimum-scope as a reviewability property** — a small block plus a `// SAFETY:` comment names
  exactly which invariant is being asserted; `clippy::multiple_unsafe_ops_per_block` is the
  mechanical version of "if two ops need different justifications, they need different blocks".
- **walrus toolchain discipline** — `rust-toolchain.toml:4` pins `channel = "1.95.0"` *exactly*
  (not `"stable"`), with a written rationale: local and CI builds agree byte-for-byte and a new
  stable release can never turn a fresh lint into a CI failure. A lint promotion here cannot be
  invalidated by a compiler bump behind your back.

## Hints & gotchas

- **These two lints are unreachable while PR 12.1's `forbid` stands.** That is deliberate and worth
  a sentence in the manifest comment: the forbid is the outer wall, these are the rules that apply
  inside any future, deliberate exception. Do not "simplify" by deleting them.
- The two inner lints are intentionally unreachable while the outer forbid stands. Verify their
  levels statically and keep the checkout policy intact; a synthetic unsafe probe is not required.
- `unsafe_op_in_unsafe_fn` belongs to the `rust_2024_compatibility` group. Do **not** enable the
  whole group as a shortcut — it drags in `if_let_rescope` and `tail_expr_drop_order`, which change
  *drop timing* and would need real behavioural review across the loader's `LocalSet` workers.
- MSRV: the lint has been stable well before 1.95, and `rust-toolchain.toml:4` pins 1.95.0 exactly,
  so there is no MSRV risk here. CI's `msrv` job would catch it if there were.
- Keep the comment style of `Cargo.toml:17-19`. Every non-`clippy::all` lint in this file explains
  *why* it needs no `priority` — a reader who does not know the group/lint precedence rule will
  otherwise "fix" it by adding one.
- Run the exact CI command (`.github/workflows/ci.yml:96`):
  `cargo clippy --all-targets --all-features -- -D warnings`. `--all-features` builds
  `pg-to-arrow`'s `conformance` feature, which compiles bundled DuckDB from C++ — minutes on a cold
  cache, seconds warm.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache (no Docker on this machine to
  regenerate it), and add no dependency — any new one must clear `cargo deny`.
- Unit tests are Go-style sibling files (`src/foo.rs` → `src/foo_test.rs`), never inline
  `mod tests {}`. This PR adds no test file at all; its probe is the manifest grep.

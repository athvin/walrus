# PR 11.17 — Record why walrus has no arena-shaped allocation lifetime

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test · **Test packages:** —

> **Phase:** 11 — Rust memory optimization · **Crates touched:** *none* — `docs/`, `scripts/`, CI ·
> **Est. size:** S · **Depends on:** PR 11.16 · **Unlocks:** PR 12.1

Arenas pay off for parse-tree or request-scoped **graphs** freed all at once. walrus has neither.
The pgoutput decoder is a flat cursor over a borrowed `&'a [u8]`
(`crates/pg-sink/src/pgoutput/reader.rs:15-18` — two fields, `buf` and `pos`) that produces one
pre-sized `Vec<TupleValue>` per row (`mod.rs:228-250`); there is no recursive node type, nothing
that outlives the frame, and nothing to bump-allocate. On the other side, the loader's per-cycle
cost is **DuckDB-side, not Rust-side**: `apply_transform` (`crates/loader/src/transform.rs:368-375`)
hands one rendered statement to `conn.execute_batch`, and `docs/benchmarks.md`'s `EXPLAIN ANALYZE`
names the window `HASH_GROUP_BY` as the cost centre — the same section where the TOAST back-scan
rewrite was **declined for a measured ≈0 delta**. The rule's thread-local scratch-arena pattern
does not fit either: `thread_local!` count in `crates/**` is **0**, and the loader runs `!Send`
DuckDB connections one-per-worker on a tokio `LocalSet` (`main.rs:111-113`, `duck.rs:38-42`), so
there is no worker pool for a per-thread arena to amortise across. `bumpalo` is in `Cargo.lock`
transitively (via `wasm-bindgen-macro-support` and `zopfli`) but has never been a direct
dependency. After this merges that reasoning is an ADR, and a CI guard keeps the direct-dependency
count of every crate Phase 11 declined at **0** — closing the phase.

## Why — learning objectives

- **Bump allocation and batch-freed lifetimes** — an arena makes allocation a pointer bump and frees
  everything in O(1) at reset; the precondition is that all the allocations share one lifetime and
  nothing escapes it. Recognising the *absence* of that shape is the skill this ticket teaches.
- **The loader's `!Send` DuckDB connection per worker on a tokio `LocalSet`** — walrus's parallelism
  model is one worker per `.duckdb` file on a single thread, which is why a `thread_local!` scratch
  arena has nothing to amortise over.

**The conflict, and how to resolve it** — CONTEXT §4 bench-gates the arena crates alongside
`mem-smallvec`. Here the decline is **structural first**: no arena-shaped lifetime (a flat cursor
and per-row `Vec`s, nothing escaping into a graph), zero `thread_local!`, and `!Send` connections
pinned one-per-worker to a `LocalSet` so the scratch-arena pattern has no pool to amortise over.
Only *secondarily* is it about the benchmark — the loader's measured cost centre is inside DuckDB.
Say that with those anchors. **"Not relevant" is not an acceptable ADR.**

## Hints & gotchas

- **Do not use `cargo deny`'s `[bans] deny` list for this.** It matches the whole dependency
  graph, so banning `bumpalo` would fail instantly on the `wasm-bindgen-macro-support` / `zopfli`
  edges. The guard must be manifest-scoped, which is why it is a shell script.
- The guard's name list encodes **decisions**, not dogma. If PR 11.13 adopted `smallvec` on its
  measurement, drop that row and say so in the ADR — a guard that contradicts a merged measurement
  is worse than no guard.
- Match the existing script conventions: `#!/usr/bin/env bash`, `set -euo pipefail`,
  `cd "$(git rev-parse --show-toplevel)"`, a header comment with the invocation line, and `chmod +x`
  (every file in `scripts/` is `0755`). CI invokes them as `bash scripts/<name>.sh`.
- `--self-test` must use a directory from `mktemp -d` with a cleanup trap and pass that directory to
  the scanner; it must not append to, patch, or restore a tracked manifest.
- Beware false positives: the root `Cargo.toml` mentions crate names inside comments. Anchor the
  grep at the start of a line (`^\s*<name>\s*=`) or you will flag your own documentation.
- `tests/e2e` is a workspace member too (`Cargo.toml:3`) — include its manifest in the scan.
- The `supply-chain` job is **ungated** (it runs even on a docs-only diff, per the `changes`
  classifier comment at `ci.yml:8-9`), which is exactly why the guard belongs there rather than in
  `gates`: it costs seconds and never needs a Rust toolchain.
- This PR touches **no** `crates/**` file, so the CI `changes` classifier emits `code: false` and
  the compile-heavy jobs skip — a correct, green run that looks unusually short. Do not "fix" it.
- Do not touch any `.sql` file or the `.sqlx` offline cache (no Docker locally to regenerate it).
- Tests, if you add any, are **sibling** `*_test.rs` files — but this ticket's guard is a shell
  script, not a Rust test, because it inspects manifests rather than code.
- This closes Phase 11. The next ticket crosses into Phase 12 (`unsafe-`), whose first PR adds
  `#![forbid(unsafe_code)]` — a real, free win rather than another declined dependency.

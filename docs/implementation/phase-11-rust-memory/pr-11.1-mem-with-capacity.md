# PR 11.1 — Pre-size the loader's per-cycle plan and bootstrap vectors

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** loader

> **Phase:** 11 — Rust memory optimization · **Crates touched:** `loader` · **Est. size:** S ·
> **Depends on:** PR 10.12 · **Unlocks:** PR 11.2

Production holds **15** `with_capacity(` calls and **not one of them is in the `loader` crate**.
`TablePlan::tier1` and `TablePlan::from_registry` each open two `Vec::new()`s and then push one
element per source column (4 sites), and `bootstrap::bootstrap` opens `owned` with `Vec::new()` and
pushes exactly `registry.len()` entries. Phase B rebuilds a `TablePlan` on **every poll** (default
1 s, per owned table) to feed `TransformSql::render`, so those four vectors re-run the doubling
ladder (4 → 8 → 16 → …) once per second per table, for a length that is known before the
first push. After this PR the five sites are pre-sized and the loader's per-cycle plan build does
zero reallocations for any table under the pre-sized bound.

## Why — learning objectives

- **Vec/String amortized growth** — `Vec::new()` starts at capacity 0 and reallocates-and-copies on
  a doubling schedule; `with_capacity(n)` pays one allocation when `n` is known up front.
- **The loader's per-poll `TablePlan` rebuild** — `phase_b::current_transform` calls
  `TablePlan::from_registry` on every cycle and hands the result to `TransformSql::from_plan`, so a
  "build once" cost is really a per-second cost.

**In scope**

- `TablePlan::tier1`: `raw_cols` / `mirror_cols` → `Vec::with_capacity(rel.columns.len())` (exact —
  the Tier-1 shape is one raw + one mirror column per source column).
- `TablePlan::from_registry`: the same two vectors → `Vec::with_capacity(rel.columns.len())`, with a
  one-line comment saying this is a **lower bound**, not an exact size (a Tier-2 `range` column fans
  out to 5 raw columns, so a range-heavy table still grows past the reservation — that is fine and
  is exactly what `with_capacity` is for).
- `bootstrap::bootstrap`: `owned` → `Vec::with_capacity(registry.len())`, reading the length
  **before** the `for row in registry` loop consumes it.
- No behavioural change anywhere: the same columns in the same order, the same SQL out of
  `TransformSql`.

**Explicitly deferred** (do *not* build these here)

- Collections whose final length is genuinely unknown stay `Vec::new()` /
  `collect()`: `parse_stream` (`crates/pg-sink/src/pgoutput/mod.rs:468`), `split_members`
  (`crates/pg-to-arrow/src/range.rs:210`), `extract_points`
  (`crates/pg-to-arrow/src/geometric.rs:125`).
- `Vec::new()` sites that are returned empty on an early-exit path are **not** churned —
  `Vec::new()` performs no allocation until the first push, so pre-sizing them would make the empty
  path *slower*.
- The `by_name` `HashMap` at `plan.rs:88` is built with `.collect()` from a sized iterator, which
  already reserves from `size_hint`. Leave it alone.
- Reusing the plan across polls (caching `TablePlan` on `TableCtx`) is a different rule
  (`mem-reuse-collections`, PR 11.6) and is out of scope.

## Hints & gotchas

- `for row in registry` **moves** `registry`; `registry.len()` must be bound before the loop or the
  borrow checker rejects it. Do not "fix" that by cloning the registry rows.
- `Vec::with_capacity(0)` is legal and allocates nothing, so an empty relation is still free.
- `with_capacity` is a *reservation*, not a cap — the registry path may exceed it (Tier-2 `range`).
  Say so in the comment; a reviewer who thinks it is exact will file a bug later.
- Do **not** touch any `.sql` file or the `.sqlx` offline cache — there is no Docker on this machine
  to regenerate the cache, and this PR needs neither.
- `unwrap()` / `expect()` are `deny` in production via `[workspace.lints.clippy]`; nothing here
  needs them.
- `clippy::all` and `warnings` are already `deny`. Clippy will flag
  `clippy::reserve_after_initialization` if you write `let mut v = Vec::new(); v.reserve(n);` —
  use `Vec::with_capacity(n)` directly.
- Loader unit tests are Go-style siblings (`foo.rs` → `foo_test.rs`); `plan.rs` has none, and its
  behaviour is covered by the integration tests under `crates/loader/tests/`. Do not add an inline
  `#[cfg(test)] mod tests {}`.

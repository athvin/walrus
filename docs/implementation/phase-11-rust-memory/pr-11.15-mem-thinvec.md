# PR 11.15 — Measure ThinVec against the already-niche-optimised Option<Vec>

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 11 — Rust memory optimization · **Crates touched:** `pg-sink` *(one const assertion)* ·
> **Est. size:** S · **Depends on:** PR 11.14 · **Unlocks:** PR 11.16

The rule's headline case does not hold in walrus. Its premise is that `Option<Vec<T>>` costs a
word more than `Vec<T>`; measured with rustc on a 64-bit target, `Option<Vec<TupleValue>>` — the
`old` field of `Message::Update` at `crates/pg-sink/src/pgoutput/mod.rs:83`, the only optional
collection in the decoder — is **24 bytes, exactly the same as `Vec<TupleValue>`**, because
`Vec`'s non-null pointer already supplies the niche `Option` needs. So `ThinVec` would buy 16 B on
that one field of an **88-byte** enum whose largest variant is `Relation`'s inline `PgRelation`
(80 B, `pg_shape.rs:73`) — an enum is as large as its largest variant, so the 16 B would not
shrink `Message` by a single byte, and PR 11.10 is already removing the remaining headroom from
the other direction. And unlike `smallvec`/`arrayvec`/`tinyvec`/`bumpalo`, **`thin_vec` is not in
`Cargo.lock` at all** (0 hits), so it is a genuinely new supply-chain surface that would have to
clear all four `cargo deny` families. After this merges, the number is written down, a
compile-time assertion keeps the niche from silently disappearing, and the dependency count stays
0.

## Why — learning objectives

- **Niche optimisation** — a type with an invalid bit pattern (here `Vec`'s non-null data pointer)
  lets `Option<T>` reuse that pattern as `None`, so `size_of::<Option<Vec<T>>>() ==
  size_of::<Vec<T>>()`. Verify layout claims with `size_of`; never quote a doc's prose at them.
- **Supply-chain cost is not uniform** — a crate already in `Cargo.lock` transitively is a cheap
  promotion (the licence is already vetted, the code already compiles into the tree); a brand-new
  crate adds an advisories/licence/bans/sources surface that must be re-argued.

## Hints & gotchas

- `size_of` is in the **prelude** as of Rust 1.80 and walrus's MSRV is 1.95 (`Cargo.toml:8`), so no
  `use std::mem::size_of;` is needed — and adding one would trip `clippy::all` + `deny(warnings)` as
  an unused import if the module already sees it.
- `const _: () = assert!(…)` is evaluated at compile time; a failure is a **build** error with your
  message, which is the point. Keep the `#[cfg(target_pointer_width = "64")]` gate — the numbers are
  64-bit-specific and CI must not break on a 32-bit target.
- Do **not** assert an absolute `== 24`. Assert the *relationship*
  (`Option<Vec<T>>` == `Vec<T>`) — that is the claim the ADR rests on, and it survives a future
  `TupleValue` change that PR 11.2's absolute assertions would (correctly) catch separately.
- The enum-size rule: `size_of::<Message>()` tracks its **largest** variant plus discriminant and
  padding. Shrinking a non-largest variant buys nothing. Write that sentence in the ADR; it is the
  finding.
- `Cargo.lock` is committed. `grep 'thin_vec' Cargo.lock` is the honest probe — a manifest-only grep
  would miss a transitive arrival.
- Any new dependency must clear **all four** `cargo deny` families, and the 8-id SPDX allow-list
  (`deny.toml:38-47`) is deliberately minimal — "each id here is required by at least one crate that
  no other allowed license covers". Widening it for a 0-byte win is exactly the trade to refuse.
- `unwrap`/`expect` are denied in production; `clippy::all` and `warnings` are `deny`. This PR adds
  no runtime code at all, so anything that fails CI here is a stray import or a fmt slip.
- Do not touch any `.sql` file or the `.sqlx` offline cache (no Docker locally to regenerate it).
- Tests, if you add any beyond the const assertion, go in a **sibling** `*_test.rs` — never an
  inline `mod tests {}`. PR 11.14 creates `pgoutput/mod_test.rs`; reuse it rather than adding a
  second one.

# PR 11.14 — Record why ArrayVec has no hard-capacity home in walrus

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 11 — Rust memory optimization · **Crates touched:** `pg-sink` *(test only)* ·
> **Est. size:** S · **Depends on:** PR 11.13 · **Unlocks:** PR 11.15

`ArrayVec<T, N>` needs a **compile-time** hard cap, and walrus does not have one to give it. The
pgoutput TupleData column count arrives as an `Int16` on the wire — `let ncols = reader.int16()?;`
at `crates/pg-sink/src/pgoutput/mod.rs:211`, where `Reader::int16` returns a `u16`
(`reader.rs:53`) — so the *format* permits up to 65 535 columns and the only real ceiling is
Postgres' 1 600-column table limit, a server policy rather than a protocol constant. Encoding
either number as an `N` fails: `[TupleValue; 1600]` is **64 000 bytes of stack per tuple** (PR
11.2 pins `TupleValue` at 40 B), and any smaller `N` would make the decoder reject a *legal*
table. Every other candidate collection has the same problem — `Vec<TupleValue>` per row,
`Vec<PgColumn>` per relation (`pg_shape.rs:78`), `Vec<SealedBatch>` per commit — all sized by user
schema, never by a constant. walrus already takes the correct std-only answer one line below the
count: `Vec::with_capacity(ncols as usize)` (`mod.rs:212`), one right-sized allocation from the
wire. After this merges, that reasoning is an ADR with the arithmetic in it, and two sibling tests
make the "growable by design" claim executable instead of assumed.

## Why — learning objectives

- **Fixed-capacity vs growable containers** — `ArrayVec` never heap-allocates and never spills; the
  cost is that exceeding `N` is an error or a panic, so `N` must be a bound the domain *guarantees*.
- **Where a compile-time bound legitimately comes from** — a protocol constant or a physical limit,
  not "usually small". pgoutput's Relation/TupleData framing gives a 16-bit count and Postgres gives
  a 1 600-column ceiling; neither is a constant the decoder may assume.

- Assert the pre-sizing: the returned `Vec`'s capacity is at least the wire count, so the "one
  right-sized allocation" claim in the ADR is checked by a test, not asserted in prose.

**Explicitly deferred** (do *not* build these here)

- `ArrayString` for the fixed-width LSN rendering. `Lsn`'s `Display`
  (`crates/common/src/lsn.rs:89-94`) is `write!(f, "{:016X}", self.0)` — **exactly 16 bytes,
  always** — which is the one place in walrus a genuine hard cap exists. Note it in the ADR as the
  single live candidate and revisit it only if PR 11.16's measurement makes small-string layout
  matter.
- Adding an `arrayvec` dependency in any form, including dev-only. The dep count must stay 0.
- Introducing a `MAX_COLUMNS` runtime rejection in the decoder. The decoder's contract is "fail loud
  at the misaligned byte", not "enforce a server-side policy" — a 1 600-column check would be new
  behaviour, and it is not what this ticket is for.

**The conflict, and how to resolve it** — CONTEXT §4 groups `mem-arrayvec` with `mem-smallvec` as
*bench-gated*. That framing is wrong here and the ADR must say so: the decline is **structural, not
performance-based**. There is no legal hard cap to encode, so the benchmark is not even reachable —
you cannot measure a type you cannot legally instantiate. Write that sentence explicitly. "Not
relevant" is not an acceptable ADR; the `Int16` wire type, the 1 600-column ceiling and the 64 KB
stack arithmetic are the evidence that makes it a finding.

## Hints & gotchas

- `Reader::int16` returns **`u16`, not `i16`** (`reader.rs:53`) — the count is unsigned on the wire.
  Don't write the ADR around a signed 32 767 ceiling; it is 65 535.
- `'n'` (NULL) and `'u'` (unchanged TOAST) are **one byte total** — no length, no value
  (`mod.rs:215-216`). That is what makes a 1 600-column frame only 1 602 bytes to build in a test.
- Tests are **sibling files**, never inline `mod tests {}` — 47 modules follow this and PRs 7.1–7.3
  moved every one of them. Wire `mod_test.rs` exactly like `typmod.rs:22-24` does.
- `unwrap()` in the new sibling test is fine: `clippy.toml` sets `allow-unwrap-in-tests = true` and
  the module is `#[cfg(test)]`. In *production* code `unwrap_used`/`expect_used` are `deny`.
- `clippy::all` + `warnings` are `deny` at the workspace root, so an unused `use` in the test file
  fails CI. `usize::from(u16)` is infallible and lint-clean — prefer it to `as usize` (Phase 17
  audits the 104 `as` casts and you do not want to add one).
- **Do not add a runtime column-count check to the decoder.** A 1 600 rejection would be new
  behaviour and would break the >1 600 guard test that is the whole point of the ADR.
- `TupleValue` is not `Copy` and is 40 B — the `[TupleValue; 1600]` figure is the stack cost *per
  tuple in flight*, and the decoder holds one per row. Put the number in the ADR; it is the most
  persuasive line in it.
- Do not touch any `.sql` file or the `.sqlx` offline cache (no Docker locally to regenerate it).
  Nothing in this PR goes near SQL.
- The golden vectors (`crates/pg-sink/tests/pgoutput_vectors.rs`) must keep passing untouched — this
  PR adds tests, it does not change decoding.

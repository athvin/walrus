# PR 14.11 — Race the control-DB and object-store bootstrap checks with try_join

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 14 — Rust async/await · **Crates touched:** `pg-sink` · **Est. size:** M ·
> **Depends on:** PR 14.10 · **Unlocks:** PR 14.12

`bootstrap::run_shared` runs three **independent** dependency checks strictly sequentially, each
retrying against the *same* `startup_deadline`: control Postgres + migrations
(`crates/pg-sink/src/bootstrap.rs:49-63`), the object-store put/get/delete canary (`:69-77`), and the
source-DB connect (`:83-88`). A slow control PG therefore eats budget the canary still needs, and the
pod answers `/startup` 503 for the **sum** of the checks instead of the **max**. `try_join!` and
`join!` appear **0** times in the entire repo. This PR joins the first two — the only pair with no
ordering constraint between them — so a rollout's bootstrap latency stops being additive, and it
does it fail-fast: the first terminal error wins and the other future is dropped.

## Why — learning objectives

- **`try_join!` = concurrency + fail-fast** — unlike `join!`, it returns `Err` the moment any branch
  fails instead of waiting for the rest; unlike sequential `?`, the branches make progress at the
  same time. Futures are lazy, so nothing runs until the macro polls them.
- **walrus's startup contract** — `/startup` answers 503 for the *whole* bootstrap, so bootstrap
  latency is a Kubernetes rollout property, not a log curiosity. Turning a sum into a max is a
  deployment-visible win.

**In scope**

- Extract the two independent blocks into private async fns in the same module:
  `bootstrap_control(cfg, deadline) -> Result<PgPool, Error>` (connect + `run_migrations` + its
  `tracing::info!`) and `bootstrap_object_store(cfg, deadline) -> Result<Arc<dyn ObjectStore>, Error>`
  (build + canary + its `tracing::info!`).
- Run exactly those two under one `tokio::try_join!` in `run_shared`, keeping every error
  classification (`Error::ControlDb` / `Error::ObjectStore`) and the retry/backoff behaviour
  untouched.
- Leave the source-DB connect and the five `SourcePreflight::assert_*` calls exactly where and in
  the order they are, *after* the join.
- Add two `bootstrap_test.rs` cases under `#[tokio::test(start_paused = true)]`: one proving the
  joined shape costs the max rather than the sum (two ~200 ms fake dependency futures, elapsed
  < 350 ms), one proving fail-fast (an immediate terminal error alongside a 10 s sleep returns
  promptly).
- Record in the PR body: `/startup` 503 duration goes from *sum* to *max* of the two checks, and the
  two `tracing::info!` lines ("control database reachable…", "object-store canary … passed") can now
  appear in either order.

**Explicitly deferred** (do *not* build these here)

- Does **not** parallelise the five `SourcePreflight::assert_*` catalog queries: they share one
  pipelined `tokio_postgres` client and carry the ordering constraint below.
- Does **not** parallelise the per-table initial backfill (`main.rs:314-325`, `backfill.rs`) — the
  CTID-range parallel backfill is a documented deferred goal.
- Does **not** change `startup_deadline`, `attempt_budget`, the backoff schedule, or `BootstrapCtx`.

**Conflict — do not apply the rule blindly.** `assert_reload_signal` must stay **before**
`assert_publication_covers`; that ordering is a deliberate error-attribution rule (comment at
`bootstrap.rs:85-87`, PR 6.2) — a missing signal table must surface as the migration-naming error,
not as a failed `ALTER PUBLICATION`. Only the control-DB and canary blocks are joined. Two further
consequences to state, not hide: the two `info!` lines become order-nondeterministic, and when
*both* dependencies are down the surfaced error (and therefore the process exit code, `ControlDb`
11 vs `ObjectStore` 12) is whichever failed first rather than always `ControlDb`.

## Skeleton

```rust
// crates/pg-sink/src/bootstrap.rs
pub async fn run_shared(cfg: &SinkConfig, deadline: Instant) -> Result<BootstrapCtx, Error> {
    // Steps 2 and 3 are INDEPENDENT: neither reads the other's output. Racing them means `/startup`
    // is 503 for max(control, canary) instead of their sum, and a terminal error in either one
    // short-circuits immediately (try_join! drops the other branch at its next await point).
    let (control_pool, object_store) = tokio::try_join!(
        bootstrap_control(cfg, deadline),
        bootstrap_object_store(cfg, deadline),
    )?;

    // Step 6 stays SEQUENTIAL and in this exact order (PR 6.2): a missing signal table must yield the
    // migration-naming error, not a failed ALTER PUBLICATION under manage_publication.
    let source_client = retry_transient(deadline, "source database", || {
        let url = cfg.source_db_url.clone();
        async move { preflight::connect_source(&url).await }
    })
    .await?;
    let pf = SourcePreflight::new(&source_client, cfg);
    let server = pf.assert_server_prereqs().await?;
    pf.assert_reload_signal().await?;
    pf.assert_publication_covers().await?;
    todo!("remaining assertions + the tracing::info! summary are unchanged");
}

/// Step 2: control Postgres reachable (transient) + migrations current (idempotent).
async fn bootstrap_control(cfg: &SinkConfig, deadline: Instant) -> Result<PgPool, Error> {
    let pool = retry_transient(deadline, "control database", || async {
        todo!("body moved verbatim from run_shared: attempt_budget + timeout + control::connect");
    })
    .await?;
    control::run_migrations(&pool)
        .await
        .map_err(|e| Error::ControlDb(format!("ensure control migrations current: {e}")))?;
    tracing::info!("control database reachable and migrations current");
    Ok(pool)
}

/// Step 3: build the store (config-derived, not retried) then put/get/delete a tiny key.
async fn bootstrap_object_store(cfg: &SinkConfig, deadline: Instant) -> Result<Arc<dyn ObjectStore>, Error> {
    let store = build_object_store(&cfg.object_store)
        .map_err(|e| Error::ObjectStore(format!("build object store: {e}")))?;
    // PR 14.4 moved `retry_transient` to an `AsyncFnMut` bound, so the closure may borrow `store` and
    // `cfg.instance` directly — no `let store = store.clone();` dance.
    retry_transient(deadline, "object store", async || {
        object_store_canary(store.as_ref(), &cfg.instance)
            .await
            .map_err(|e| Error::ObjectStore(e.to_string()))
    })
    .await?;
    tracing::info!("object-store canary (put/get/delete) passed");
    Ok(store)
}
```

```rust
// crates/pg-sink/src/bootstrap_test.rs — deterministic: paused time makes "elapsed" virtual.
#[tokio::test(start_paused = true)]
async fn joined_dependency_checks_cost_the_max_not_the_sum() {
    async fn fake_dep(ms: u64) -> Result<u8, Error> {
        tokio::time::sleep(Duration::from_millis(ms)).await;
        Ok(7)
    }
    let start = Instant::now();
    let (a, b) = tokio::try_join!(fake_dep(200), fake_dep(200)).unwrap();
    let elapsed = start.elapsed();
    assert_eq!((a, b), (7, 7));
    assert!(
        elapsed < Duration::from_millis(350),
        "sequential awaits would take ~400ms; got {elapsed:?}"
    );
}

#[tokio::test(start_paused = true)]
async fn try_join_fails_fast_on_a_terminal_error() {
    let start = Instant::now();
    let out: Result<(u8, u8), Error> = tokio::try_join!(
        async { Err(Error::Config("bad bucket".into())) },
        async {
            tokio::time::sleep(Duration::from_secs(10)).await;
            Ok(1)
        },
    );
    assert!(matches!(out, Err(Error::Config(_))));
    assert!(start.elapsed() < Duration::from_secs(1), "the slow branch must be dropped, not awaited");
}
```

## Hints & gotchas

- `tokio::try_join!` needs every branch to have the **same** error type. Both helpers return
  `Result<_, common::Error>`, so no `map_err` bridging is required — keep it that way rather than
  introducing `anyhow` here (`bootstrap` is library-side; `anyhow` belongs in `main`).
- Prefer named `async fn` helpers over inline `async { … }` blocks. A bare async block containing
  `?` frequently cannot infer its error type, and the fix (`Ok::<_, Error>(x)` at the end) is uglier
  than the extraction — which is also what makes the module unit-testable.
- Use `#[tokio::test(start_paused = true)]` for the timing assertions. Paused time auto-advances when
  the runtime is idle, so `Instant::elapsed()` is *virtual* and deterministic — a wall-clock
  `< 350 ms` assertion on shared CI runners is a flake generator. `tokio`'s `test-util` feature is
  already a pg-sink dev-dependency.
- Both branches now retry against the *same* `deadline` concurrently. That is the intended
  semantics (the deadline is a wall-clock budget, not a per-check allowance) — do not divide it.
- A dropped `try_join!` branch stops at its next `.await`, so an in-flight canary `PUT` may still
  land in the bucket after a control-DB failure. The canary key is `_walrus/canary/{instance}` and
  the operation is idempotent, so this is harmless — but do not add "cleanup" logic for it.
- Do **not** touch any `.sql` file or the `.sqlx` offline cache — there is no Docker on this machine
  to regenerate it. `control::run_migrations` is called, not modified.
- `unwrap()` / `expect()` are `deny` in production but allowed in `#[cfg(test)]` via `clippy.toml`,
  which is why the new test cases may `unwrap()`.
- Unit tests are Go-style siblings: extend `crates/pg-sink/src/bootstrap_test.rs`, never add an
  inline `mod tests {}` to `bootstrap.rs`.

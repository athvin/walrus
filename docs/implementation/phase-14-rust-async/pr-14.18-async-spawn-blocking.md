# PR 14.18 — Document why DuckDB work cannot use spawn_blocking and assert the !Send boundary

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test · **Test packages:** loader

> **Phase:** 14 — Rust async/await · **Crates touched:** `loader` ·
> **Est. size:** M · **Depends on:** PR 14.17 · **Unlocks:** PR 15.1

Calls to `spawn_blocking` and `block_in_place` appear **0 times** in production Rust, and the loader really does run
long blocking work inside `async fn`s: `full_rebuild`'s `CREATE OR REPLACE TABLE … AS SELECT`
(`compaction.rs:27-59`, called synchronously from the async `full_rebuild_abortable` at
`compaction.rs:77`), `prune_raw`'s `DELETE` + `CHECKPOINT` (`compaction.rs:87`), the drain
`CHECKPOINT` (`apply_loop.rs`) and `TableDb::open` (`bootstrap.rs`). The steady-state calls cannot move
to the blocking pool as written: they **borrow** a `duckdb::Connection`, while `spawn_blocking`
demands `F: Send + 'static`; `Connection: Send + !Sync` makes its shared borrow `!Send`, as well as
non-`'static`. `TableDb::open` is the owned exception, but offloading it would not shorten the
sequential bootstrap critical path. Although `block_in_place` is normally legal on a multi-thread
runtime's outer `block_on` driver, `LocalSet::run_until` explicitly disables it while polling the
apply workers, so using it at the DuckDB sites would panic. This PR adds
neither call. It records the analysis, adds positive `Send` assertions plus compile-fail shared-borrow
guards, strengthens the existing accurate comments, and files the open finding: all N apply loops
share a single thread, so a multi-second rebuild for one table stalls every other one.

## Why — learning objectives

- **`spawn_blocking`'s `Send + 'static` bound** — and the distinction that actually bites here:
  `T: Send` (a value may move between threads) versus `&T: Send`, which requires `T: Sync` (a value
  may be *shared* across threads). Borrowing APIs collide with the second, not the first.
- **walrus loader storage truth** — DuckDB reclaims space only by rewriting the table, which is why
  compaction is long, blocking, and cannot simply be made "async".

**In scope**

- A new ADR, `docs/implementation/notes/rust-skills/async-spawn-blocking.md`, recording three things:
  1. **The bound analysis, precisely.** `spawn_blocking` requires `FnOnce() -> R + Send + 'static`.
     `duckdb::Connection` **is** `Send` but is **not** `Sync` (it owns a `RefCell<InnerConnection>`
     and the crate only writes `unsafe impl Send`). The steady-state compaction, prune and drain sites take
     `&duckdb::Connection`, and `&T: Send` holds only when `T: Sync` — so the closure is `!Send`,
     and a borrow is not `'static` either. Record the *theoretically available* alternative and why
     it is not taken here: `TableDb` is `Send`, so a redesigned worker could move it into the
     blocking pool and return it. The worker would need to move the database out of `TableCtx` and
     make every exit path recover it. Its `InterruptHandle` can be created before the move, so drain
     cancellation is preservable rather than inherently broken; that ownership redesign belongs to
     the concurrency follow-on.
  2. **Why `block_in_place` does not help.** Tokio 1.52 normally permits it on this multi-thread
     runtime's outer `runtime.block_on` driver. But `LocalSet::RunUntil::poll` installs
     `disallow_block_in_place()` before it polls both the `run_until` future and local tasks. The
     actual apply-worker DuckDB sites therefore take Tokio's LocalSet error path and panic. Even if
     the restriction did not exist, a blocking wrapper could not move or advance sibling LocalSet
     tasks, which are pinned to the driving thread.
  3. **The open finding.** All N apply loops share ONE thread (`main.rs:106` `LocalSet::new()`,
     `:132` `spawn_local`), so `compaction.rs:77`'s multi-second rewrite stalls **every other
     table's** apply loop. File it as the next phase's work — one `current_thread` runtime per
     `.duckdb` file, each on its own OS thread — and state plainly that this ADR does **not** bless
     the stall.
- Strengthen the already-accurate comments in `crates/loader/src/duck.rs` and
  `crates/loader/src/main.rs`: retain the `Send + !Sync` distinction, link the ADR, and name the
  shared-thread open finding.
- Correct `crates/loader/src/compaction.rs:10-11`'s "runs on the table's **own worker thread**" to
  say what is true today (this worker's *task*, on the shared `LocalSet` thread) with a pointer to
  the ADR's open finding.
- Add type-level guards without a dependency: `duck_test.rs` instantiates a positive `T: Send`
  bound for `Connection` and `TableDb`, plus a spawn-blocking-shaped bound with a legal closure;
  `duck.rs` adds `compile_fail` doctests proving `&Connection` and `&TableDb` are not `Send`.

**Explicitly deferred** (do *not* build these here)

- **Do not** introduce a thread-per-file runtime. That is the ADR's filed follow-on, and it touches
  bootstrap, shutdown ordering and the lease renewer — far beyond this ticket.
- **Do not** change the compaction cadence, the retention floor, or `full_rebuild_abortable`'s
  interrupt-handle mechanism.
- **Do not** `spawn_blocking` the Prometheus `render()` in the `/metrics` handler. It is marginal;
  note it in the ADR as measured-and-declined, do not change it.
- Do not add `static_assertions`, `trybuild`, or any other dependency — built-in doctests and plain
  generic bounds cover the evidence, and every new dep must clear `cargo deny`.

**Conflict — this is a documented rejection, not conformance.** The corpus rule says "move CPU work
to `spawn_blocking`". walrus's borrowed steady-state DuckDB API structurally cannot as written, for
the reason above. The ADR is the
rejection record — and it must NOT be read as blessing the shared-thread stall, which is a real,
open finding with an owner in the next phase. Write both halves, or the note is misleading.

## Hints & gotchas

- **Verify the `Send`/`Sync` facts in *your* pinned `duckdb` before writing a word of the ADR.**
  `Cargo.toml` pins `duckdb = "=1.10504.0"`; open its `src/lib.rs` and find the `Connection` struct
  and the `unsafe impl Send for Connection {}` beneath it. If a future bump adds
  `unsafe impl Sync`, the whole analysis changes and the ADR's reversal clause fires.
- **`T: Send` and `&T: Send` are different questions.** `&T: Send ⟺ T: Sync`. The positive unit
  test and negative compile-fail doctests intentionally prove different halves of that distinction.
- Stable Rust cannot reflect a generic negative auto-trait bound at runtime. Keep the positive
  `T: Send` unit-test instantiations and the negative `compile_fail` doctests together; do not replace
  them with an autoref pseudo-specialisation whose generic body always selects its fallback.
- Do not reach for `static_assertions::assert_not_impl_all!` or `trybuild`. Both are new
  dependencies and would need to clear `cargo deny`'s advisories/licence/bans gates for a 15-line
  test helper.
- `duck_test.rs` is already wired from `duck.rs`; append to it rather than creating a new module.
  Tests are Go-style siblings — never an inline `mod tests {}`.
- Keep the two halves of the ADR clearly separated. A reader who skims section 1 and stops must not
  come away thinking the shared-thread stall was reviewed and accepted; put the open finding under
  its own heading with the word "open" in it.
- `compaction.rs`'s `interrupt_handle()` watcher is the *existing* answer to "the rewrite blocks":
  a `Send + Sync` handle on the runtime pool interrupts a query running on the LocalSet driver
  thread. Mention it in the ADR — it is the pattern the follow-on will preserve, not throw away.
- `clippy::all` + `warnings` are `deny`; `unwrap`/`expect` are `deny` in production and re-allowed
  under `#[cfg(test)]` by `clippy.toml`. Do not touch `.sql` or the `.sqlx` offline cache — there is
  no Docker on this machine to regenerate it.

# PR 14.18 — Document why DuckDB work cannot use spawn_blocking and assert the !Send boundary

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test · **Test packages:** loader

> **Phase:** 14 — Rust async/await · **Crates touched:** `loader` ·
> **Est. size:** M · **Depends on:** PR 14.17 · **Unlocks:** PR 15.1

`spawn_blocking` and `block_in_place` appear **0 times** in the repo, and the loader really does run
long blocking work inside `async fn`s: `full_rebuild`'s `CREATE OR REPLACE TABLE … AS SELECT`
(`compaction.rs:27-59`, called synchronously from the async `full_rebuild_abortable` at
`compaction.rs:77`), `prune_raw`'s `DELETE` + `CHECKPOINT` (`compaction.rs:87`), the drain
`CHECKPOINT` (`apply_loop.rs:85`) and `TableDb::open` (`bootstrap.rs:81`). None of it can move to the
blocking pool as written: every one of those calls **borrows** a `duckdb::Connection`, and
`spawn_blocking` demands `F: Send + 'static` — a borrow is neither. `block_in_place` cannot rescue it
either. This PR does not add either call. It writes the analysis down as an ADR, pins the type-level
facts with a real compile-and-run guard in `duck_test.rs`, **corrects two comments in the tree that
state the reason wrongly**, and files the one genuinely open finding this analysis uncovered: all N
apply loops share a single thread, so a multi-second rebuild for one table stalls every other one.

## Why — learning objectives

- **`spawn_blocking`'s `Send + 'static` bound** — and the distinction that actually bites here:
  `T: Send` (a value may move between threads) versus `&T: Send`, which requires `T: Sync` (a value
  may be *shared* across threads). Borrowing APIs collide with the second, not the first.
- **walrus loader storage truth** — DuckDB reclaims space only by rewriting the table, which is why
  compaction is long, blocking, and cannot simply be made "async".

**In scope**

- A new ADR, `docs/implementation/notes/rust-skills/async-spawn-blocking.md`, recording three things:
  1. **The bound analysis, precisely.** `spawn_blocking` requires `FnOnce() -> R + Send + 'static`.
     `duckdb::Connection` **is** `Send` but is **not** `Sync` (it owns a `RefCell<InnerConnection>`
     and the crate only writes `unsafe impl Send`). Every walrus call site takes
     `&duckdb::Connection`, and `&T: Send` holds only when `T: Sync` — so the closure is `!Send`,
     and a borrow is not `'static` either. Record the *theoretically available* alternative and why
     it is not taken: `TableDb` is `Send`, so it could be moved into the blocking pool and returned,
     but that surrenders the connection for the whole rewrite and breaks the
     `interrupt_handle()`-based drain abort at `compaction.rs:71-78`.
  2. **Why `block_in_place` does not help.** It requires a multi-thread-runtime **worker** thread;
     the `LocalSet` is driven by `runtime.block_on` on the main thread (`main.rs:38` → `:143`), so it
     is not applicable there — and even where it is, it hands off *other runtime tasks*, never the
     `LocalSet`'s own, which are pinned to the thread that drives it.
  3. **The open finding.** All N apply loops share ONE thread (`main.rs:106` `LocalSet::new()`,
     `:132` `spawn_local`), so `compaction.rs:77`'s multi-second rewrite stalls **every other
     table's** apply loop. File it as the next phase's work — one `current_thread` runtime per
     `.duckdb` file, each on its own OS thread — and state plainly that this ADR does **not** bless
     the stall.
- Correct the two comments that state the reason wrongly: `crates/loader/src/duck.rs:36-39` and
  `crates/loader/src/main.rs:104-105` both say `Connection` is `!Send`. Replace with the accurate
  reason (`!Sync`, so `&TableDb` cannot cross a thread boundary), each linking the ADR.
- Correct `crates/loader/src/compaction.rs:10-11`'s "runs on the table's **own worker thread**" to
  say what is true today (this worker's *task*, on the shared `LocalSet` thread) with a pointer to
  the ADR's open finding.
- Add the type-level guard to `crates/loader/src/duck_test.rs`: a trybuild-free `is_send::<T>()`
  probe plus a `#[test]` asserting the four facts that make `spawn_blocking` impossible, and a
  `spawn_blocking`-shaped bound function that is deliberately never instantiated with a `TableDb`
  borrow.

**Explicitly deferred** (do *not* build these here)

- **Do not** introduce a thread-per-file runtime. That is the ADR's filed follow-on, and it touches
  bootstrap, shutdown ordering and the lease renewer — far beyond this ticket.
- **Do not** change the compaction cadence, the retention floor, or `full_rebuild_abortable`'s
  interrupt-handle mechanism.
- **Do not** `spawn_blocking` the Prometheus `render()` in the `/metrics` handler. It is marginal;

- Do not add `static_assertions`, `trybuild`, or any other dependency — the probe is 15 lines of

**Conflict — this is a documented rejection, not conformance.** The corpus rule says "move CPU work

rejection record — and it must NOT be read as blessing the shared-thread stall, which is a real,
open finding with an owner in the next phase. Write both halves, or the note is misleading.

## Skeleton

```rust
// crates/loader/src/duck_test.rs — append. No dependency, no trybuild, no negative impls.

use std::marker::PhantomData;

/// A `Send` probe via autoref specialisation. Method resolution tries the `&Probe<T>` impl first;
/// that impl only applies when `T: Send`, so a non-`Send` `T` falls through to the `Probe<T>` impl.
/// The two traits must both be in scope and must share the method name — that is what makes the
/// autoref order the tie-breaker.
struct Probe<T>(PhantomData<T>);

trait ProbeSend {
    fn probe(&self) -> bool;
}
impl<T: Send> ProbeSend for &Probe<T> {
    fn probe(&self) -> bool {
        true
    }
}

trait ProbeFallback {
    fn probe(&self) -> bool;
}
impl<T> ProbeFallback for Probe<T> {
    fn probe(&self) -> bool {
        false
    }
}

fn is_send<T>() -> bool {
    (&Probe::<T>(PhantomData)).probe()
}

/// The exact bound `tokio::task::spawn_blocking` imposes. Deliberately dead code: it exists so the
/// bound is written down in the tree, and is NEVER instantiated with anything borrowing a
/// `TableDb` — see docs/implementation/notes/rust-skills/async-spawn-blocking.md.
#[allow(dead_code)]
fn requires_spawn_blocking_bounds<F, R>(_f: F)
where
    F: FnOnce() -> R + Send + 'static,
    R: Send + 'static,
{
}

#[test]
fn the_probe_itself_is_trustworthy() {
    // Controls in BOTH directions — a probe that can only say one thing proves nothing.
    assert!(is_send::<i64>(), "i64 is Send");
    assert!(is_send::<&'static i64>(), "&i64 is Send because i64 is Sync");
    todo!("add the negative control: is_send::<std::cell::Ref<'static, u8>>() (or another known \
           !Send type) must be false");
}

#[test]
fn duckdb_handles_are_send_but_not_sync_so_spawn_blocking_cannot_borrow_them() {
    // 1. Moving a handle between threads is legal…
    assert!(is_send::<duckdb::Connection>(), "duckdb writes `unsafe impl Send for Connection`");
    assert!(is_send::<TableDb>(), "TableDb is Send: both fields are");
    // 2. …but SHARING one is not, because `&T: Send` requires `T: Sync`, and both hold a RefCell.
    todo!("assert !is_send::<&'static duckdb::Connection>() and !is_send::<&'static TableDb>() — \
           THIS is why every `&duckdb::Connection` call site is closed to spawn_blocking, and why \
           all 14 clippy::future_not_send sites are in `loader`");
    // 3. The bound exists in the tree, instantiated only with something legal.
    requires_spawn_blocking_bounds(|| 1_i64);
}
```

## Hints & gotchas

- **Verify the `Send`/`Sync` facts in *your* pinned `duckdb` before writing a word of the ADR.**
  `Cargo.toml` pins `duckdb = "=1.10504.0"`; open its `src/lib.rs` and find the `Connection` struct
  and the `unsafe impl Send for Connection {}` beneath it. If a future bump adds
  `unsafe impl Sync`, the whole analysis changes and the ADR's reversal clause fires.
- **`T: Send` and `&T: Send` are different questions.** `&T: Send ⟺ T: Sync`. Using
  `is_send::<&'static T>()` to probe `Sync`-ness is why one probe suffices for both facts — say so
  in a comment, or the next reader will "simplify" it into a second redundant trait pair.
- The autoref-specialisation probe is fiddly. If it fights the compiler (ambiguity, or the fallback
  winning when it should not), **fall back to the simpler form the ticket also accepts**: an
  `#[allow(dead_code)] fn requires_send<T: Send>(_: T) {}` that is instantiated with known-`Send`
  types and deliberately never with a `TableDb` borrow, plus a comment. A working weak guard beats a
  clever guard that does not compile.
- Both `Probe` traits must be in scope at the call site and must use the **same method name**. Give
  it a distinctive name (`probe`, not `is_send`) so the free `fn is_send` does not shadow anything.
- Do not reach for `static_assertions::assert_not_impl_all!` or `trybuild`. Both are new
  dependencies and would need to clear `cargo deny`'s advisories/licence/bans gates for a 15-line
  test helper.
- `duck_test.rs` is already wired from `duck.rs`; append to it rather than creating a new module.
  Tests are Go-style siblings — never an inline `mod tests {}`.
- Keep the two halves of the ADR clearly separated. A reader who skims section 1 and stops must not
  come away thinking the shared-thread stall was reviewed and accepted; put the open finding under
  its own heading with the word "open" in it.
- `compaction.rs`'s `interrupt_handle()` watcher (`:71-78`) is the *existing* answer to "the rewrite
  blocks": a `Send + Sync` handle on the runtime pool interrupting a query running on another
  thread. Mention it in the ADR — it is the pattern the follow-on will build on, not throw away.
- `clippy::all` + `warnings` are `deny`; `unwrap`/`expect` are `deny` in production and re-allowed
  under `#[cfg(test)]` by `clippy.toml`. Do not touch `.sql` or the `.sqlx` offline cache — there is
  no Docker on this machine to regenerate it.

# PR 14.5 — Make the watermark oneshot waiter unsubscribe on drop

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 14 — Rust async/await · **Crates touched:** `pg-sink` ·
> **Est. size:** S · **Depends on:** PR 14.4 · **Unlocks:** PR 14.6

walrus's echo request/response is otherwise exemplary — subscribe-then-insert, a
`tokio::time::timeout` around the wait, superseded detection at `reload_export.rs:297-306` — but
`WatermarkWaiters`' doc comment claims at `reload_signal.rs:39-42` that "senders never leak", and
that is **false**. `subscribe` inserts the sender at `reload_signal.rs:57`; the only removal is
`resolve` at `reload_signal.rs:80`. `await_echo` subscribes at `reload_export.rs:286` and then `?`s
on the signal INSERT at `reload_export.rs:296`, so a failed INSERT (a dropped source connection, a
statement timeout, a re-signal that never lands) leaves the entry in the `HashMap` for the life of
the process. There is no `unsubscribe`, no RAII guard, and no accessor with which a test could even
observe the leak. After this merges `subscribe` returns a `SubscribeGuard` that removes its own
entry on `Drop` — the one cleanup path an early `?` cannot skip — and the map size is assertable.

## Why — learning objectives

- **oneshot request/response with an RAII registry entry** — `Drop` is the cleanup path that runs on
  the `?` return, the timeout, the panic and the happy path alike; a manual `remove` on the success
  branch is not cleanup, it is a hope.
- **walrus reload H1** — the chunk low watermark `L_i` is the signal transaction's *decoded commit
  LSN*, so the waiter exists only for the round trip between the INSERT and its echo.

**In scope**

- `WatermarkWaiters`: store `(u64 /* generation */, oneshot::Sender<Echo>)` in the map, hand out a
  fresh generation from an `AtomicU64` on every `subscribe`.
- `subscribe(&self, reload_id, chunk_no) -> SubscribeGuard<'_>` — the guard owns the receiver, the
  key and its generation.
- `SubscribeGuard`: `Deref`/`DerefMut` to `oneshot::Receiver<Echo>` (so `rx.try_recv()` keeps
  working), `impl Future` delegating to the receiver (so `timeout(d, rx).await` keeps working), and
  a `Drop` that calls the new private `unsubscribe(key, generation)`.
- `unsubscribe` removes **only if the stored generation matches** — a stale guard dropped after a
  re-subscribe for the same key must not evict the live waiter.
- `pub fn waiter_count(&self) -> usize` — the assertable mirror, in the style of
  `crosscheck_violations`.
- Rewrite the `WatermarkWaiters` doc comment: the "senders never leak" sentence becomes an accurate
  description of the guard, of `resolve`'s removal, and of the generation rule.
- New `reload_signal_test.rs` cases: `subscribe_then_failed_insert_leaves_no_waiter` (the ticket's
  probe), `stale_guard_drop_does_not_evict_the_live_waiter`, and `resolve_then_drop_is_a_no_op`.

**Explicitly deferred** (do *not* build these here)

- **No protocol change.** The 3-attempt re-signal loop, the `DELETE + INSERT` re-signal shape, the
  `echo_timeout` config and the superseded (`Ok(Err(_))`) branch all stay exactly as they are.
- **Do not bound the map.** No LRU, no capacity cap, no eviction sweep — the guard is the fix.
- Do not change `resolve`'s logging, its cross-check, or the `Echo` type.
- Do not make `WatermarkWaiters` methods `async` or swap `parking_lot::Mutex` for a tokio one.

```rust
// crates/pg-sink/src/reload_signal.rs — the registry.

/// Registry of in-flight watermark waits, keyed by `(reload_id, chunk_no)`.
///
/// Shared (`Arc`) between the decode loop (which resolves) and the exporter tasks (which
/// subscribe, PR 6.5). **Entries cannot leak:** [`Self::subscribe`] hands back a
/// [`SubscribeGuard`] whose `Drop` removes the key, so an exporter that returns early — a failed
/// signal INSERT, a timeout, a `?` anywhere between subscribing and awaiting — takes its sender
/// with it. Each entry carries a monotonic generation so a *stale* guard dropped after a
/// re-subscribe for the same key removes nothing.
#[derive(Debug, Default)]
pub struct WatermarkWaiters {
    waiters: Mutex<HashMap<(i64, i64), (u64, oneshot::Sender<Echo>)>>,
```

```rust
// crates/pg-sink/src/reload_signal.rs — the guard.

/// An in-flight subscription. Deref gives the [`oneshot::Receiver`]; awaiting the guard awaits the
/// echo. Dropping it — on the happy path, on a `?`, or on a timeout — unsubscribes.
#[derive(Debug)]
pub struct SubscribeGuard<'a> {
    waiters: &'a WatermarkWaiters,
    key: (i64, i64),
    generation: u64,
    rx: oneshot::Receiver<Echo>,
}

impl std::ops::Deref for SubscribeGuard<'_> {
    type Target = oneshot::Receiver<Echo>;
    fn deref(&self) -> &Self::Target { &self.rx }
}

impl std::ops::DerefMut for SubscribeGuard<'_> {
    fn deref_mut(&mut self) -> &mut Self::Target { &mut self.rx }
}

/// So `tokio::time::timeout(d, guard).await` keeps working by value, exactly as it did with a bare
/// `Receiver`. `oneshot::Receiver` is `Unpin`, so this is a plain delegation.
impl std::future::Future for SubscribeGuard<'_> {
    type Output = Result<Echo, oneshot::error::RecvError>;
    fn poll(
        self: std::pin::Pin<&mut Self>,
        cx: &mut std::task::Context<'_>,
    ) -> std::task::Poll<Self::Output> {
        todo!("std::pin::Pin::new(&mut self.get_mut().rx).poll(cx)");
    }
}

impl Drop for SubscribeGuard<'_> {
    fn drop(&mut self) {
        self.waiters.unsubscribe(self.key, self.generation);
    }
}
```

## Hints & gotchas

- **Why the generation matters.** `await_echo` re-subscribes on every attempt. The old receiver is
  dropped when the loop iteration ends — *before* the next `subscribe` — so today's ordering is
  safe, but an unconditional `remove` in `Drop` would be one refactor away from silently deleting
  the live waiter. The generation check makes the guard correct independently of drop order.
- **Implement `Future`, not just `Deref`.** The five integration tests in `crates/pg-sink/tests/`
  pass the receiver to `tokio::time::timeout` **by value**. Without `impl Future for SubscribeGuard`
  every one of them breaks; with it, none of them change.
- `oneshot::Receiver` panics if polled after it has completed. `timeout` never re-polls a `Ready`
  inner future, so the delegation is safe — but do not add your own re-poll loop.
- **Borrowck in `await_echo`:** the guard borrows `self.waiters` (an `Arc` field) immutably while
  `self.client.batch_execute(...)` borrows `self.client` mutably. Those are disjoint fields of
  `*self`, so it compiles. If a caller ever hits a genuine conflict, clone the `Arc` into a local —
  do **not** change `subscribe`'s signature to `self: &Arc<Self>`, which would force every unit test
  to wrap `WatermarkWaiters::default()` in an `Arc`.
- `unsubscribe` must bind the lock guard to a `let` rather than locking inside a `match`/`if let`
  scrutinee — PR 14.3 made `clippy::significant_drop_in_scrutinee` a workspace `deny`.
- Use `Ordering::Relaxed` for the generation counter: it only needs uniqueness, and the `Mutex`
  already provides the ordering that matters.
- `#[derive(Debug)]` on `SubscribeGuard` needs `WatermarkWaiters: Debug` (it already is) and
  `oneshot::Receiver<Echo>: Debug` (it is).
- Tests are Go-style siblings; `reload_signal_test.rs` is already wired at
  `reload_signal.rs:235-237`.
  `unwrap`/`expect` are re-allowed under `#[cfg(test)]` by `clippy.toml`, `deny` in production.
- `clippy::all` + `warnings` are already `deny`. A `Drop` impl plus `Deref` will attract
  `clippy::` scrutiny in later phases; keep the guard's public surface minimal.
- Do not touch any `.sql` file or the `.sqlx` offline cache — there is no Docker on this machine to
  regenerate it, and the reload signal table's DDL is unchanged.

# PR 14.3 — Tighten the lock scope in the echo resolver and deny locks held across await

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 14 — Rust async/await · **Crates touched:** `pg-sink` ·
> **Est. size:** S · **Depends on:** PR 14.2 · **Unlocks:** PR 14.4

No walrus production lock is held across an `.await` today: all 7 `.lock()` sites are `parking_lot`
guards inside sync fns or immediately-dropped temporaries (`loader/src/health.rs:73,78`,
`loader/src/phase_a.rs:56,248,270`, `pg-sink/src/reload_signal.rs:57,80`). But `reload_signal.rs:80`
takes its guard in a **`match` scrutinee** and therefore holds it for the whole match arm —
including two `tracing` events — which is the tree's single `clippy::significant_drop_in_scrutinee`
site, and it sits on the decode loop's hot path. Meanwhile `[workspace.lints]` names none of
`await_holding_lock`, `await_holding_refcell_ref`, `await_holding_invalid_type`,
`significant_drop_in_scrutinee` or `significant_drop_tightening`, so nothing stops the next
contributor holding a `MutexGuard` across an S3 PUT. After this merges the echo resolver takes the
sender out of the map *before* it matches, and all five lints are `deny` at the workspace root.

## Why — learning objectives

- **`MutexGuard` drop timing** — a temporary created in a `match` scrutinee lives until the end of
  the *whole* match, not the end of the scrutinee expression; the fix is a `let` binding.
- **walrus reload H1** — the echo resolver runs inline on the decode loop, once per chunk signal, so
  guard scope here is replication latency, not just style.

## Scope

**In scope**

- `Cargo.toml`, `[workspace.lints.clippy]`: add, with a short justifying comment,
  `await_holding_lock`, `await_holding_refcell_ref`, `await_holding_invalid_type`,
  `significant_drop_in_scrutinee`, `significant_drop_tightening`, all `= "deny"`.
- `crates/pg-sink/src/reload_signal.rs`: bind the removed sender to a `let` before matching, so the
  `MutexGuard` is dropped at the end of that statement rather than after the two `tracing` events.
  Keep the arm bodies byte-identical.
- One comment at the fixed site naming the rule it encodes (scrutinee temporaries outlive the
  match), so the next reader does not "simplify" it back.
- Run `cargo clippy --all-targets --all-features -- -D warnings` and resolve anything the two
  **nursery** lints surface beyond the known site — the survey says there are none, but nursery
  lints are exactly the ones where a clippy version can disagree.

**Explicitly deferred** (do *not* build these here)

- **Do not populate `clippy.toml`'s `await-holding-invalid-types`.** The obvious candidate is
  `duckdb::Connection`, and the loader deliberately holds one across awaits on its `LocalSet` — see
  PR 14.18's ADR. Naming the lint arms the gate; the type list stays empty here.
- Do not convert any `parking_lot::Mutex` to `tokio::sync::Mutex`, and do not add a new lock.
- Do not touch the other six `.lock()` sites; they are already correct.
- No `priority` keys on the existing lint entries — see Hints.

## Hints & gotchas

- **No `priority` juggling is needed.** All five additions are `"deny"`, the same level as the
  `all = "deny"` group, so cargo's group-then-lint ordering cannot downgrade anything. A `priority`
  key would only be required if a later PR wanted to *allow* one of these workspace-wide.
- **Two of the five are nursery lints** (`significant_drop_in_scrutinee`,
  `significant_drop_tightening`). Nursery lints are allow-by-default *and* can change behaviour
  between clippy releases; denying them workspace-wide is a deliberate, greppable bet. If a
  toolchain bump ever makes one fire on correct code, the fix is a narrowly scoped `#[allow]` with a
  comment — not deleting the deny.
- `significant_drop_tightening` is the noisier of the two: it fires whenever a guard's live range is
  longer than the statements that actually need it. The survey found 0 sites, but run the full
  `--all-targets --all-features` clippy before you believe it — integration tests under `tests/`
  count too.
- **`parking_lot::MutexGuard` is not `Send`.** If a future ever held one across an `.await`, the
  failure in walrus would usually show up first as `future_not_send` in a `Send`-required crate
  (PR 14.8's gate), not as `await_holding_lock`. Both nets are wanted; neither replaces the other.
- `await_holding_invalid_type` with an empty `await-holding-invalid-types` list is a no-op today. It
  is named now so the *policy* is one config line away, and so the deliberate exclusion of
  `duckdb::Connection` is recorded rather than forgotten.
- Do not "simplify" the hoisted `let` back into the scrutinee in a later cleanup — the comment is
  load-bearing.
- `unwrap`/`expect` are `deny` in production (re-allowed under `#[cfg(test)]` by `clippy.toml`),
  `clippy::all` + `warnings` are already `deny`.
- Do not touch any `.sql` file or the `.sqlx` offline cache — there is no Docker on this machine to
  regenerate it.

# PR 14.7 — Move the last blocking std::fs call to tokio::fs and ban the blocking file APIs

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** loader

> **Phase:** 14 — Rust async/await · **Crates touched:** `loader` · **Est. size:** S ·
> **Depends on:** PR 14.6 · **Unlocks:** PR 14.8

The whole walrus production tree contains **exactly one** `std::fs::` call: `retire_file` at
`crates/loader/src/ddl.rs:315` (`std::fs::remove_file`), a sync `pub fn` on the `DROP TABLE` path.
`tokio::fs` is used **0** times and the loader's tokio feature list does not even enable `fs`.
Worse than the one site is the absence of a gate: `clippy.toml` is **2 lines**
(`allow-unwrap-in-tests` / `allow-expect-in-tests`) with no `disallowed-methods` key, so the next
blocking `read_to_string` inside an async fn lands unchallenged. After this PR the production
`std::fs::` count is 0, `retire_file` is `async` over `tokio::fs::remove_file`, and `clippy.toml`
arms `disallowed_methods` on the read/write/remove-file set — a gate that costs zero code and is
already `deny` through `clippy::all`.

## Why — learning objectives

- **`tokio::fs` is `std::fs` on the blocking pool** — it is not "async file I/O"; every call is a
  `spawn_blocking` hop. That is why it keeps the executor thread free, and also why it is not free.
- **When blocking file I/O is legitimately fine** — both binaries call `*Config::load()` (figment
  `Toml::file`/`Yaml::file`) at `main.rs:17` *before* `Builder::new_multi_thread()` at
  `main.rs:28`/`:30`. There is no runtime to block, so there is nothing to fix.
- **`clippy.toml` `disallowed-methods` as a lint gate** — a project-specific ban list expressed in
  config, not code; `clippy::disallowed_methods` lives in `clippy::style` ⊂ `clippy::all`, which is
  already `deny` at `Cargo.toml:16`, so the config alone arms it.

**In scope**

- Turn `retire_file` into `pub async fn retire_file(path: &Path) -> Result<(), LoaderError>` over
  `tokio::fs::remove_file`, preserving the idempotent `NotFound → Ok(())` arm and the
  `LoaderError::Internal("retire {path}: {e}")` message shape.
- Add `fs` to the loader's tokio feature list.
- Update the single caller (`crates/loader/tests/ddl_destructive.rs`) to `#[tokio::test]` and
  `.await` both `retire_file` calls, keeping the idempotence assertion.
- Add a `disallowed-methods` key to `clippy.toml` covering exactly six paths — `std::fs::read`,
  `std::fs::read_to_string`, `std::fs::write`, `std::fs::remove_file`, `std::fs::File::open`,
  `std::fs::File::create` — each with a `reason` naming the `tokio::fs` replacement.
- Extend the e2e harness's existing file-level allow (`tests/e2e/src/lib.rs:1`) with
  `clippy::disallowed_methods` **and a comment** saying why: `sink_spill_count` (`:159`) and
  `grep_sink_log` (`:556`) are sync log scrapes in an out-of-process test harness, not walrus
  production code. Do not silently delete the ban entry to make them pass.

**Explicitly deferred** (do *not* build these here)

- Does **not** make config loading async. `LoaderConfig::load()` / `SinkConfig::load()` run before
  the runtime is built, by design — there is no executor to starve.
- Does **not** audit `object_store`'s or `duckdb`'s internal file I/O. DuckDB's `Connection` does
  blocking file work by construction; that is PR 14.18's subject, not this one.
- Does **not** wire `retire_file` into the apply loop. It stays a `pub` API on the drop-table path
  (called today only by the integration test); this PR changes its shape, not its callers.

**Conflict — do not apply the rule blindly.** The `disallowed-methods` list must **not** include
`create_dir_all` / `remove_dir_all`. `clippy.toml` is workspace-wide and applies to test targets
too, and the integration tests use those two roughly **60** times for tempdir setup/teardown
(`crates/loader/tests/*.rs`, `crates/pg-sink/tests/*.rs`). Banning them would mean ~60 `#[allow]`s
for zero production benefit. Keep the ban to the read/write/remove-**file** set, which has exactly
one production site — the one this PR removes.

## Skeleton

```rust
// crates/loader/src/ddl.rs — the one production `std::fs::` site, ported.
use std::path::Path;

/// Retire a dropped table's `.duckdb` file (call after its owning connection is closed). Idempotent —
/// a missing file (a crash mid-retire re-run) is success.
///
/// `async` because the delete now goes through [`tokio::fs`], which hands the blocking `unlink` to the
/// runtime's blocking pool instead of parking an executor thread inside the apply worker.
pub async fn retire_file(path: &Path) -> Result<(), LoaderError> {
    match tokio::fs::remove_file(path).await {
        Ok(()) => Ok(()),
        Err(e) if e.kind() == std::io::ErrorKind::NotFound => Ok(()),
        Err(e) => Err(LoaderError::Internal(format!(
            "retire {}: {e}",
            path.display()
        ))),
    }
}
```

## Hints & gotchas

- `tokio::fs::remove_file` returns `std::io::Error`, the same type as `std::fs::remove_file` — the
  `e.kind() == ErrorKind::NotFound` arm ports across unchanged. Do not "simplify" it away; that arm
  is what makes a crash-mid-retire re-run succeed.
- `tokio::fs` is compiled out without the `fs` feature; the compiler reports an unresolved
  `tokio::fs` import that looks like a typo. Add the feature first.
- Making a `pub fn` `async` is a breaking change for every caller. There is exactly one
  (`ddl_destructive.rs`), and it is a plain `#[test]` — it needs `#[tokio::test]`. The loader already
  depends on tokio with `macros`, so no dev-dependency change is required.
- `clippy.toml` applies to **all** targets: `crates/*/src`, `crates/*/tests`, benches, and the
  `tests/e2e` harness lib. Run `cargo clippy --all-targets --all-features` (not plain
  `cargo clippy`) or you will not see the e2e breakage until CI does.
- `clippy::disallowed_methods` is already `deny` through `clippy::all` at `Cargo.toml:16` — do
  **not** add a second entry to `[workspace.lints.clippy]`; that would be a redundant knob with two
  places to drift.
- Paths in `disallowed-methods` are resolved against the *definition*, not the import, so
  `use std::fs; fs::read(..)` is caught too. Associated functions need the full path
  (`std::fs::File::open`).
- Do **not** touch any `.sql` file or the `.sqlx` offline cache — there is no Docker on this machine
  to regenerate it, and this PR needs neither.
- `unwrap()` / `expect()` stay `deny` in production; `clippy::all` and `warnings` are already `deny`.
- Unit tests are Go-style siblings (`foo.rs` → `foo_test.rs`); `ddl.rs` has no sibling test today and
  this PR does not add one — the behaviour is covered by the existing integration test.

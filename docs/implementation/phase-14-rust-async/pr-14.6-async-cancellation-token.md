# PR 14.6 — Hold a CancellationToken DropGuard so every early return drains the pod

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 14 — Rust async/await · **Crates touched:** `loader`, `pg-sink` ·
> **Est. size:** M · **Depends on:** PR 14.5 · **Unlocks:** PR 14.7

Both binaries spawn the health server **before** their long bootstrap (`loader/src/main.rs:58`,
`pg-sink/src/main.rs:70`) and then hand-roll `token.cancel(); let _ = server.await;` on exactly
**one** failure path each (`loader/src/main.rs:63-70`, `pg-sink/src/main.rs:75-82`). Every *later*
`?` returns without cancelling: in the loader `main.rs:60` (`control::connect`), `:61`
(`build_store`), `:78` (`read_current_epoch`), `:102` (`configure_s3`); in the sink `main.rs:103`
(`establish_stream`) and `:131` (`Heartbeat::connect`). On those paths the health server and the
lease renewer are abandoned with the token still live, and the ownership leases are never released —
the pod dies holding a live lease and its replacement hits `LoaderError::LeaseContended`.
`CancellationToken::drop_guard()` is used **0** times in the tree (`child_token()` exactly once, at
`reload.rs:410`). After this merges each binary's `run()` puts its whole fallible middle under a
`DropGuard`, the two hand-rolled teardown blocks collapse to a plain `?`, and the behaviour is
unit-tested through a small library helper.

## Why — learning objectives

- **`CancellationToken::drop_guard()` as RAII shutdown** — the `?`-proof way to cancel: `Drop` runs
  on the error return, the early return and the unwind, which a hand-written `token.cancel()` on one
  branch does not.
- **walrus fencing** — the ownership lease must be released (or expire) before a replacement pod can
  claim the `.duckdb` file; a pod that exits without cancelling wastes a whole lease TTL.

## Scope

**In scope**

- A small library helper, added to **both** `crates/loader/src/shutdown.rs` and
  `crates/pg-sink/src/shutdown.rs` (each crate owns its own copy — no new dependency edge between
  them):
  `pub async fn cancel_on_exit<F: Future>(token: &CancellationToken, body: F) -> F::Output`,
  holding `let _guard = token.clone().drop_guard();` for the body's duration.
- `crates/loader/src/main.rs`: extract the fallible middle of `run()` (control connect → store →
  bootstrap → epoch → renewer → `configure_s3` → the `LocalSet` drain → `release_all`) into a
  private `async fn pipeline(...)`, and call it through `cancel_on_exit`. `server.await` stays in
  `run()`, **after** the guarded call.
- `crates/pg-sink/src/main.rs`: same shape — the fallible middle (`run_shared` → `establish_stream`
  → the decode loop → the reload-controller join) moves under `cancel_on_exit`; `server.await` moves
  out to `run()` after it.
- Delete both hand-rolled `token.cancel(); let _ = server.await;` blocks; the two calls become
  `bootstrap::bootstrap(...).await?` and `bootstrap::run_shared(&cfg, deadline).await?`.
- Keep the explicit happy-path `token.cancel()` in the sink (`main.rs:181`) — it is what lets the
  reload controller and health server wind down *inside* the guarded body, before the guard drops.
- New cases in `crates/loader/src/shutdown_test.rs` (created by PR 14.1) and
  `crates/pg-sink/src/shutdown_test.rs`: the token is cancelled when the body returns `Err` from a
  post-spawn step, and also when it returns `Ok`.

**Explicitly deferred** (do *not* build these here)

- **No per-worker child tokens.** `child_token()` stays at its single site (`reload.rs:410`).
- **No change to what the drain does.** PR 3.12 (loader) and PR 2.28 (sink) own the drain steps;
  this PR only changes *whether the drain is reachable* from a given exit path.
- **No lease release on the error path.** Cancelling the token stops the renewer; actually calling
  `release_all` from an aborted bootstrap is a separate design question (the lease then expires by
  TTL, which is the designed net). Say so in the PR body; do not build it.
- Do not add `tokio-util` features, and do not touch `install_signal_handlers`.

**Conflict — the guard must not outlive the body.** If the guard were held across `server.await`
the join would hang: `serve_on` only returns once the token is cancelled. Binding it inside
`cancel_on_exit` (whose scope ends when the body completes) is exactly what guarantees the drop
happens first. Do **not** hoist `let _guard = …` to the top of `run()`, and do not remove the
sink's explicit happy-path `token.cancel()`.

## Skeleton

```rust
// crates/loader/src/shutdown.rs (and, verbatim, crates/pg-sink/src/shutdown.rs).

/// Run `body` holding a [`CancellationToken`] drop guard: whatever ends it — `Ok`, an early `?`,
/// or an unwinding panic — the token is cancelled **before this returns**.
///
/// That "before this returns" is the whole point twice over. It makes every `?` in the bootstrap
/// wind the health server and the lease renewer down instead of abandoning them; and it means the
/// caller can safely `server.await` afterwards, which would otherwise hang forever, because
/// `health::serve_on` only completes once the token is cancelled.
///
/// Cancellation on the **success** path is deliberate, not a side effect: both binaries reach the
/// end of their pipeline only when the pod is already shutting down.
pub async fn cancel_on_exit<F>(token: &CancellationToken, body: F) -> F::Output
where
    F: std::future::Future,
{
    let _guard = token.clone().drop_guard();
    body.await
}
```

## Hints & gotchas

- **`drop_guard()` consumes the token**, which is why the idiom is `token.clone().drop_guard()`.
  `CancellationToken` clones are cheap (`Arc`-based) and all clones share one cancellation state.
- **Where the guard is bound is the whole design.** Inside `cancel_on_exit` it dies with the body;
  at the top of `run()` it would still be alive during `server.await` and the join would hang
  forever, because `health::serve_on` uses `with_graceful_shutdown(shutdown.cancelled())`. If your
  first run of the binary hangs on shutdown, this is why.
- `DropGuard` also exposes `disarm()`, which returns the token *without* cancelling. Do not use it
  here — cancel-on-success is what both binaries want, and `disarm` would reintroduce the hang.
- **The helper must live in the library, not in `main.rs`.** `crates/loader/src/main.rs` and
  `crates/pg-sink/src/main.rs` are binary roots; nothing in them is reachable from a sibling test
  module. That is exactly why `cancel_on_exit` goes in `shutdown.rs` — it is what makes the
  Definition of Done testable at all.
- **Extracting `pipeline` is a borrow exercise, not a rewrite.** Pass `&LoaderConfig`,
  `&CancellationToken` and `&Arc<LoaderState>`; everything the old body owned (`pool`, `store`,
  `owned`, `keys`, `renewer`, the `LocalSet`) stays local to `pipeline`. Move lines, do not retype
  them — a behavioural change hiding in this diff is very hard to spot in review.
- The loader's `LocalSet` and its `spawn_local` handles must stay inside `pipeline`: `LocalSet`
  futures are `!Send`, and moving them across the `cancel_on_exit` boundary is fine only because
  the helper is generic over any `Future` and adds no `Send` bound. Do not add one.
- Keep the sink's `state.mark_terminating(); token.cancel();` pair inside `pipeline` — the reload
  controller and health server need the token cancelled *before* their joins, which are also inside.
- **Do not "fix" the lease release on the error path here.** With the token cancelled the renewer
  stops, so the lease lapses at TTL and PR 3.12's fencing story still holds. Releasing eagerly from
  an aborted bootstrap is a separate, argued change.
- `#[tokio::test]` needs no `start_paused`; these cases never sleep. `loader` gained the tokio
  `test-util` dev-feature in PR 14.1 — nothing new is required, so `cargo deny` is unaffected.
- Tests are Go-style siblings; `crates/pg-sink/src/shutdown.rs:126-128` is already wired, and PR
  14.1 added the loader's. `unwrap`/`expect` are `deny` in production, re-allowed under
  `#[cfg(test)]`; `clippy::all` + `warnings` are already `deny`.
- Do not touch any `.sql` file or the `.sqlx` offline cache — there is no Docker on this machine to
  regenerate it.

# PR 14.9 — Ban a direct async-trait dependency now that AFIT is available

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test,deny · **Test packages:** —

> **Phase:** 14 — Rust async/await · **Crates touched:** *none — workspace policy (`deny.toml`)* ·
> **Est. size:** S · **Depends on:** PR 14.8 · **Unlocks:** PR 14.10

walrus defines exactly **2** traits in production — `pg-sink/src/batch.rs:22` (`Clock: Send + Sync`,
a test seam) and `pg-to-arrow/src/batch.rs:747` (`ArrowNumBuilder<T>`, a macro-fed numeric bridge) —
neither async, and the `#[async_trait]` macro is used **0** times. Yet `async-trait 0.1.89` is in
`Cargo.lock:484`, pulled transitively by `axum`, `axum-core`, `object_store` and `tokio-postgres`,
so `cargo add async-trait` would look unremarkable in review. MSRV is **1.95**, twenty releases past
AFIT's 1.75 stabilisation: a walrus-authored async trait never needs the macro. This PR makes that a
machine-checked policy — `deny.toml`'s `[bans]` gains a `deny` entry with a `wrappers` allow-list, so
the crate stays tolerated transitively and becomes a hard error as a direct dependency.

## Why — learning objectives

- **AFIT vs `#[async_trait]`** — native `async fn` in traits (stable 1.75) has no boxed future and no
  proc-macro, but it is **not dyn-compatible** and its futures are **not `Send` by default**. Knowing
  those two caveats is what lets you ban the macro honestly instead of dogmatically.
- **`cargo-deny` `[bans] deny` + `wrappers`** — how to forbid a crate you must still tolerate
  transitively: `wrappers` names the direct dependents that are permitted to pull it, and anything
  else is a build failure.

## Skeleton

```toml
# deny.toml
[bans]
# Start at "warn": the tree carries known duplicate majors (arrow 54 vs 58, rand 0.8 vs 0.10,
# windows-sys generations, …) pulled by transitive deps.
multiple-versions = "warn"
# Each future entry needs a justifying comment.
skip = []
# Crates that may never be a DIRECT walrus dependency.
#
# `async-trait` boxes every trait future on the heap and adds a proc-macro to the build graph. It
# existed to work around the absence of `async fn` in traits, which stabilised in Rust 1.75 — and the
# walrus MSRV is 1.95 (workspace `rust-version`). AFIT's two caveats do not bite here: walrus has two
# trait definitions, both sync (pg-sink/src/batch.rs:22 `Clock`, pg-to-arrow/src/batch.rs:747
# `ArrowNumBuilder`), and needs no `dyn` async trait. If one is ever genuinely required, the reviewed
# answer is `trait-variant` (or an explicit `-> impl Future<Output = …> + Send` bound), not this macro.
#
# `wrappers` = the DIRECT dependents allowed to pull it transitively (verified against Cargo.lock:484).
# A fifth path failing this check is the point: review it, don't widen the list reflexively.
deny = [
  { name = "async-trait", wrappers = ["axum", "axum-core", "object_store", "tokio-postgres"] },
]
```

## Hints & gotchas

- `wrappers` entries are crate **names**, not versions, and they must be *direct* dependents of the
  banned crate. Read them off `Cargo.lock`, not off memory — `grep -n 'async-trait' Cargo.lock` then
  walk back to the nearest preceding `name = "…"` for each hit.
- Do not use `skip` or `[bans] allow` for this: `skip` is for duplicate-version noise, while
  `deny` + `wrappers` is the construct that says "tolerated transitively, forbidden directly".
- `cargo deny check` runs all four families (advisories / licenses / bans / sources). Use
  `cargo deny check bans` while iterating so an unrelated advisory does not mask your result.
- The CI version of cargo-deny is pinned (`.github/workflows/ci.yml`, `supply-chain` job) so the
  gate cannot change under the repo. If your local cargo-deny is newer, match the pinned version
  before concluding anything about the diagnostics text.
- Do not run a manifest-mutating negative probe. Review the wrappers entry directly and rely on the
  pinned positive cargo-deny gate; `Cargo.toml` and `Cargo.lock` must remain byte-identical.
- If you ever do need `dyn` dispatch over an async trait, the caveats matter: AFIT is not
  object-safe, and its futures are not `Send` — which, note, is fine on the loader's `LocalSet`
  (PR 14.8) and not fine anywhere `tokio::spawn` is involved.
- Do **not** touch any `.sql` file or the `.sqlx` offline cache — there is no Docker on this machine
  to regenerate it, and this PR is config-only.
- `unwrap()` / `expect()` stay `deny` in production; `clippy::all` and `warnings` are already `deny`.
- Unit tests are Go-style siblings (`foo.rs` → `foo_test.rs`); this PR adds none — a supply-chain
  policy is tested by `cargo deny`, not by `cargo test`.

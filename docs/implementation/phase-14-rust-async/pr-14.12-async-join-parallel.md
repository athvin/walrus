# PR 14.12 — Join the two independent Phase-A control reads on every poll

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test,integration · **Test packages:** control,loader

> **Phase:** 14 — Rust async/await · **Crates touched:** `loader` · **Est. size:** S ·
> **Depends on:** PR 14.11 · **Unlocks:** PR 14.13

`run_phase_a` opens **every** poll cycle with two independent, indexed control-DB reads awaited back
to back — `control::max_ready_lsn_end` (`crates/loader/src/phase_a.rs:75`) then
`control::read_checkpoint` (`:77`) — purely to compute one gauge,
`walrus_loader_raw_append_lag_bytes`. Neither read consumes the other's output. That is **2 serial
queries per table per `poll_interval`**, with their round-trip latencies paid serially on the loop
that also owns the append. Tokio join macros appear **0** times in the loader (`try_join!` first
appears in pg-sink in PR 14.11), and `join_all` appears **0** times in the repo. After this PR the
two reads issue concurrently in one task — no spawn, no `Send` bound, so it works on the loader's
`LocalSet` — and the gauge's latency changes from the sum of two round trips to their maximum. The
SQL query count remains two.

## Why — learning objectives

- **`join!` / `try_join!` run futures concurrently inside ONE task** — no `tokio::spawn`, therefore
  no `Send` bound on the futures. That is precisely why this works in the loader, where every apply
  loop is a `!Send` `LocalSet` task (see PR 14.8).
- **walrus Phase A ordering** — the gauge is *observability*; the claim is *correctness*. Phase A
  claims in `(lsn_end, id)` commit order, never max-row-LSN, and the claim must stay sequential
  because it decides what the rest of the pass does.

**In scope**

- Extract the gauge's two reads into a small private async fn in `phase_a.rs`, e.g.
  `async fn read_lag_inputs(ctx: &TableCtx) -> Result<(Option<Lsn>, Lsn), LoaderError>`, whose body
  is a single `tokio::try_join!` over `control::max_ready_lsn_end` and `control::read_checkpoint`,
  with a doc comment saying why the two are safe to race (independent reads, no shared txn).
- Call it from `run_phase_a` and feed `raw_append_lag_bytes` exactly as before — the metric value,
  its precomputed `ctx.series` label (`"{schema}.{table}"`) and the `Lsn::ZERO` fallback for a
  missing checkpoint are unchanged.
- Leave the rest of the pass untouched, in order: `claim_ready`, the pause/idle probe, the append,
  the watermark txn.
- Record the measured change in the PR body: the gauge's control-DB latency changes from the
  **sum → max** of two round trips per table per `poll_interval`; the query count remains two. At
  scale, N tables still issue `2 × N × 3600 s / poll_interval` gauge queries per hour, plus the pool
  note below.

**Explicitly deferred** (do *not* build these here)

- Does **not** parallelise `claim_ready` or `reload_supersede_floor`. The claim is ordering-sensitive
  — it decides what the rest of the pass does — and the reload floor is read relative to it.
- Does **not** parallelise the per-file append loop. Appends into one `.duckdb` are serial by
  construction (one exclusive writer per file).
- Does **not** add `futures`/`join_all` or any new dependency: `tokio::try_join!` is a macro from the
  already-enabled `macros` feature.

**Conflict — do not apply the rule blindly.** `control::connect` caps the pool at **5**
(`crates/control/src/db.rs:76`, `DEFAULT_MAX_CONNECTIONS`). Two concurrent acquires per table × N
owned tables can exceed that. It **degrades to queueing, never deadlocks** — each future holds
exactly one connection and releases it on completion, and neither read is inside a transaction — but
the PR must say so explicitly, and this pattern **must not** be copied inside a transaction, where a
join that acquires a second connection while the first holds an open txn is a genuine
self-deadlock risk. If a later PR raises table counts, the pool size (not the join) is the dial.

## Skeleton

```rust
// crates/loader/src/phase_a.rs

/// The two inputs to the Phase-A backlog gauge, read CONCURRENTLY.
///
/// They are independent indexed reads on the control plane — neither consumes the other's output and
/// neither runs inside a transaction — so racing them changes latency from the sum of 2 round trips
/// to their maximum while retaining 2 SQL queries.
/// `try_join!` (not `join!`) because both are fallible with the same error type: the first failure
/// short-circuits and the other future is dropped at its next await point.
///
/// Runs in ONE task: no `tokio::spawn`, so no `Send` bound — which is what makes it legal on the
/// loader's `LocalSet` (the apply-loop futures are `!Send`, PR 14.8).
///
/// Pool note: this holds two of `control::connect`'s `DEFAULT_MAX_CONNECTIONS` (5) at once. With many
/// owned tables that queues; it cannot deadlock, because neither read is inside an open transaction.
async fn read_lag_inputs(ctx: &TableCtx) -> Result<(Option<Lsn>, Lsn), LoaderError> {
    let (max_ready, checkpoint) = tokio::try_join!(
        control::max_ready_lsn_end(&ctx.pool, ctx.epoch, &ctx.schema, &ctx.table),
        control::read_checkpoint(&ctx.pool, ctx.epoch, &ctx.schema, &ctx.table),
    )?; // ControlError -> LoaderError via #[from] (error.rs:12)
    Ok((
        max_ready,
        checkpoint.map_or(Lsn::ZERO, |cp| cp.raw_appended_lsn),
    ))
}

/// One Phase-A pass. Returns the max `lsn_end` appended, or `None` if the queue was empty.
pub async fn run_phase_a(ctx: &TableCtx) -> Result<Option<Lsn>, LoaderError> {
    // Observability (PR 5.6): set the Phase-A backlog gauge every poll (0 when caught up) —
    // `max(lsn_end over ready files) − raw_appended_lsn`. Doing this before the claim means idle
    // polls report a truthful 0.
    let (max_ready, raw_appended) = read_lag_inputs(ctx).await?;
    common::metrics::set_raw_append_lag(
        &ctx.series,
        raw_append_lag_bytes(max_ready, raw_appended),
    );

    // 1. Claim in (lsn_end, id) order — SEQUENTIAL and unchanged: the claim decides what the rest of
    //    the pass does, so it may not be raced against anything.
    let claimed =
        control::claim_ready(&ctx.pool, ctx.epoch, &ctx.schema, &ctx.table, ctx.max_files).await?;
    todo!("the remainder of run_phase_a is unchanged");
}
```

## Hints & gotchas

- Use `try_join!`, not `join!`: both reads are fallible with the same `control::ControlError`, so
  `try_join!` yields `Result<(A, B), ControlError>` and one `?` converts it to `LoaderError` through
  the existing `#[from]` at `crates/loader/src/error.rs:12`. `join!` would hand you two `Result`s to
  unwrap by hand.
- `&ctx.pool` is `&PgPool`, which implements `PgExecutor` — passing it to both futures at once is
  fine and each acquires its own connection. Passing a `&mut PgConnection` to both would not compile,
  and that is the borrow-checker telling you something true about transactions.
- Concurrency here is *within one task*. Do not reach for `tokio::spawn` "to make it really
  parallel": the apply-loop future is `!Send` (it holds `TableDb`), so it would not compile, and
  `spawn_local` would add a task for two round trips.
- Keep the gauge computation where it is — **before** `claim_ready`. Moving it after the claim would
  make an idle poll report a stale non-zero backlog.
- The metric label is the precomputed `ctx.series`; leave it exactly as is. A changed label is a
  broken dashboard, and it is a silent break.
- Do **not** touch any `.sql` file or the `.sqlx` offline cache — there is no Docker on this machine
  to regenerate it. `max_ready_lsn_end` and `read_checkpoint` are called, never modified.
- `unwrap()` / `expect()` are `deny` in production; `clippy::all` and `warnings` are already `deny`.
- Unit tests are Go-style siblings (`phase_a.rs` → `phase_a_test.rs`). This PR adds none on purpose:
  the pure math is already covered and the concurrency is proven by the grep plus the compose suite.

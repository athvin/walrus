# PR 23.3 — Match TupleValue and Tier exhaustively instead of falling through a wildcard

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** pg-to-arrow

> **Phase:** 23 — Rust pattern matching · **Crates touched:** `pg-to-arrow`, `pg-sink` ·
> **Est. size:** M · **Depends on:** PR 23.2 · **Unlocks:** PR 23.4

Re-audited at **27094ef** after PR 23.2. Non-test Rust targets under `crates` (including benches,
excluding integration tests and sibling `*_test.rs` files) contain **53 literal `_ =>` arms**.
This task's bounded targets are the **5** arms in `pg-to-arrow` that fall through on walrus-owned
enums: 3 on `common::TupleValue`
(`crates/pg-to-arrow/src/batch.rs:456`, `:493`, `:739`) and 2 on `common::Tier`
(`crates/pg-to-arrow/src/descriptor.rs:133`, `:153`). The other 48 arms are outside this task's
named boundary: they are primitive/foreign catch-alls, intentional rejection paths, or component
decisions that this TupleValue/Tier pass does not own.

The formerly worst site is **not present on this baseline**. PR 10.9 commit `c206a796` already
replaced `append_value`'s bytea `_ => unreachable!(…)` with all four `TupleValue` variants;
`batch.rs` now contains zero `unreachable!` calls and its bytea match is already the target style.
This PR therefore rewrites only the 5 remaining enum arms, pins those five functions with
`#[deny(clippy::wildcard_enum_match_arm)]`, and denies
`clippy::match_wildcard_for_single_variants` workspace-wide (2 binding-wildcard sites, both in
`crates/pg-sink/tests/reload_recovery.rs`).

## Why — learning objectives

- **Exhaustiveness as a compile-time checklist** — `|` alternation instead of `_`, so adding a
  variant to an enum you own becomes a build failure at every named site rather than a silent
  fallthrough. `#[non_exhaustive]` constrains downstream crates, not the defining crate.
- **Why `TupleValue::Null` and `TupleValue::UnchangedToast` must never collapse** — the loader
  back-scans `<table>_raw` to resolve an unchanged-TOAST placeholder
  (`crates/common/src/pg_shape.rs:130-141`, PR 3.6). They share an Arrow *null* at these three
  fan-out helpers, but they remain distinct variants.
- **Restriction vs pedantic lint placement** — `wildcard_enum_match_arm` is a restriction lint and
  belongs only on the five functions whose enum fallthrough this task owns;
  `match_wildcard_for_single_variants` is a narrow pedantic lint suitable for workspace policy.
- **A compile-time red seam for a compile-time property** — these rewrites deliberately preserve
  runtime behavior, so a new runtime test cannot distinguish the old wildcard from explicit arms.
  Enabling the two lint guards first is the honest failing regression test.

## Hints & gotchas

- **Do not resurrect the stale bytea work.** `c206a796` changed `batch.rs` from 9 to 8 `_ =>`
  arms and removed its only `unreachable!`; the current bytea match already names every
  `TupleValue` variant. There is no legitimate failing bytea runtime test for this PR.
- **The three parse helpers preserve errors for `Binary`.** Naming `TupleValue::Text(_) |
  TupleValue::Binary(_)` does not claim both parse successfully: the unchanged `text(value, …)?`
  still rejects `Binary` exactly as before. The rewrite changes exhaustiveness, not behavior.
- **The five item-level denies are the red test.** Land them before the rewrites so the compiler
  proves that an enum wildcard is what fails. Do not weaken them with an allow.
- **`duckdb_of` contains nested matches with different scrutinees.** Only the outer match is on
  `Tier`; its `_ if RangeFamily…` guards and `_ => "STRUCT"` are on `u32` and must stay.
- **`RunOutcome` production handling is already right.** The controller in `reload.rs` names both
  variants. The workspace lint only exposes two test expectations that say “anything but drained”.
- `Message` is defined and matched inside `pg-sink`, so `#[non_exhaustive]` does not technically
  force those catch-alls. They remain by component policy because the three dispatchers ignore
  message families they do not own; the new comments make that choice reviewable.
- No new dependency is needed. Do not touch `.sql` or the `.sqlx` cache.

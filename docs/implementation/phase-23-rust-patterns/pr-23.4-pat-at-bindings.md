# PR 23.4 — Bind the Decimal128 precision boundary with an @ range pattern

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 23 — Rust pattern matching · **Crates touched:** `pg-to-arrow` · **Est. size:** S ·
> **Depends on:** PR 23.3 · **Unlocks:** PR 23.5

Production uses exactly **one** `@` binding — `crates/pg-sink/src/consume.rs:219`, `m @
(Message::Insert { .. } | Update { .. } | Delete { .. })`. Meanwhile the single most important
numeric boundary in the type model, `numeric` precision `p ≤ 38` (Tier-1 `Decimal128`) versus `p >
38` or unconstrained (Tier-3 `VARCHAR` carrier), is spelled **three different ways in three files**:
an if-guard `precision == 0 || precision > 38` (`schema.rs:100`), a match guard
`(1..=38).contains(&p)` (`range.rs:61`), and a range pattern `Some((39..=255, _))`
(`tier3.rs:24`). The first two are precisely the rule's "the guard duplicates the range" shape. This
PR rewrites both as `Some((p @ 1..=38, s)) => DataType::Decimal128(p, s)` — one pattern that bounds
*and* binds — and adds the boundary test (`p = 0 / 1 / 38 / 39`) that no test file pins today.

## Why — learning objectives

- **`name @ pattern`, range patterns, and const paths in patterns** — `p @ 1..=38` tests and
  binds in one unit; `39..=255` and half-open `oids::FIRST_NORMAL_OID..` are the same feature
  without a binding. All of them work in `match`, `if let`, `while let` and `let … else`.
- **The three-tier type model at its sharpest edge** — `numeric` with `p ≤ 38` is a lossless Tier-1
  `Decimal128`; unconstrained or `p > 38` is a Tier-3 `VARCHAR` carrier, because DuckDB's `DECIMAL`
  caps at precision 38 and its Parquet reader silently downcasts anything wider to `DOUBLE`.
- **One invariant, one spelling** — three encodings of the same boundary is how they drift apart.
  This PR does not (yet) centralise the constant, but it makes two of the three literally identical.

  `Some((p @ 1..=38, s)) => DataType::Decimal128(p, s)`.
- `crates/pg-to-arrow/src/range.rs:60-63` — replace `Some((p, s)) if (1..=38).contains(&p)` with

  unconstrained through **both** call sites (`tier1_data_type` and `RangeFamily::elem_data_type`),

## Skeleton

```rust
// crates/pg-to-arrow/src/schema.rs — the `oids::NUMERIC` arm of `tier1_data_type` (:98-104).
// `numeric_precision_scale` returns `Option<(u8, i8)>`; `Decimal128` takes `(u8, i8)`, so `p` and
// `s` drop straight in with no re-access and no guard.
pub fn tier1_data_type(type_oid: u32, atttypmod: i32) -> Option<DataType> {
    Some(match type_oid {
        // …unchanged BOOL / INT2 / INT4 / INT8 / FLOAT4 / FLOAT8 arms…
        // Two numeric cases, kept strictly apart (§2.3): p ≤ 38 is a lossless Decimal128;
        // unconstrained (typmod -1), p == 0 or p > 38 is a Tier-3 VARCHAR carrier (PR 2.15).
        oids::NUMERIC => match numeric_precision_scale(atttypmod) {
            Some((p @ 1..=38, s)) => DataType::Decimal128(p, s),
            // `Option` is foreign, so a catch-all is correct here (see PR 23.3's scope note).
            _ => return None,
        },
        // …unchanged TEXT / BYTEA / JSON / DATE / TIME / TIMESTAMP(TZ) arms…
        _ => return None,
    })
}
```

```rust
// crates/pg-to-arrow/src/range.rs — `RangeFamily::elem_data_type` (:56-68). Identical pattern to
// schema.rs above: same boundary, now the same spelling.
pub fn elem_data_type(self, atttypmod: i32) -> DataType {
    match self {
        Self::Int4 => DataType::Int32,
        Self::Int8 => DataType::Int64,
        Self::Num => match crate::schema::numeric_precision_scale(atttypmod) {
            todo!("Some((p @ 1..=38, s)) => DataType::Decimal128(p, s)"),
            _ => DataType::Utf8,
        },
        // …unchanged Ts / TsTz / Date arms…
    }
}
```

```rust
// crates/pg-to-arrow/src/schema_test.rs — sibling test file (`use super::*;` at :1). `numeric(p,s)`
// packs `((p << 16) | s) + VARHDRSZ`, so build the typmods the same way the existing test at :91
// does. Both call sites, one test — that is what makes the boundary a contract.
#[test]
fn numeric_precision_38_is_the_tier1_boundary_at_both_call_sites() {
    const P0: i32 = 4; // the degenerate numeric(0,0) typmod — Postgres never emits it
    const P1: i32 = (1 << 16) + 4;
    const P38: i32 = (38 << 16) + 4;
    const P39: i32 = (39 << 16) + 4;

    assert_eq!(numeric_precision_scale(P38), Some((38, 0)));
    assert_eq!(
        tier1_data_type(oids::NUMERIC, P38),
        Some(DataType::Decimal128(38, 0)),
        "38 is the LAST Tier-1 precision"
    );
    assert_eq!(tier1_data_type(oids::NUMERIC, P39), None, "39 is Tier-3");
    todo!("also pin P1 => Decimal128(1, 0), P0 => None, and -1 (unconstrained) => None");

    // The same boundary through the range element mapper.
    use crate::range::RangeFamily;
    assert_eq!(
        RangeFamily::Num.elem_data_type(P38),
        DataType::Decimal128(38, 0)
    );
    todo!("and RangeFamily::Num.elem_data_type(P39) == DataType::Utf8, same for P0 and -1");

    // …and tier3 agrees on the other side of the line (PR 2.15).
    assert!(crate::tier3::is_tier3_text(oids::NUMERIC, P39));
    assert!(!crate::tier3::is_tier3_text(oids::NUMERIC, P38));
}
```

## Hints & gotchas

- **`p` is `u8` and `s` is `i8`.** `numeric_precision_scale` returns `Option<(u8, i8)>` and
  `DataType::Decimal128(precision: u8, scale: i8)` matches exactly — no `as` cast is needed, and you
  should not add one (Phase 17's `num-` tickets care about that).
- **`1..=38` deliberately excludes 0.** The current `precision == 0 || precision > 38` guard treats
  `p = 0` as *not* Tier-1, and `p @ 1..=38` reproduces that. Note the pre-existing asymmetry: a
  `p = 0` typmod is also not Tier-3 by `tier3.rs`'s `Some((39..=255, _))` test, so it falls through
  both. Postgres cannot emit `numeric(0,0)`, so this is defensive dead space — **leave it as it
  is**; "fixing" it is a behaviour change, not a pattern refactor.
- Build the test typmods with the shift formula, not magic numbers: `((p << 16) | s) + 4`, exactly
  like the existing test at `schema_test.rs:91`. `655366` is `numeric(10,2)` if you want to check
  yourself.
- Range patterns need the bounds to be constants known at compile time. That is why the shared-const
  refactor is deferred: `oids::FIRST_NORMAL_OID..` works because it is a `const`, but a `let`-bound
  value would not.
- `schema_test.rs` opens with `use super::*;`, so `tier1_data_type`, `numeric_precision_scale`,
  `oids` and `DataType` are already in scope; you only need `use crate::range::RangeFamily;` inside
  the new test. It is a Go-style sibling file wired in at `schema.rs:130-132` — do not add an inline
  `mod tests {}`.
- `clippy::all` + `warnings` are already `deny` workspace-wide and `unwrap`/`expect` are denied in
  production (`clippy.toml` re-allows them under `#[cfg(test)]`), so the new test may `unwrap`
  freely but the two production arms may not.
- No new dependency is needed; anything you add must clear `cargo deny` (advisories, the 8-license
  allow-list, bans). Do not touch any `.sql` file or the committed `.sqlx` cache — there is no
  Docker on this machine to regenerate it.

# PR 21.3 — Assert walrus wire and exit-code invariants at compile time with const blocks

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** common

> **Phase:** 21 — Rust const & compile-time · **Crates touched:** `common`, `pg-sink` ·
> **Est. size:** S · **Depends on:** PR 21.2 · **Unlocks:** PR 21.4

There are **zero `const { }` blocks anywhere in walrus** and **zero runtime `assert!` in
production**, so a set of load-bearing invariants is enforced by prose alone. The sharpest is at
`crates/common/src/error.rs:125`, where a comment says *"Every variant is < 125, so the i32 repr
fits a u8 without truncation"* — and the very next line does an unchecked `code as u8` (`:126`).
Append an eleventh `ExitCode` variant with a value above 255 and the process silently exits with a
*different* number than the one runbooks and alerts grep for. Three more invariants have the same
shape: `PHASE_BOOTSTRAPPING`/`PHASE_READY` must stay distinct (`pg-sink/src/health.rs:22-23`, or
every pod reports `Bootstrapping` forever), `XID_PREFIXED = b"RYIUDTM"` must stay exactly the seven
streamed-block tags proto §7 lists (`pgoutput/mod.rs:19`), and `MAX_STARTUP_DEADLINE` must be
nonzero for the bound check at `config.rs:127` to mean anything. After this merges, each of those
four comments is a build gate: violate it and `cargo build` fails with the message, before a test
ever runs.

## Why — learning objectives

- **Inline `const { }` blocks as anonymous compile-time expressions** — stable since 1.79 (walrus's
  MSRV is 1.95), usable anywhere an expression is, and *distinct* from a named `const ITEM`. Reach
  for one when you want a one-off compile-time guarantee at the exact place the invariant is relied
  on, not a value anyone else will name.
- **`const { assert!(..) }` as a build-breaking invariant check** — zero runtime cost, and the error
  surfaces at compile time with your message instead of at 03:00 in a pod. It also teaches the
  const-eval subset: `while` is const, `for` is not; indexing and enum-to-int casts are const;
  formatting arguments in the panic message are not.
- **The walrus `ExitCode` `#[repr(i32)]` contract** — the numbers are a *public* interface
  (`error.rs:105-107`: "runbooks and alerts grep them — so never renumber an existing code, only
  append"). A `u8` truncation would break that contract silently.
- **The pgoutput proto-v2 xid-prefix rule** — exactly seven message tags carry a per-message xid
  inside a Stream Start..Stop block. The same bytes parse differently in and out of a stream, so
  the size of that tag set is a wire-format fact, not a tuning knob.

**In scope** — four `const { }` blocks, each placed at the site that relies on the invariant:

- `crates/common/src/error.rs`: a private `const ALL_EXIT_CODES: [ExitCode; 10]` listing every
  variant, plus a `const { }` block inside `From<ExitCode> for std::process::ExitCode` (`:123-128`)
  that walks it with a const `while` loop and asserts each discriminant is `< 125`. The fixed array
  length is itself part of the gate: adding a variant without listing it is a compile error.
- `crates/pg-sink/src/health.rs`: `const { assert!(PHASE_BOOTSTRAPPING != PHASE_READY, "…") }` at
  the top of `HealthState::phase()` (`:74`).
- `crates/pg-sink/src/pgoutput/mod.rs`: `const { assert!(XID_PREFIXED.len() == 7, "…") }` at the
  top of `parse_one` (`:238`), naming proto §7 in the message.
- `crates/common/src/config.rs`: `const { assert!(!MAX_STARTUP_DEADLINE.is_zero(), "…") }` at the
  top of `CommonConfig::validate` (`:108`) — the ceiling check at `:127` is vacuous if the ceiling
  is zero. (`Duration::is_zero` is a `const fn`.)
- Update the four prose comments the assertions now enforce so they point at the gate instead of
  restating the claim — `error.rs:125` in particular should read as "checked below", not "trust me".

**Explicitly deferred** (do *not* build these here)

- **No `static_assertions` dependency.** Const blocks are stable since 1.79 and the MSRV is 1.95,
  so no crate is needed and `cargo deny` stays untouched. If you find yourself reaching for
  `const_assert!`, you want `const { assert!(..) }`.
- **Do not convert any runtime validation into a compile-time one.** `CommonConfig::validate`
  reads env/file input; an out-of-range `startup_deadline` must stay a `Result`-returning terminal
  `Error::Config`, per the walrus config convention. The new assertion is about the *ceiling
  constant*, never about the field.
- No const-generic bound assertions — that is PR 21.4.
- No new `const fn` (PR 21.1 already did that sweep) and no new named `const` item beyond the
  private `ALL_EXIT_CODES` array.
- No `.sql` / `.sqlx` edits, no new dependency, no change to any exit-code *number*.

**Conflict to resolve explicitly** — `clippy::assertions_on_constants` is a member of `clippy::all`
and therefore **already denied** (`Cargo.toml:16`). It fires on `assert!(true)`, `assert!(false)`
and `assert!(SOME_CONST_BOOL)` — a bare literal or a path to a `const bool`. Write every assertion
as a **comparison or method call over** the constants (`PHASE_BOOTSTRAPPING != PHASE_READY`,
`XID_PREFIXED.len() == 7`, `!MAX_STARTUP_DEADLINE.is_zero()`, `(ALL_EXIT_CODES[i] as i32) < 125`)
and the lint will not trip. If one still does, that is the lint telling you the assertion is
trivially true as written — **drop or restate it, never `#[allow]` it.**

// crates/common/src/error.rs — after the ExitCode enum (:110-121).

/// Every [`ExitCode`] variant, in declaration order. The **fixed length is part of the gate**:
/// appending a variant without listing it here is a compile error, which is exactly the nudge a
/// contributor needs before they renumber a code runbooks grep.
const ALL_EXIT_CODES: [ExitCode; 10] = [
    ExitCode::Success,
    ExitCode::Config,
    todo!("the remaining eight, in the order declared at :111-120"),
];

impl From<ExitCode> for std::process::ExitCode {
    fn from(code: ExitCode) -> Self {
        // The claim at :125 is now checked, not asserted in prose. `for` is not const-evaluable;
        // `while` is. The condition is a comparison, so `clippy::assertions_on_constants` (denied
        // via `clippy::all`) does not fire.
        const {
            let mut i = 0;
            while i < ALL_EXIT_CODES.len() {
                assert!(
                    (ALL_EXIT_CODES[i] as i32) < 125,
                    "every ExitCode must stay < 125 so `code as u8` below cannot truncate the \
                     process exit status runbooks grep"
                );
                i += 1;
            }
        };
        std::process::ExitCode::from(code as u8)
    }
}

## Hints & gotchas

- **`for` is not const-evaluable; `while` is.** The `ALL_EXIT_CODES` walk must be a `while` loop
  with a manual index. `<[T]>::len()` and indexing are both const.
- **Panic messages in const eval cannot be formatted.** `assert!(cond, "…{x}…")` with a runtime-ish
  argument will not compile in a const block — keep every message a plain string literal.
- **`clippy::assertions_on_constants` is already `deny`** via `clippy::all` (`Cargo.toml:16`). Do
  not `#[allow]` it; restate the condition as a comparison instead. There are only 7 `#[allow]`s in
  production tree-wide — do not casually make it 8.
- **You cannot unit-test a compile-time assertion.** A failing `const { assert!(..) }` does not
  produce a test failure, it produces a build failure — so the "does it bite?" evidence has to be a
  manual edit pasted into the PR body. Do not add `trybuild` for this; it is a new dependency that
  must clear `cargo deny`, for four assertions.
- **`Duration::is_zero` is a `const fn`** (std, since 1.53), which is what makes the `config.rs`
  assertion legal. `Duration::from_secs(60 * 60)` at `:16` is likewise const.
- `XID_PREFIXED` is `&'static [u8]` (`b"RYIUDTM"`), so `.len()` is a const slice length — but note
  it is `const XID_PREFIXED: &[u8]`, so `XID_PREFIXED.len()` goes through the reference. That is
  fine in const eval; `XID_PREFIXED[0]` would be too.
- **Put each block where the invariant is used, not at module top.** The whole point is that the
  next reader of `parse_one` / `phase()` / the `as u8` cast sees the gate on the same screen as the
  code that depends on it.
- Unit tests are **Go-style sibling files** — extend `crates/common/src/error_test.rs`, wired by
  the `#[cfg(test)] #[path = "error_test.rs"] mod tests;` at `error.rs:130-132`. Never add an
  inline `mod tests {}`.
- `unwrap`/`expect` are `deny` in production; `clippy::all` + `warnings` are already `deny`
  workspace-wide. Nothing in this PR needs either.
- The `.sqlx` offline cache **cannot be regenerated** (no Docker locally) and nothing here touches
  a query — if `cargo sqlx prepare --check` complains, you have gone off-scope.
- If `ALL_EXIT_CODES` has to be visible from `error_test.rs`, `pub(crate)` is enough — the sibling
  test module is inside the crate. Do not make it `pub`; it is a gate, not API.

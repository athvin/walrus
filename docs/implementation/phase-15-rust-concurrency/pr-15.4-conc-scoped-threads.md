# PR 15.4 — Guard the zero-OS-thread invariant and document the async structured-concurrency equivalent

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 15 — Rust concurrency · **Crates touched:** *(none — `.github/` + `docs/`)* ·
> **Est. size:** S · **Depends on:** PR 15.3 · **Unlocks:** PR 16.1

`std::thread` appears **0 times in the entire repository** — every `*.rs` under `crates/` and
`tests/`, benches and sibling test files included. walrus spawns no OS threads at all, so there is
no stack frame whose data a scoped thread could borrow and `conc-scoped-threads` has nothing to
apply to. All concurrency is tokio: **12 `tokio::spawn` sites** and **28 `CancellationToken` uses**
in production, which is the async analogue of the join-before-return guarantee `thread::scope`
provides. Today nothing stops that invariant from silently eroding. This PR nails it down with a CI
guard in the existing `fmt · clippy · test` job and writes the note that explains what walrus uses
*instead* — including the reason it could not switch even if it wanted to.

## Why — learning objectives

- **`std::thread::scope` lifetime guarantees vs `Arc` sharing** — and what "structured concurrency"
  means once the runtime is async rather than OS-threaded.
- **Why the loader's non-`Send` DuckDB connection pins its work to one task**, and how
  `CancellationToken` shapes walrus's graceful shutdown.

## Read first

- [`conc-scoped-threads`](../../../.claude/skills/rust-skills/rules/conc-scoped-threads.md) — take
  the *Key Points*: "all threads are joined automatically when the scope returns — even on panic",
  and the `'env` borrow guarantee. Those two properties are exactly what you must show walrus already
  gets from awaited `JoinHandle`s + `CancellationToken`, without OS threads.
- `crates/pg-sink/src/reload.rs:405-485` (`spawn_exporter`) — the `tokio::spawn` at line 424, the
  `OwnedSemaphorePermit` moved *into* the task so the slot frees on every exit path, and the
  `self.token.child_token()` at line 410. This is walrus's structured-concurrency shape: a child
  token scopes the task's lifetime to its parent's.
- `crates/loader/src/health.rs:117-126` and `crates/pg-sink/src/health.rs:155-164` — `serve_on`,
  whose `shutdown: CancellationToken` parameter feeds
  `.with_graceful_shutdown(async move { shutdown.cancelled().await })`. Cancellation, not a thread
  join, is how walrus ends work deterministically.
- `crates/loader/src/apply_loop.rs:1-30` — the module doc ("**one worker per `.duckdb` file** —
  never share a DuckDB connection across tables") and `apply_loop`, the function at line 17 that
  heads the loader's 14 `clippy::future_not_send` sites.
- `.github/workflows/ci.yml:53-104` — the `gates` job (`name: fmt · clippy · test`): the fmt step at
  `:93`, the clippy step at `:96-97`, the test step at `:99`. Your guard goes immediately after
  clippy.
- `docs/implementation/notes/duckdb-lts-bump.md` — the house style for a decision note (H1, a
  `> **Status:**` blockquote stating the verdict, then evidence).

The note follows the house shape used by `docs/implementation/notes/duckdb-lts-bump.md`: an H1
`# No OS threads in walrus (PR 15.4)`, then a verdict blockquote, then the evidence. Its required
outline (each entry is one `##` heading in the new file):

- **Blockquote at the top**, before any heading:
  `> **Status:** decided <date> — **the zero-OS-thread invariant is now a CI gate.**` … `std::thread`
  has never appeared in walrus; all concurrency is tokio tasks scoped by `CancellationToken`, which
  is the async form of the join-before-return guarantee `std::thread::scope` provides.
- **`The evidence`** — the four probes as a table, with these exact results:

  | probe | result |
  |---|---|
  | `grep -rn --include='*.rs' 'std::thread' crates tests \| wc -l` | **0** (across 189 `.rs` files) |
  | `grep -rn --include='*.rs' 'tokio::spawn' crates/*/src \| grep -v _test.rs \| wc -l` | **12** |
  | `grep -rn --include='*.rs' 'CancellationToken' crates/*/src \| grep -v _test.rs \| wc -l` | **28** |
  | `clippy::future_not_send` (nursery, from the evidence sweep) | **14**, all in `loader`, from `apply_loop.rs:17` |

- **`What thread::scope guarantees, and where walrus gets the same thing`** — the mapping.
  `thread::scope` gives (a) children joined before the scope returns, even on panic, and (b) children
  borrowing `'env` stack data. walrus gets (a) from `self.token.child_token()`
  (`crates/pg-sink/src/reload.rs:410`) plus awaited `JoinHandle`s and
  `.with_graceful_shutdown(shutdown.cancelled())` (`crates/loader/src/health.rs:120-123`,
  `crates/pg-sink/src/health.rs:158`). It does **not** get (b): a `tokio::spawn`ed future is
  `'static`, so walrus pays with `move` + `Arc`. Say that gap out loud.
- **`The hard constraint: the DuckDB connection is not Send`** — the loader's 14
  `clippy::future_not_send` sites start at `crates/loader/src/apply_loop.rs:17` because
  `duckdb::Connection` is `!Send`, which makes the whole apply-loop future `!Send`: it cannot cross a
  thread boundary at all — no `thread::spawn`, no `thread::scope`, no `spawn_blocking` without
  restructuring. "One worker per `.duckdb` file, never shared" (the `apply_loop.rs` module doc) is the
  same fact seen from the data side.
- **`Scope of the guard`** — it greps `crates/*/src` only, which covers production sources **and**
  their sibling `*_test.rs` files (those live under `src/`). `tests/` and `crates/*/benches/` are
  deliberately not covered; a future bench that genuinely wants a thread will not trip it.
- **`What would reopen this`** — the concrete trigger, e.g. a CPU-bound, order-independent stage that
  profiles as dominant *and* whose data is `Send`. Name the evidence that would suffice.
- **`See also`** — `.claude/skills/rust-skills/rules/conc-scoped-threads.md` and
  `docs/implementation/notes/no-data-parallelism.md` (PR 15.3 — the sibling rayon ban).

## Hints & gotchas

- **`! grep …` and `set -e` do interact — correctly, but only if you keep the `!`.** GitHub's default
  shell for `run:` is `bash --noprofile --norc -eo pipefail`. A negated command is a *tested* command,
  so a `grep` that finds nothing (exit 1) is inverted to 0 and does **not** trip `-e`; a `grep` that
  finds a match becomes exit 1 and fails the step. Drop the `!` and you invert the whole gate.
- **The frozen pattern `std::thread::` misses `use std::thread;` + `thread::spawn(…)`.** That is a
  real hole. Widening the pattern to `'std::thread'` (no trailing colons) catches both forms and
  still satisfies every DoD box here — it is an acceptable strengthening, and worth a sentence in
  the note explaining which form you chose and why.
- **The glob `crates/*/src` deliberately includes sibling `*_test.rs` files**, because walrus puts
  unit tests under `src/` (Go-style: `src/foo.rs` → `src/foo_test.rs`). So the guard bans threads in
  unit tests too. That is a real constraint on future tickets — say so in the note rather than
  letting someone discover it in a red CI run. Integration tests under `tests/` and benches under
  `crates/*/benches/` are *not* covered.
- **Do not put this in a new job.** The `gates` job already has a warmed cargo cache and runs on
  every push; a separate job would pay checkout + toolchain setup for a `grep`. Note also that the
  `gates` job is gated on `needs.changes.outputs.code == 'true'`, so a docs-only PR skips it — which
  is fine, because a docs-only PR cannot add a thread.
- **`tokio::spawn` is *not* structured concurrency by itself** — a detached task outlives its parent.
  What makes walrus's usage structured is the `child_token()` + the moved `OwnedSemaphorePermit`
  (`crates/pg-sink/src/reload.rs:410,424-425`), which bound the task's lifetime and release its slot
  on every exit path. Get that distinction right in the note; it is the interesting part.
- **Be honest about the one guarantee async does not reproduce.** `thread::scope` lets children
  borrow `'env` stack data; a `tokio::spawn`ed future must be `'static`, so walrus pays with `move`
  + `Arc` (see the `Arc<AtomicI64>` handoff PR 15.1 just retuned). Writing "async gives you
  everything scoped threads give you" would be wrong.
- Keep prose hard-wrapped at ~95–100 columns to match the rest of `docs/implementation/notes/`.
- No `.sql` file and no `.sqlx` cache entry is involved — and must not be, since there is no Docker
  on this machine to regenerate the offline cache.

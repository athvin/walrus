# PR 15.3 — Ban rayon in deny.toml and record why walrus has no data-parallel hot path

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test,deny · **Test packages:** —

> **Phase:** 15 — Rust concurrency · **Crates touched:** *(none — `deny.toml` + `docs/`)* ·
> **Est. size:** S · **Depends on:** PR 15.2 · **Unlocks:** PR 15.4

rayon is not a dependency of any crate (**0 hits for `rayon` across every `Cargo.toml`**) and does
not appear in `Cargo.lock` at all (**0 of 493 packages**), and `Cargo.toml:66-69` already documents
deliberately dropping it: criterion is pinned `default-features = false` specifically to shed
`plotters`/`rayon`/`html_reports`. Structurally there is nothing to parallelise — the pgoutput decode
consumes a strictly ordered byte stream whose whole invariant is `(commit_lsn, lsn)` ordering, and
the loader's heavy transform is SQL executed by **DuckDB's own** thread pool, not by Rust iterators.
This PR turns that accident of history into an executable policy: a `cargo deny` ban that the
existing supply-chain CI job enforces on every push, plus a note that records the *reason* so nobody
re-litigates it from first principles in a year.

## Why — learning objectives

- **Work-stealing data parallelism vs async I/O concurrency** — and reading a dependency ban as
  executable policy (`cargo deny` `[bans]`), not as a comment someone might notice.
- **Why a CDC pipeline's ordering invariant `(commit_lsn, lsn)` forecloses per-message parallelism**
  — the correctness argument, which is stronger and more durable than "we didn't need the speed".

The note follows the house shape used by `docs/implementation/notes/duckdb-lts-bump.md`: an H1
`# No data parallelism in walrus (PR 15.3)`, then a verdict blockquote, then the evidence. Its
required outline (each entry is one `##` heading in the new file):

- **Blockquote at the top**, before any heading:
  `> **Status:** decided <date> — **rayon is banned in \`deny.toml\`.** walrus is an ordered,`
  `> I/O-bound pipeline; its one CPU-heavy stage is SQL run by DuckDB's own thread pool. There is`
  `> no data-parallel hot path to hand to a work-stealing scheduler.`
- **`The evidence`** — the four probes as a table, with these exact results:

  | probe | result |
  |---|---|
  | `grep -rn 'rayon' --include=Cargo.toml .` | 0 direct deps |
  | `grep -n 'name = "rayon' Cargo.lock` | no match (0 of 493 packages) |
  | `Cargo.toml:66-69` | criterion pinned `default-features = false` — drops `plotters/rayon/html_reports` |
  | `crates/loader/benches/transform.rs:11` | `SET threads = 4` — the parallelism knob is DuckDB's |

- **`Why parallel decode would be *wrong*, not merely unnecessary`** — the ordering argument. Every
  downstream guarantee (Phase-B dedup "max `(commit_lsn, lsn)` wins", the reload watermark algebra's
  low watermark `L_i`, the durability checkpoint) keys on commit LSN, and a work-stealing scheduler
  is *defined* by not preserving submission order. This section is the point of the note — write it
  first.
- **`Where the CPU actually goes`** — cite `docs/benchmarks.md`: the transform is DuckDB SQL, and the
  sink's measured hot cost was per-row meta JSON + allocation (PR 5.7), addressed by amortisation
  (PRs 5.7 and 15.2), not by threads.
- **`What would reopen this`** — the concrete trigger, e.g. a profile showing a *per-batch,
  order-independent* CPU stage (Parquet encode of an already-sealed batch) dominating wall time. Say
  what evidence would suffice, so the decision is revisable rather than permanent by default.
- **`See also`** — `.claude/skills/rust-skills/rules/conc-rayon-par-iter.md` and

## Hints & gotchas

- **Use `crate = "rayon"`, not `name = "rayon"`.** CI pins `cargo-deny@0.19.9`
  (`.github/workflows/ci.yml:479-482`), where `[bans]` entries are `PackageSpec`s: `crate = "rayon"`
  (optionally `"rayon@1"`). The older `{ name = "…", version = "…" }` form is deprecated and can emit
  a diagnostic. Both satisfy `grep -c 'rayon' deny.toml`, but only `crate` keeps `cargo deny check`
  output clean — verify locally before pushing, since the CI job runs the *pinned* version.
- **Verify with the same version CI uses**: `cargo install cargo-deny --version 0.19.9 --locked`,
  or `cargo binstall cargo-deny@0.19.9`. A newer local cargo-deny can accept schema the pinned one
  rejects, which turns a green local run into a red CI job.
- **Banning a crate that is absent is a no-op today — that is the point.** `cargo deny check bans`
  will pass trivially; the value is the *next* PR, where `cargo add rayon` fails the supply-chain
  job with a named reason instead of sailing through review.
- **`deny.toml` is in the CI path filter** (`.github/workflows/ci.yml:50`), so this docs-and-config
  PR does trigger the supply-chain job. Good — that is the probe.
- **The note must not read as boilerplate.** "Not applicable" is a failed note. The reviewable claim
  is the ordering one: Phase-B dedup ("max `(commit_lsn, lsn)` wins"), the reload low watermark
  `L_i`, and the durability checkpoint all assume a single ordered stream. Say which of them breaks
  and how.
- Keep prose hard-wrapped at ~95–100 columns to match the rest of `docs/implementation/notes/`.
- No `.sql` file and no `.sqlx` cache entry is involved — and must not be, since there is no Docker
  on this machine to regenerate the offline cache.

# PR 24.8 — Guard the workspace against an unjustified proc-macro plus facade crate split

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 24 — Rust macros · **Crates touched:** none (CI + docs only) · **Est. size:** S ·
> **Depends on:** PR 24.7 · **Unlocks:** PR 25.1

None of the **6** workspace members sets `[lib] proc-macro = true` — the string `proc-macro` does not
appear in a single one of the 7 manifests — and none of them is published: the only `publish` key in
the whole tree is `tests/e2e/Cargo.toml:7`'s `publish = false`, and no member carries `description`,
`repository`, `documentation` or `readme`. So the facade + re-export layout this rule prescribes has
**no external consumer to serve**: dependents are path-only (`common = { path = "../common" }`), they
already see every item `common` re-exports at `lib.rs:16-23`, and a version-skew story between an impl
crate and a facade cannot arise inside one lockstep workspace. The rule's most plausible walrus
motivation — the ID newtypes still deferred at `ids.rs:5` (`EpochNo` / `SchemaVersion` / `ReloadId`
are still bare `i64`) — is served by exactly the `macro_rules!` pattern PRs 24.2–24.6 build, including
the `#[doc(hidden)] pub mod __private` convention PR 24.5 already lands. This PR therefore adds no
seventh crate: it extends PR 24.7's guard with two more invariants and PR 24.7's note with the
two-crate section, so a future `walrus-derive` has to be an argued decision rather than a drive-by.

## Why — learning objectives

- **Why the split is forced, not stylistic** — a crate with `[lib] proc-macro = true` compiles for
  the *host* and can export **nothing but** procedural macros: no trait, no type, no function. Any
  library that wants both a derive and ordinary API items has no choice but two crates.
- **The `::mycrate::__private::` call convention** — generated code runs in the *caller's* crate, so
  it must name every helper by an absolute path through the facade. That is the same problem
  `$crate` solves for `macro_rules!` (PR 24.4) and the same reason `__private` exists (PR 24.5) —
  one concept, two mechanisms.
- **walrus's workspace shape** — 6 path-only members inheriting `[workspace.package]`
  (`edition`/`license`/`rust-version`), none published, all locked in step. Half the facade
  pattern's benefits are version-skew mitigations that simply do not exist in that shape.

## Scope

**Conflict to resolve explicitly (do not apply the rule blindly):** CONTEXT §4 pre-decides this rule
as **D**, on the same "walrus publishes nothing" evidence that makes `api-serde-optional`,
`doc-cargo-metadata` and `lint-cargo-metadata` D. **Do not create a `walrus-derive` (or any 7th)
crate**, not even an empty one "so the guard has something to check" — a speculative proc-macro member
would cost a host compile on every clean build and in both Docker images while exporting nothing
anyone calls. The required resolution is: one shared note (extending PR 24.7's file, *not* a second
note) plus two more invariants in PR 24.7's guard. Also do not let the decline pretend the rule is
wrong — it is correct *for a published library*; the note's job is to state the precondition walrus
does not meet and to name what would change that.

## Skeleton

```bash
# scripts/proc-macro-guard.sh — appended below PR 24.7's invariant 1. MANIFESTS is already defined
# there as (Cargo.toml crates/*/Cargo.toml tests/e2e/Cargo.toml); reuse it, don't redeclare it.

# Invariant 2 (PR 24.8): no member may become a proc-macro crate. A `proc-macro = true` lib can
# export ONLY procedural macros — no trait, no type, no fn — so this would always mean a new crate
# plus a facade. Same `|| true`: no match is the success case under `set -e`.
declared=$(grep -nE '^[[:space:]]*proc-macro[[:space:]]*=' "${MANIFESTS[@]}" || true)
if [ -n "$declared" ]; then
  echo "::error::a workspace member declares proc-macro = true — see docs/implementation/notes/proc-macros-declined.md (§ The two-crate split) before adding one"
  echo "$declared"
  exit 1
fi

# Invariant 3 (PR 24.8): the workspace stays 6 path-only members. Hard-coded ON PURPOSE — adding a
# crate should force a conscious edit here (and a paragraph in the note), not slip through.
# `--no-deps` means no dependency resolution: no network, no registry, no compile.
EXPECTED_MEMBERS=6
actual=$(cargo metadata --no-deps --format-version 1 \
  | python3 -c 'import json,sys; print(len(json.load(sys.stdin)["packages"]))')
if [ "$actual" != "$EXPECTED_MEMBERS" ]; then
  echo "::error::workspace member count is $actual, expected $EXPECTED_MEMBERS — if this is a deliberate new crate, bump EXPECTED_MEMBERS and say why in docs/implementation/notes/proc-macros-declined.md"
  exit 1
fi

echo "ok: no proc-macro crate; workspace is $actual path-only members, none published"
```

```text
docs/implementation/notes/proc-macros-declined.md — the section PR 24.8 appends. The `##` heading is
shown indented here so this fence stays an outline; write it at column 0 like the rest of the note.

  ## The two-crate split (PR 24.8)

### What the rule prescribes
`mycrate-derive` (`[lib] proc-macro = true`) + `mycrate` facade that `pub use`s the derive, so users
depend on one crate and generated code says `::mycrate::__private::helper(..)`.

### Why the split is forced
A `proc-macro = true` crate compiles for the host and can export ONLY procedural macros — quote the
rule's constraint, then state the consequence: it is never one crate, always two.

### Why walrus does not need the facade half
- 6 path-only members, none published (only `tests/e2e/Cargo.toml:7` sets `publish = false`; no
  `description`/`repository` anywhere) -> no external consumer, no version skew to hide.
- `common` is already the facade: `lib.rs:4-23`, 11 `pub mod`s + 14 re-exports, 4 dependent crates.
- The absolute-path problem the facade solves for generated code is already solved declaratively:
  `$crate::` (PR 24.4) + `#[doc(hidden)] pub mod __private` (PR 24.5).

### The candidate that would have justified it, and why it does not
`EpochNo` / `SchemaVersion` / `ReloadId` (`ids.rs:5`, still bare `i64`) each need ~25 mechanical
lines (`ids.rs:11-66`). Input is an IDENTIFIER, so `macro_rules!` emits them verbatim; a derive is
only unavoidable when the input is a TYPE DEFINITION whose fields must be walked (PR 24.7's trigger).

### How it is enforced
`scripts/proc-macro-guard.sh` invariants 2 and 3, in the CI `supply-chain` job.
```

## Hints & gotchas

- **`cargo metadata` without `--no-deps` is a different command.** It resolves the whole dependency
  graph (network, registry index, `Cargo.lock` update) and can take tens of seconds in a cold job.
  `--no-deps` reads only the workspace manifests. Keep the flag; the `supply-chain` job has no
  toolchain-install step and no cargo cache.
- **`python3` is present on `ubuntu-latest` and on macOS**, so it is the portable JSON reader here;
  `jq` also exists on the GitHub runner but not necessarily locally. Whichever you pick, do not parse
  the JSON with `grep -c '"name"'` — dependency-free output still contains `name` keys in
  `targets[]`, and the count will be wrong.
- **Hard-coding `EXPECTED_MEMBERS=6` is the feature, not a bug.** The point of a D-archetype guard is
  that the next person who wants a 7th crate has to open this file and the note. Say so in a comment,
  or a future reader will "fix" it into `>= 6`.
- **Whitespace variants.** `proc-macro=true`, `proc-macro = true`, and an indented form under `[lib]`
  are all valid TOML. Anchor with `^[[:space:]]*` and allow `[[:space:]]*=`; do not match a bare
  `proc-macro` substring, or PR 24.7's own comments (and this note's filename) will trip it.
- **Do not grep `Cargo.lock` for proc-macros.** 19 of them are in there by design (`serde_derive`,
  `sqlx-macros`, `thiserror-impl`, `async-trait`, …) and must stay. Manifests only — same rule as
  PR 24.7.
- **`common` could never itself become the proc-macro crate.** A `proc-macro = true` lib exports only
  macros, so `Error`, `Lsn`, `SinkMeta` and the other 14 re-exports at `lib.rs:16-23` would stop
  compiling instantly. That is the concrete reason the split is forced — put it in the note.
- **Don't confuse this with `__private`.** PR 24.5's `#[doc(hidden)] pub mod __private` is already
  landed and is the *right* half of this rule to have adopted; this ticket declines only the
  crate-splitting half. Say that explicitly in the note so a reader doesn't think walrus rejected the
  convention wholesale.
- **The e2e crate is the only one with a `publish` key.** Write "no member is published; only
  `tests/e2e/Cargo.toml:7` states it explicitly" — not "no `publish` metadata anywhere". Precision is
  the entire value of a decision note.
- No new dependency is introduced, so nothing has to clear `cargo deny`'s advisories / 8-license
  allow-list / bans. A `walrus-derive` crate would have introduced three (`syn`, `quote`,
  `proc-macro2`) plus their transitive tails.
- This PR touches no Rust, so `cargo fmt --check`, `clippy` and `cargo test --workspace` are
  unchanged-green by construction — run them anyway before pushing.

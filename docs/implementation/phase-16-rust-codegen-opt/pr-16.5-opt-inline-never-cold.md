# PR 16.5 — Extract the decoder's EOF error construction into a `#[cold] #[inline(never)]` helper

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 16 — Rust compiler optimization · **Crates touched:** `pg-sink` · **Est. size:** S ·
> **Depends on:** PR 16.4 · **Unlocks:** PR 16.6

`Reader` builds `DecodeError::UnexpectedEof { needed, offset, remaining }` **inline at five sites**
— `crates/pg-sink/src/pgoutput/reader.rs:34, 56, 70, 84, 104` — one in `need` and one each in
`int16`, `int32`, `int64` and `string`. On `main` three of them live inside `map_err` closures on a
`try_into` that the preceding `need()` already proved can never fail; PR 16.2 turned those into
`let … else` arms and deliberately **kept the count at five** so this ticket has its target intact.
Either way it is literally the rule's "Bad" shape: error-construction code sitting in the body of
the hottest function in the sink, inside the **236 ns/row `parse_tuple`** path, where it costs
instruction-cache footprint on every well-formed row that never takes it. `#[inline(never)]` and
`#[cold]` counts are **0** repo-wide. This PR collapses the five to one
`#[cold] #[inline(never)] fn eof(needed: usize, pos: usize, remaining: usize) -> DecodeError`, with
byte-identical behaviour — the golden vectors pin the error payloads.

## Why — learning objectives

- **`#[cold]` + `#[inline(never)]` for code layout** — the pair moves error-construction bytes into
  a separate section away from the hot function, so the instruction cache holds decode work instead
  of struct-literal setup, and the branch to it gets the "unlikely" layout.
- **The pgoutput framing contract** — running off the end of a message is a *modelled* decode error,
  never a panic (`reader.rs:1-2` says so in the module doc). Extracting the constructor must not
  weaken that: `eof` returns a `DecodeError`, it does not `panic!` and it is not `-> !`.

## Skeleton

```rust
// crates/pg-sink/src/pgoutput/reader.rs — a private free function, below the `impl Reader`.

/// Build the `UnexpectedEof` a failed read reports.
///
/// `#[cold]` tells the compiler this is the unlikely branch (better layout + branch hints);
/// `#[inline(never)]` keeps the three-field struct setup out of `Reader`'s bodies, which run
/// inside the 236 ns/row `parse_tuple` loop. Behaviour is unchanged and *checked*: the golden
/// vectors in `crates/pg-sink/tests/pgoutput_vectors.rs` pin `needed` / `offset` / `remaining`.
/// This is an error constructor, never a panic — `pgoutput` framing failures are modelled
/// (`reader.rs` module doc).
#[cold]
#[inline(never)]
fn eof(needed: usize, pos: usize, remaining: usize) -> DecodeError {
    DecodeError::UnexpectedEof {
        needed,
        offset: pos,
        remaining,
    }
}

impl<'a> Reader<'a> {
    /// Error unless at least `n` bytes remain — and hand those bytes back (PR 16.2).
    #[inline]
    fn need(&self, n: usize) -> Result<&'a [u8], DecodeError> {
        self.rest()
            .get(..n)
            .ok_or_else(|| eof(n, self.pos, self.remaining()))
    }

    /// Big-endian `Int32` (OID / xid). `int16` / `int64` take the same shape with 2 / 8.
    #[inline]
    pub fn int32(&mut self) -> Result<u32, DecodeError> {
        let Some(&arr) = self.rest().first_chunk::<4>() else {
            return Err(todo!("eof(4, self.pos, self.remaining())"));
        };
        self.pos += 4;
        Ok(u32::from_be_bytes(arr))
    }

    /// A null-terminated UTF-8 `String`. NOTE the offset: this site reports `start`, not
    /// `self.pos` — they are equal today, but pass `start` so the vectors stay byte-identical.
    pub fn string(&mut self) -> Result<String, DecodeError> {
        let start = self.pos;
        let tail = self.rest();
        let Some(rel) = tail.iter().position(|&b| b == 0) else {
            return Err(todo!("eof(1, start, self.remaining())"));
        };
        todo!("unchanged remainder");
    }
}
```

## Hints & gotchas

- **`#[cold]` must not change semantics.** `eof` returns a `DecodeError`; it is not `-> !` and it
  does not `panic!`. The module doc at `reader.rs:1-2` promises "running off the end is a modelled
  `DecodeError::UnexpectedEof`, never a panic" — that promise is the reason this crate can decode
  hostile bytes at all.
- Watch the `offset` argument. `string`'s site reports `start` (the position *before* the NUL scan);
  the others report `self.pos`. They coincide today, but pass what the original site passed — the
  golden vectors compare payloads, and a silent off-by-one here is exactly the bug they exist to
  catch.
- Take the arguments by value (`usize`, `usize`, `usize`) as in the frozen signature, not `&self`.
  A `&self` method would re-borrow `Reader` inside `let … else` arms that already hold a borrow of
  `self.rest()` and will not compile.
- Naming: `eof` is a **private free function** in `reader.rs`. Do not `pub` it — `pg_sink::pgoutput`
  re-exports `Reader`, and widening the public surface for a constructor is a Phase-13 `api-*`
  discussion, not this one.
- `#[cold]` + `#[inline(never)]` are both stable and MSRV-clean on the pinned 1.95.0 toolchain
  (`rust-toolchain.toml:4`); no feature gate, no nightly.
- `unwrap`/`expect` are `deny` in production and `clippy::all` + `warnings` are already `deny`
  workspace-wide, so every rewritten arm must still produce a real error value.
- `reader.rs` has **no sibling `reader_test.rs`** — its coverage is the integration test
  `crates/pg-sink/tests/pgoutput_vectors.rs`. If you want a unit-level assertion on `eof`, add it
  there rather than inventing a new sibling file mid-refactor.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it.
- Benches are not a CI gate; re-running `cargo bench -p pg-sink --bench decode` is optional here.
  If you do run it and the median moves outside noise, add the row to `docs/benchmarks.md`
  § History — a null result is still worth one line.

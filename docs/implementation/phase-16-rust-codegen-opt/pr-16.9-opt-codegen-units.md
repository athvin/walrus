# PR 16.9 — Record the codegen-units rejection and guard the default

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test · **Test packages:** common

> **Phase:** 16 — Rust compiler optimization · **Crates touched:** `common` *(plus `Cargo.toml`
> and a design note)* · **Est. size:** S · **Depends on:** PR 16.8 · **Unlocks:** PR 16.10

walrus already rejected this rule — in writing, with a reason, three years of roadmap ago.
`Cargo.toml:71-75` says it outright: *"`codegen-units` is left at the default: cgu=1 buys only a few
percent more for ~2× the release build — a bad trade for a project whose Phase-5 north star is
\*cutting\* CI/Docker build time (PRs 5.1-5.3)"*. Measured, not theoretical:
`grep -cE '^\s*codegen-units' Cargo.toml` = **0** (the single mention in the file is that comment at
`:73`), and both release images cold-build bundled DuckDB **from source**
(`deploy/docker/Dockerfile.loader:41`, already the slowest job in CI). What is missing is
durability: the rationale is a comment nobody is obliged to read, `docs/implementation/notes/` holds
no build-profile ADR, and nothing fails if a future "quick perf win" adds the key. After this merges
the decision lives in `docs/implementation/notes/rust-skills/opt-codegen-units.md`, `Cargo.toml:73` links
to it, and `crates/common/tests/build_profile.rs` fails `cargo test -p common` the moment
`[profile.release]` grows a `codegen-units` line or loses the rationale.

## Why — learning objectives

- **Codegen units and parallel LLVM compilation** — rustc splits a crate into N units so LLVM can
  optimise them in parallel; `codegen-units = 1` gives LLVM the whole crate (better inlining,
  dead-code elimination, constant propagation) and gives you a serial, much longer link.
- **The compile-time/runtime trade-off is a *project* decision, not a lint** — the same setting is
  right for a latency-critical service and wrong for a project whose stated goal was cutting CI and
  Docker build time.
- **Read a repo's own recorded decisions before "optimising" it** — the answer to this rule was
  already in `Cargo.toml`; the failure mode this ticket fixes is that it was only in a comment.
- **An ADR plus a mechanical guard beats either alone** — the note explains, the test enforces, and
  the re-open trigger is written down so the decision can be revisited on evidence rather than
  re-litigated on vibes.

## Hints & gotchas

- **`crates/common/tests/build_profile.rs` is PR 16.1's file.** If 16.1 has not merged, create it
  here in the same shape (`include_str!("../../../Cargo.toml")`, one `#[test]` per invariant) and
  say so in the PR body — but do **not** add the `lto` assertion; that is 16.1's probe.
- **The path depth matters:** from `crates/common/tests/`, the workspace manifest is
  `../../../Cargo.toml`. Get it wrong and you `include_str!` the *crate* manifest, which has no
  `[profile.release]` at all and the test passes vacuously.
- **`include_str!` is a real build dependency.** rustc records it in the dep-info file, so editing
  `Cargo.toml` recompiles the test — which is exactly why this guard works. Do not replace it with a
  runtime `std::fs::read_to_string`; that would read from whatever the CWD happens to be.
- **Parse the table, not the file.** `codegen-units` appears in the *comment* at `:73` and will
  appear in your new ADR-link line too. Scope the assertion to the `[profile.release]` body and skip
  `#` lines, or the guard fails the instant it is written.
- **`[profile.release]` is currently the last table in `Cargo.toml`.** Your body-extraction helper
  must handle "no following `[` header" (end of file) as well as a following table — someone will
  add `[profile.bench]` one day.
- **Do not "improve" the PR 5.7 comment.** Its wording is the recorded decision and PR 16.1's guard
  may key off part of it. Append your ADR pointer; leave the sentences alone.
- Integration tests live under `crates/<crate>/tests/` and are *not* the Go-style sibling pattern —
  `clippy.toml` re-allows `unwrap`/`expect` there, so a plain `assert!`/`panic!` in this file is
  fine even though production code denies them.
- **`clippy::all` + `warnings` are already `deny`**; a `--all-targets` clippy run covers this test
  file, so keep it warning-clean (no unused helper, no dead `const`).
- Adding a `docs/**`-only file does not trigger the heavy CI suite, but this PR also touches
  `Cargo.toml` and a test — expect the full `gates` job. That is fine; it is a string comparison.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache (no Docker locally to
  regenerate it), and add no dependency — any new one must clear `cargo deny`.

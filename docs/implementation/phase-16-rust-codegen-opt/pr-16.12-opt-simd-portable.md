# PR 16.12 — Decline portable SIMD and ban the SIMD crates

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test,deny · **Test packages:** —

> **Phase:** 16 — Rust compiler optimization · **Crates touched:** *(`deny.toml` and a design
> note)* · **Est. size:** S · **Depends on:** PR 16.11 · **Unlocks:** PR 17.1

There is no bare numeric vector workload here to vectorize. `grep -rn
'Vec<f32>\|Vec<f64>\|\[f32\]\|\[f64\]\|\[f32;\|\[f64;' crates/*/src` minus `*_test.rs`
returns **0**. The merged tree has 38 production `f32`/`f64` token mentions across six files:
metric gauges (`crates/common/src/metrics.rs`), lease-duration bindings
(`crates/control/src/{table_ownership,reload}.rs`), backpressure ratios
(`crates/pg-sink/src/memory.rs`), scalar Arrow builders, and geometric parsing/appending
(`crates/pg-to-arrow/src/{batch,geometric}.rs`). `batch.rs` has one `&[Option<f64>]` helper, but it
only iterates a handful of parsed geometric fields into Arrow children; it performs no numeric
arithmetic. walrus's measured hot costs are per-cell `String` allocation (PR 5.4) and
JSON serialisation (PR 5.7): allocator and branch work, not arithmetic density. `std::simd` also
requires nightly, and `rust-toolchain.toml:4` pins stable `1.95.0`. After this merges the decision
is recorded in `docs/implementation/notes/rust-skills/opt-simd-portable.md` **and made mechanical**: `deny.toml`
grows `[[bans.deny]]` entries for `wide`, `packed_simd_2` and `simdeez`, so a future SIMD dependency
fails the pinned `cargo deny` supply-chain job (`.github/workflows/ci.yml:473`) instead of sliding
in.

## Why — learning objectives

- **When SIMD is and is not the answer** — SIMD pays where arithmetic density is high over
  contiguous numeric data. walrus is allocation- and branch-bound over strings and enums; there is
  no `[f64]` to widen.
- **Nightly vs stable, again** — `#![feature(portable_simd)]` is nightly-only against a repo that
  pins one exact stable; the stable alternatives are third-party crates, each a permanent
  supply-chain obligation.
- **`cargo deny` bans as the enforcement arm of an architectural decision** — an ADR explains, but
  `[[bans.deny]]` is what makes the decision survive a well-meaning PR. Every entry needs a
  justifying comment, which `deny.toml:55` already requires.
- **Declining half a rule** — the rule's autovectorization-friendly idioms (iterators over indexing,
  `chunks_exact`, no early exits) are worth having, and PR 16.2 already delivered them in the hot
  paths; say so rather than pretending the whole rule is inapplicable.

## Hints & gotchas

- **Verify the entry syntax against the pinned cargo-deny (0.19.9), not the docs of the latest.**
  Modern versions take `crate = "wide"` (a package spec, optionally `"wide@0.7"`) plus `reason`;
  older schemas used `name = "wide"` / `version = "*"`. Run `cargo deny check bans` locally with the
  pinned version before pushing — a schema mismatch fails the whole `supply-chain` job, not just
  this check.
- **None of the three crates is in `Cargo.lock` today** (verified: no `wide`, `packed_simd_2`,
  `simdeez`, `safe_arch`), so the ban is inert on a clean tree — which is exactly what you want a
  guard to be. If `cargo deny check bans` fails on a clean tree, you have banned something a
  transitive dependency actually pulls; re-check the name before widening the list.
- **Do not ban `safe_arch` or other low-level building blocks.** The three named crates are the
  user-facing SIMD APIs; banning transitive infrastructure risks breaking an unrelated upgrade for
  no benefit. Keep the list to the record's three.
- **`multiple-versions = "warn"` must stay `warn`.** `deny.toml:51-54` explains why (known duplicate
  majors from transitive deps). Flipping it while you are "in the file anyway" fails CI for an
  unrelated reason and buries this PR's actual change.
- **Every `[bans]` entry needs a justifying comment** — that is `deny.toml:55`'s stated convention,
  and it is the difference between a ban a future reader can evaluate and one they will delete.
- **Do not claim the whole rule is inapplicable.** Its autovectorization half is real advice, and
  PR 16.2 already applied it; an ADR that ignores that reads as dismissive and will be re-litigated.
- **Do not add a string guard to `crates/common/tests/build_profile.rs` for this one.** The
  `supply-chain` job is the guard; a duplicate check would drift out of sync with `deny.toml`.
- **`geometric.rs` will tempt you.** `Pt { x: f64, y: f64 }` looks vectorizable — read the module
  first: it parses Postgres geometric text into nested Arrow `STRUCT`/`LIST<STRUCT>` builders and
  performs no arithmetic over a slice of `Pt`. Say that in the ADR; it is the one place a reader
  will push back.
- No Rust changes means `cargo fmt`/`clippy`/`test` should be unchanged from `main` — run them
  anyway. Do not touch any `.sql` file or the committed `.sqlx` offline cache (no Docker locally to
  regenerate it).

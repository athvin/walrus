# PR 16.7 — Mark the decoder's rare framing branches with std::hint::cold_path

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 16 — Rust compiler optimization · **Crates touched:** `pg-sink` · **Est. size:** S ·
> **Depends on:** PR 16.6 · **Unlocks:** PR 16.8

The pgoutput decoder has five branches that can only fire if the wire cursor has misaligned —
`DecodeError::BadTupleFormat` at `crates/pg-sink/src/pgoutput/mod.rs:200`, `:228`, `:307`, `:331`
and `:346`. On a well-formed stream from a walsender they are taken **zero** times, ever, yet the
optimiser currently has no way to know that: one of them is the fall-through arm of the per-column
`match` inside `parse_tuple`'s `for _ in 0..ncols` loop, the exact 236 ns/row loop the PR 5.4
`parse_tuple/narrow_int4` bench measures. `std::hint::cold_path()` — stabilised in **1.95.0**, which
is precisely the toolchain `rust-toolchain.toml:4` pins — expresses "this path is rare" on stable
Rust, and it appears **0 times** in walrus today (`grep -rn 'cold_path' crates tests | wc -l` = 0).
After this merges each of those five branches opens with a `cold_path()` call, the golden vectors
still pin byte-identical error payloads, and the `msrv` CI job proves the hint is MSRV-clean rather
than a nightly feature smuggled in.

## Why — learning objectives

- **`std::hint::cold_path()` on stable** — a zero-cost, no-argument optimiser hint that marks the
  *enclosing* code path unlikely, letting LLVM sink those blocks out of the hot layout; unlike
  `#[cold]` (PR 16.5/16.6) it needs no separate function to attach to.
- **MSRV decides which hints you may reach for** — `std::hint::{likely, unlikely}` are still
  nightly-gated; `rust-toolchain.toml:4` pins stable `1.95.0` and `Cargo.toml:8` declares the same
  MSRV, so the nightly half of this rule is simply unavailable and reaching for it would be a
  toolchain change disguised as an optimisation.
- **pgoutput framing: which branches are structurally impossible** — `'n'`/`'u'`/`'t'`/`'b'` is the
  *closed* set of TupleData format bytes (proto §5) and `'N'` is a fixed marker; anything else means
  the cursor desynchronised upstream, which walrus treats as fail-loud, never guess.
- **A dependency is not a branch hint** — the rule's stable fallback is the `likely-stable` crate;
  in walrus every new dep must clear `cargo deny`'s advisories / 8-license / bans gate, which is a
  real recurring cost to buy a compiler hint `std` already ships.

## Scope

**In scope**

- Add `std::hint::cold_path();` as the **first statement** of each of the five rare framing branches
  in `crates/pg-sink/src/pgoutput/mod.rs` — `:200` (`expect_n`), `:228` (`parse_tuple`
  fall-through), `:307` (`'I'` marker), `:331` (`'U'` old-image tag), `:346` (`'D'` old-image tag).
- Where the branch is currently a one-expression match arm (`other => return Err(...)`), widen it to
  a block so the hint and the `return` both fit; keep the arm's binding name (`other`, `marker`,
  `b`) and the constructed error **exactly** as they are.
- A short comment at the first use naming *why* the branch is cold (a well-formed walsender stream
  never produces a byte outside the closed set) and that `cold_path` is stable as of the pinned
  1.95.0 — so the next reader does not "clean it up".

**Explicitly deferred** (do *not* build these here)

- **No reordering of `parse_one`'s message-tag match arms** (`mod.rs:248-450`). The current order
  mirrors the protocol spec and the golden-vector file order; churning it for a speculative layout
  win is exactly the guessing PR 5.7 refused.
- **No nightly feature flags** — no `#![feature(likely_unlikely)]`, no `std::hint::likely`,
  no `std::hint::unlikely`.
- **No new dependency** — `likely-stable` is not added.
- No `#[cold]` / `#[inline(never)]` work: `UnexpectedEof` extraction is PR 16.5 and the
  `Error::ValueParse` constructor is PR 16.6. Do not revisit either.
- No benchmark gate. Branch hints on a never-taken path are a layout change, not a throughput
  change; do not claim a criterion delta you cannot measure.

**Conflict with the corpus — resolve it this way.** The rule's *primary* recommendation is
`std::hint::{likely, unlikely}`, which is **nightly-only**, and `rust-toolchain.toml:4` pins stable
`1.95.0`; its stable fallback is the third-party `likely-stable` crate. **Resolution: use only
`std::hint::cold_path()`.** Adding a dependency to express a branch hint would have to clear
`deny.toml`'s advisories / license allow-list / bans gate (and the pinned `cargo-deny` job at
`.github/workflows/ci.yml:473`) forever, for no measured gain — while `cold_path` is in `std` on the
toolchain walrus already pins. Do **not** apply the rule's nightly sections blindly.

// crates/pg-sink/src/pgoutput/mod.rs

/// Consume the fixed `'N'` marker that precedes a new tuple; a mismatch is an upstream framing
/// error (a misaligned parse).
fn expect_n(reader: &mut Reader<'_>) -> Result<(), DecodeError> {
    let b = reader.byte1()?;
    if b != b'N' {
        // A well-formed walsender stream ALWAYS has 'N' here (proto §6); reaching this means the
        // cursor desynchronised upstream. `cold_path` (stable since 1.95.0 — the channel pinned in
        // rust-toolchain.toml) tells LLVM to sink this block out of the hot layout.
        std::hint::cold_path();
        return Err(DecodeError::BadTupleFormat { byte: b });
    }
    Ok(())
}

            b'n' => TupleValue::Null,
            b'u' => TupleValue::UnchangedToast,
            b't' => todo!("unchanged — keep the existing Text arm verbatim"),

## Hints & gotchas

- **`cold_path()` takes no arguments and returns `()`.** It is *not* `unlikely(cond)`. It marks the
  path it is *called on*, so it must be inside the rare branch — putting it before the `if` marks
  the hot path cold, which is the opposite of the point.
- **`clippy::all` + `warnings` are already `deny`** (`Cargo.toml:12-16`). Widening `other => return
  Err(..)` into `other => { ...; return Err(..) }` is fine, but do not leave an unused binding
  behind — rename to `_other` only if you genuinely stop using it (you don't; the error carries it).
- **`rustfmt` will reformat the widened arms.** Run `cargo fmt` before `cargo fmt --check`, and keep
  the diff to the five branches — a stray reflow elsewhere in a 480-line file makes review hard.
- **Do not touch `crates/pg-sink/tests/pgoutput_vectors.rs`.** It is the behaviour lock for this PR;
  a change there would mean you altered decoder behaviour, which this ticket forbids.
- `mod.rs` has **no sibling `mod_test.rs`** (unlike `typmod.rs` → `typmod_test.rs`). Do not invent
  one here just to hold a hint test — there is nothing observable to assert about `cold_path`, and
  walrus's convention is sibling `foo_test.rs` for unit tests, `tests/` for conformance.
- **This is unobservable at runtime by design.** The probe is the grep count plus the still-green
  golden vectors, not a benchmark. Do not add a criterion case or claim a delta in
  `docs/benchmarks.md`; the branches you hinted are never executed in the benches at all.
- If `std::hint::cold_path` ever fails to resolve, you are not on the pinned toolchain — check
  `rustup show` against `rust-toolchain.toml:4` rather than reaching for `#![feature(...)]`.
- No new dependency, so `cargo deny` is unaffected; keep it that way. `likely-stable` would have to
  clear `deny.toml`'s advisories, 8-license allow-list and bans checks on every future run.
- `unwrap`/`expect` are denied in production (`Cargo.toml:20-21`); none of this diff needs either.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it.

# PR 16.4 — Deny `clippy::inline_always` in the workspace lints

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 16 — Rust compiler optimization · **Crates touched:** — (workspace `Cargo.toml` only) ·
> **Est. size:** S · **Depends on:** PR 16.3 · **Unlocks:** PR 16.5

`grep -rn 'inline(always)' crates tests | wc -l` = **0**: walrus has never forced an inline, and
`clippy::inline_always` did not appear among the **51** distinct pedantic/nursery lints the PR 8.5
sweep surfaced — because nothing triggers it. That is a clean baseline with no fence around it.
`clippy::inline_always` is a **pedantic** lint, so `[workspace.lints.clippy] all = "deny"`
(`Cargo.toml:15-16`) does not cover it, and nothing stops PR 16.3's fresh `#[inline]` work from
drifting one word further into `#[inline(always)]` the next time a benchmark disappoints. This PR
adds a single line — `inline_always = "deny"` — to `[workspace.lints.clippy]`, which every one of
the six members already inherits via `[lints] workspace = true`. No crate source changes; after it,
a scratch `#[inline(always)] fn` anywhere in the workspace fails
`cargo clippy --all-targets --all-features -- -D warnings`.

## Why — learning objectives

- **clippy lint groups** — why a *pedantic* lint needs its own `[workspace.lints]` entry, and why
  it needs **no `priority` key**: `priority` only matters when a group and one of its own members
  disagree, and `inline_always` is not a member of `clippy::all`.
- **Lint-as-policy** — encoding "you may, but you must show the measurement" as a workspace `deny`
  plus a documented site-local `#[allow]`, rather than as a convention nobody enforces.

## Read first

- [`opt-inline-always-rare`](../../../.claude/skills/rust-skills/rules/opt-inline-always-rare.md) —
  take its Bad/Good contrast (annotating everything vs one profiled `Hasher::write`) and its
  "Measuring Inline Impact" section. The rule's own position is that `#[inline(always)]` is
  legitimate **only** with a measurement; this PR makes that literal.
- `Cargo.toml:10-21` — `[workspace.lints.rust] warnings = "deny"`,
  `[workspace.lints.clippy] all = "deny"`, and the PR 7.7 comment at `:17-19` explaining that
  `unwrap_used`/`expect_used` are `restriction` lints outside `all`, "so no `priority` juggling is
  needed". Your new line follows exactly that pattern and that comment style.
- Any member manifest, e.g. `crates/common/Cargo.toml` — the `[lints] workspace = true` block that
  makes a root-level lint reach the crate. All six members declare it; you do not edit any of them.
- `docs/implementation/phase-16-rust-codegen-opt/pr-16.3-opt-inline-small.md` § "Definition of Done"
  — the sibling PR whose eleven `#[inline]` attributes this lint fences.
- `docs/benchmarks.md` § "History" — where an exception's justifying measurement must live.

## Scope

**In scope**

- One line in `[workspace.lints.clippy]`: `inline_always = "deny"`, with a comment recording that
  it is pedantic (hence not covered by `all`, hence no `priority`), and naming the escape hatch.
- Verify the escape hatch works: a site-local `#[allow(clippy::inline_always)]` with a comment
  citing a `docs/benchmarks.md` measurement compiles cleanly.
- Verify the deny bites: a temporary `#[inline(always)] fn` in any member fails clippy.

**Explicitly deferred** (do *not* build these here)

- Adding `#[inline(always)]` anywhere. This PR touches **no crate source at all**.
- Promoting any other pedantic or nursery lint. `doc_markdown` (203 sites), `must_use_candidate`
  (109), `use_self` (145) and the rest of the PR 8.5 sweep belong to Phase 33 (`lint-*`).
- Adding `clippy::missing_inline_in_public_items` (PR 16.3 already declined it: it would demand the
  attribute on all 347 public functions).
- A `[lints]` block in any member manifest — they already inherit.

**Conflict — a blanket deny would over-block the rule.** `opt-inline-always-rare` explicitly
*permits* `#[inline(always)]` for hot paths proven by profiling; denying it outright would forbid
something the rule endorses. **Resolution:** deny at the workspace level and allow the exception
**site-locally**, with a comment citing the criterion delta recorded in `docs/benchmarks.md`. That
is the same measured-exception shape PR 7.7 used for `unwrap_used`/`expect_used` — which are also
outside `clippy::all` and also needed no `priority` juggling. The policy is not "never"; it is
"never without a number in the repo".

## Hints & gotchas

- `clippy::inline_always` is **pedantic**, not `restriction` and not part of `clippy::all` — that is
  the whole reason this one line is needed. Adding `priority = -1` to `all` would be cargo-culting;
  the PR 7.7 comment at `Cargo.toml:17-19` already explains the rule, so match its wording.
- In `[workspace.lints.clippy]`, keys use **snake_case without the `clippy::` prefix**
  (`inline_always`, not `clippy::inline_always`). The prefix *is* required in a source-level
  `#[allow(clippy::inline_always)]`.
- All six members (`common`, `control`, `loader`, `pg-sink`, `pg-to-arrow`, `tests/e2e`) already
  carry `[lints] workspace = true`, so this line reaches every crate with no per-crate edit — and
  `--all-targets` extends it to benches, integration tests and the e2e harness.
- Prove the negative control on a **member crate**, not on a bench: `crates/pg-sink/benches/*.rs`
  carries a file-level `#![allow(clippy::unwrap_used, clippy::expect_used)]` and is easy to confuse
  with a lint that is not firing.
- Do not "pre-approve" an exception by adding an `#[allow]` with no measurement behind it. The
  policy this PR encodes is that the allow's comment must cite a `docs/benchmarks.md` § History row;
  an allow without one is exactly the drift the lint exists to catch.
- Tests in walrus are Go-style sibling `foo_test.rs` files, not inline `mod tests {}` — if you write
  a scratch function to test the deny, delete it again; this PR ships **only** the manifest line.
- No new dependency is involved. Anything you might add would have to clear `cargo deny`
  (advisories, the 8-license allow-list, bans) — for a one-line lint, never worth it.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it.

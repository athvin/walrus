# PR 16.11 — Decline profile-guided optimization with the measured evidence

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test · **Test packages:** common

> **Phase:** 16 — Rust compiler optimization · **Crates touched:** `common` *(plus a design note)* ·
> **Est. size:** S · **Depends on:** PR 16.10 · **Unlocks:** PR 16.12

No PGO scaffolding exists — searching the six shipped build/benchmark surfaces (`Cargo.toml`,
`.github/workflows/ci.yml`, both Dockerfiles, `justfile`, and `scripts/bench-e2e.sh`) for
`profile-generate`, `profile-use`, or `llvm-profdata` returns **0**. The roadmap task and source rule
necessarily name those literals as prose. More importantly, walrus has already *measured* why it
should stay that way. `docs/benchmarks.md` PR 5.6 ranks the **loader** as the system bottleneck, and
PR 5.5's
committed `EXPLAIN ANALYZE` shows its cost centres are DuckDB SQL operators —
`WINDOW` → `HASH_GROUP_BY` → `LEFT_DELIM_JOIN` — executing inside the bundled C++ engine, code a
Rust `-Cprofile-generate` run never observes. On the Rust side, PR 5.7 already recorded thin LTO as
an **honest null** (−0.8 % to +1 %) on the very micro-benches PGO would be judged on, and the sink
never backs up (`walrus_sink_inflight_bytes` = 0 at 6-7 k rows/s). After this merges,
`docs/implementation/notes/rust-skills/opt-pgo-profile.md` records that reasoning with its numbers and a
falsifiable re-open trigger, and `crates/common/tests/build_profile.rs` keeps the PGO string count
at 0 mechanically.

## Why — learning objectives

- **What PGO actually measures** — a three-pass instrument → profile → optimize cycle that feeds
  real branch/call frequencies back into codegen. It is only as good as the workload you profile,
  and it only sees the code the instrumented compiler emitted.
- **A Rust profile cannot reach an embedded C++ query engine** — `-Cprofile-generate` instruments
  rustc's codegen units. DuckDB's vendored C++ is compiled by the `duckdb` crate's build script, not
  by rustc; instrumenting it would mean separate `CFLAGS`/`CXXFLAGS` and a second profile merge —
  a different project.
- **walrus's measured bottleneck ranking** — loader ingest/transform first, sink second (PR 5.6);
  and within the loader, the window dedup, not the TOAST back-scan (PR 5.5). Optimising the Rust
  binary harder is not where the leverage is.
- **Declining with numbers, not adjectives** — a `D` verdict is only credible if it cites the
  measurement it rests on and names the measurement that would overturn it.

## Hints & gotchas

- **The ADR is a `.md`, so a `*.rs`-scoped grep will not see it** — but the *test file* now contains
  the strings `profile-generate`, `profile-use` and `llvm-profdata` as literals. That is safe only
  because the guard scans a fixed `include_str!` list; never widen it to a directory walk, and never
  add `crates/**` to the list, or it will flag itself.
- **`include_str!` on `justfile` and `scripts/bench-e2e.sh` is deliberate**: rustc records them as
  build inputs, so editing either recompiles and re-runs the test. A runtime `fs::read` would depend
  on the CWD and would not rebuild.
- **From `crates/common/tests/`, the workspace root is `../../../`.** Same trap as PR 16.10 — a
  wrong depth gives you a file that trivially passes.
- **Do not confuse this with the LTO decision.** PR 16.1 adopted `lto = "thin"`; PGO is a *separate*
  rule with a separate cost. The ADR should cite the LTO null as evidence about walrus's Rust hot
  paths, not as a reason to revisit LTO.
- **The strongest argument is the C++ boundary, not "we are I/O-bound".** Write it precisely:
  `-Cprofile-generate` instruments rustc's codegen units; DuckDB's engine is compiled by the
  `duckdb` crate's build script (the `bundled` feature, `Dockerfile.loader:10-12`), so it is outside
  the profile entirely. "I/O-bound" alone is the kind of adjective a `D` verdict must avoid.
- **State the re-open trigger as a measurement, not a feeling** — e.g. "a criterion bench showing a
  Rust-side hot path that accounts for a majority of end-to-end time in a `just bench-e2e`
  scenario". Anything vaguer will be re-litigated.
- Integration tests under `crates/common/tests/` get `unwrap`/`expect` re-allowed by `clippy.toml`,
  but `clippy --all-targets` still lints them under `deny(warnings)` — no unused imports or dead
  consts.
- Benches are **never a CI gate** (`docs/benchmarks.md:4-6`) and `just bench-e2e` is local-only; do
  not propose wiring either into CI as part of declining PGO.
- No new dependency, so `cargo deny` is unaffected. Do not touch any `.sql` file or the committed
  `.sqlx` offline cache — there is no Docker on this machine to regenerate it.

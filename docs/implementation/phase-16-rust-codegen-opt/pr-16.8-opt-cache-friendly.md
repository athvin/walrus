# PR 16.8 — Freeze hot-path type footprints with compile-time size guards

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 16 — Rust compiler optimization · **Crates touched:** `common`, `pg-sink`,
> `pg-to-arrow` · **Est. size:** S · **Depends on:** PR 16.7 · **Unlocks:** PR 16.9

`grep -rn 'size_of' crates tests | wc -l` measured **0** on the tree this phase was surveyed
against: nothing in walrus records, defends, or even *knows* how wide the per-row types are.
`parse_stream` returns a `Vec<Message>` (`crates/pg-sink/src/pgoutput/mod.rs:466`) whose element
width is set by the **widest** variant, `Relation` — which embeds a whole `PgRelation` (two
`String`s, a `Vec`, an oid, a replica identity) — so every hot `Insert` element in that vector pays
the per-table variant's width. `TupleValue` (`crates/common/src/pg_shape.rs:102`) is sized by
`Binary(Bytes)` (32 B) even though `Text(String)` (24 B) is the variant the `wide30` (30 cells/row)
and `text_heavy` benches actually exercise. After this merges those footprints are **frozen at
compile time** — adding a `String` to a guarded variant fails `cargo build` instead of silently
widening every element of a per-frame `Vec` — and the measured numbers, with their cache-line
arithmetic, are written into `docs/benchmarks.md` so the next optimisation argues from a number.

## Why — learning objectives

- **`size_of` in a `const` assertion is a zero-runtime-cost layout guard** — `const _: () =
  assert!(size_of::<T>() <= N, "…");` is evaluated by the compiler, needs no test binary, no
  dependency, and fails the *build* rather than a test run.
- **An enum is as wide as its widest variant (plus a discriminant, minus niches)** — which is why a
  rarely-constructed `Message::Relation` sets the price of every `Message::Insert` in the same
  `Vec`, and why `Bytes` (32 B) sets `TupleValue`'s width for text-only workloads.
- **walrus's per-frame and per-row footprints** — a `Vec<Message>` per walsender frame, a
  `Vec<TupleValue>` per row, a `Vec<Emit>` per relation; 30 cells/row is what `wide30` costs before
  a single heap `String` payload is touched.
- **Measure and freeze ≠ optimise** — this PR changes no layout. It converts an unknown into a
  documented number plus a tripwire, which is the precondition every later layout change needs.

## Scope

**In scope**

- **Measure first.** Get the real `size_of` for `pgoutput::Message`, `common::TupleValue` and
  `pg_to_arrow::batch::Emit` on the pinned 1.95.0 toolchain (see Hints for the one-line trick).
  Modelled expectations, to sanity-check against — *not* to hard-code: `Message` 88 B,
  `TupleValue` 40 B, `Emit` 1 B.
- **A compile-time guard for each of the three**, placed immediately below its type definition and
  gated `#[cfg(target_pointer_width = "64")]`:
  `const _: () = assert!(std::mem::size_of::<T>() <= N, "<why this width matters>");`
  The message must say *why* (per frame element / per row cell / per source column), not just repeat
  the number.
- **A short doc comment addition on each guarded type** pointing at the guard, so the next person to
  add a field reads the reason before they hit the compile error.
- **A `docs/benchmarks.md` section** — "Hot-path type footprints (PR 16.8)" — with a small table
  (type · measured bytes · how many per instance · per-row/per-frame arithmetic) and the cache-line
  reading: 64-byte lines, so `Message` at 88 B never packs two to a line, and a `wide30` row's
  `Vec<TupleValue>` is 30 × 40 B ≈ 1 200 B ≈ 19 lines *before* a single heap `String` payload is
  dereferenced. State the reference machine and toolchain, per the file's existing convention.

**Explicitly deferred** (do *not* build these here)

- **No AoS → SoA rewrite of `BatchBuilder`.** Its `Vec<Box<dyn ArrayBuilder>>` pointer-chase
  (`batch.rs:75`) stays exactly as is — replacing dyn dispatch with an enum is a Phase-19 trait
  question, not a layout tweak.
- **No `#[repr(C)]`, no `#[repr(align(64))]`, no manual padding, no field reordering.** This PR
  observes and freezes; it does not move a byte.
- **No cache-miss profiling.** `perf` is unavailable on the macOS M2 reference machine named in
  `docs/benchmarks.md`; do not add a profiling step you cannot run.
- **No boxing of any variant.** Shrinking `Message::Relation` belongs to
  `pr-11.10-mem-box-large-variant.md`.
- No new dependency — in particular **not** `static_assertions`; the built-in `const _: () =
  assert!(…)` form is enough.

**Conflicts — resolve them this way, do not apply the rule blindly.**

1. **`mem-box-large-variant` (PR 11.10) owns the fix; this PR owns the measurement.** If 11.10 has
   already boxed the oversized `Message` variant, do **not** undo it: record the *post-boxing*
   number and set the guard to it. The guard is a ratchet, always against the tree as merged.
2. **`anti-premature-optimize` / `perf-profile-first` (both from this same corpus) forbid layout
   churn without a measurement.** That is exactly why the deferred list above is so wide: the only
   artifact here is a number, a guard and a paragraph.
3. **`mem-assert-type-size` (PR 11.2) overlaps directly.** It lands `const _: () = assert!(size_of
   ::<T>() == N, …)` — an **exact-equality** ratchet — for `TupleValue`, `PgColumn`, `PgRelation`,
   `Message`, `DecodeError` and `pg_to_arrow::Error`. Resolution:
   - If those guards already exist: **keep them verbatim.** Do *not* loosen `==` into `<=` — the
     equality form is strictly stronger. This PR's delta is then (a) the **`Emit`** guard, which
     11.2 does not cover, (b) the doc comments tying the numbers to the per-frame/per-row
     containers, and (c) the `docs/benchmarks.md` footprint section, which 11.2 explicitly does not
     write.
   - If they do not exist (11.2 not merged): add `Message` and `TupleValue` guards here in the
     `<= N` ceiling form, and say in the guard message that 11.2 may tighten them to `==`.
   Either way the end state is **≥ 3 `size_of` guards covering `Message`, `TupleValue` and `Emit`**.
   Say which case you are in, in the PR body.

## Hints & gotchas

- **How to read the size without a test.** Put `const _: [(); 0] = [(); std::mem::size_of::<Message
  >()];` in the file and compile: the error says *"expected an array with a fixed size of 0
  elements, found one with 88 elements"* — that number is the size. Delete the probe, write the real
  guard. (A `#[test] fn sizes()` with `--nocapture` also works, but leave no test behind: a const
  assertion already fails the build, and a test would duplicate the guard and fail later.)
- **`size_of` is in the prelude since Rust 1.80**, so bare `size_of::<T>()` compiles on the pinned
  1.95.0. Spell it `std::mem::size_of::<T>()` anyway — it is what the DoD greps for and what PR 11.2
  used, so the two guard families stay greppable together.
- **`Emit` is private to `batch.rs`.** The guard must live in that file; you cannot assert on it
  from a `tests/` integration target. Do not make the type `pub` to satisfy a guard.
- **Don't gate `Emit` on pointer width** — it contains no pointers, so its size is the same on any
  target and a `#[cfg]` would just be noise. Gate the two that embed `String`/`Bytes`/`Vec`.
- **`<=` vs `==`.** This ticket's ceilings are `<=` so a *shrink* (e.g. PR 11.10 boxing a variant)
  does not spuriously fail. If PR 11.2's `==` guards are already there, leave them: `==` is the
  stronger ratchet, and mixing the two forms is fine as long as you say so in the PR body.
- **Adding a variant is as dangerous as adding a field.** `Message` is `#[non_exhaustive]`
  (`mod.rs:41`) — the guard is the only thing that will notice a wide new variant.
- **The inline size is not the whole cost.** A `TupleValue::Text(String)` is 40 B inline plus a heap
  allocation the CPU must chase; say so in the benchmarks section rather than implying the guard
  bounds memory use.
- **`clippy::all` + `warnings` are already `deny`** (`Cargo.toml:12-16`) and `unwrap`/`expect` are
  denied in production — none of this diff needs either. `rustfmt` will reflow long `assert!`
  messages; run `cargo fmt` before `cargo fmt --check`.
- **Do not touch `.sql` files or the committed `.sqlx` offline cache** — there is no Docker on this
  machine to regenerate it. Nothing here should go near them.
- Benches are **never a CI gate** (`docs/benchmarks.md:4-6`); adding a section to that file does not
  make one. Do not wire a size check into a bench.

# PR 16.3 — Add `#[inline]` to the cross-crate hot-path accessors

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 16 — Rust compiler optimization · **Crates touched:** `common`, `pg-sink` ·
> **Est. size:** S · **Depends on:** PR 16.2 · **Unlocks:** PR 16.4

**Zero `#[inline]` attributes exist anywhere in walrus** — `grep -rn '#\[inline' crates tests | wc -l`
= **0**. That is a real gap for exactly two families of function. `common::Lsn::new` and
`Lsn::as_u64` (`crates/common/src/lsn.rs:26, 31`) are one-line `const fn` accessors over a `u64`
with **28 production call sites in the other four crates**; and `Reader`'s primitives
(`crates/pg-sink/src/pgoutput/reader.rs:17-123`) run once per wire field inside the
**236 ns/row `parse_tuple`** bench. Today cross-crate inlining of both rests entirely on
`lto = "thin"` — best-effort, and **absent from the dev/test profile** — because without `#[inline]`
a non-generic function's body is simply not available to a downstream crate. Both criterion targets
link the libraries across a crate boundary (`crates/pg-sink/benches/decode.rs:14`,
`crates/pg-to-arrow/benches/batch.rs:16`), so the benches see the same boundary the shipped binaries
see. After this PR there are **≥ 10** `#[inline]` attributes, every one on a body of ≤ 5 lines, and
the re-measured `parse_tuple` / `append_row` medians — **including a null result** — are recorded in
`docs/benchmarks.md`.

## Why — learning objectives

- **`#[inline]` vs `#[inline(always)]` vs no attribute** — and the concrete mechanism: a non-generic
  function's MIR is only exported to downstream crates when it is `#[inline]` (or generic, or LTO
  reaches it). "The compiler usually decides well" is true *within* a crate and false across one.
- **walrus's criterion benches are separate crates linking the libs** — `benches/decode.rs` is its
  own compilation unit `use`ing `pg_sink::pgoutput::{…}`, so a bench number here reflects the crate
  boundary the `pg-sink` binary pays, not an artificially flat single-crate view.

- [`opt-inline-small`](../../../.claude/skills/rust-skills/rules/opt-inline-small.md) — take the

  bloats every call site. The ≤ 5-line rule in the DoD below is that caution made mechanical.
- `crates/common/src/lsn.rs:21-34` — `Lsn::ZERO`, `Lsn::new`, `Lsn::as_u64`. Note `ZERO` is an
  associated **const**, not a function; it has no call to inline.
- `crates/pg-sink/src/pgoutput/reader.rs` (all of it, post-PR-16.2) — the ten `pub` readers and

- `crates/pg-sink/benches/decode.rs:1-20, 215-230` — `bench_parse_tuple`, and the `use

  caller.
- `crates/pg-to-arrow/benches/batch.rs:1-20` — the same shape for `append_row`.
- `docs/benchmarks.md` § "How to re-run" and § "History" — the exact commands and the format each
  measured delta is written in (PR 5.7's entry is the model: a table plus an honest verdict).
- `Cargo.toml:71-77` — the `lto = "thin"` comment; `#[inline]` is what makes that best-effort
  cross-crate inlining a guarantee rather than a hope.

## Scope

**In scope**

- `#[inline]` on `common::Lsn::new` and `common::Lsn::as_u64`.
- `#[inline]` on the small `pub` methods of `pg_sink::pgoutput::Reader`: `new`, `remaining`, `peek`,
  `byte1`, `int16`, `int32`, `int64`, `take`, `lsn`. (Eleven attributes in total with the two above.)
- Re-run `cargo bench -p pg-sink --bench decode` and `cargo bench -p pg-to-arrow --bench batch`,
  and append a PR 16.3 entry to `docs/benchmarks.md` § History with the before/after medians for
  `parse_tuple` and `append_row` — **including if the delta is within noise**. PR 5.7's "honest
  null" entry is the precedent and the required tone.

**Explicitly deferred** (do *not* build these here)

- `#[inline(always)]` anywhere. PR 16.4 denies `clippy::inline_always` workspace-wide precisely so
  this PR's work cannot drift into it.
- Enabling `clippy::missing_inline_in_public_items`. That restriction lint would demand the
  attribute on all **347** public functions in the tree — the exact binary/instruction-cache bloat
  this rule's Cautions section warns against.
- `Reader::string` and `common::Lsn`'s `FromStr` / `Display` / serde impls — all multi-line, all
  called once per field at most, none worth the code-size trade.
- `#[cold]` / `#[inline(never)]` — PRs 16.5 and 16.6.

## Skeleton

```rust
// crates/common/src/lsn.rs
impl Lsn {
    /// The zero LSN — orders below every nonzero LSN.
    // (An associated `const`, not a function: there is no call site to inline.)
    pub const ZERO: Lsn = Lsn(0);

    /// Wrap a raw `u64` WAL position.
    ///
    /// `#[inline]` because `common` is a library crate: without it the body of this non-generic
    /// `const fn` is not exported to `pg-sink` / `control` / `loader` / `pg-to-arrow`, and the
    /// 28 cross-crate call sites pay a real call for a `mov`. `lto = "thin"` may recover it —
    /// `#[inline]` makes it independent of the profile (the dev/test profile has no LTO at all).
    #[inline]
    pub const fn new(raw: u64) -> Self {
        Lsn(raw)
    }

    /// The raw `u64` WAL position.
    #[inline]
    pub const fn as_u64(self) -> u64 {
        self.0
    }
}
```

## Hints & gotchas

- `#[inline]` is a **hint with a mechanism**: it exports the function's MIR so downstream crates
  *can* inline it. It is not a command — do not reach for `#[inline(always)]` when a number
  disappoints; PR 16.4 is about to make that a hard error.
- You cannot put `#[inline]` on `Lsn::ZERO`. It is an associated const; `rustc` rejects the
  attribute there. Record that in a comment rather than silently skipping it.
- `const fn` and `#[inline]` compose fine — `Lsn::new`/`as_u64` keep `const`.
- Benches are **never a CI gate** (`docs/benchmarks.md:4-6`); CI only compile-checks the bench
  targets through `clippy --all-targets`. Run them yourself on a quiet machine via `just bench`, and
  compare **deltas on the same machine**, never absolute numbers across machines.
- Criterion's `change:` line is only meaningful if `target/criterion/` still holds the previous run.
  Measure `main` first, then the branch, in the same working tree.
- `pg-sink`'s decode loop and `benches/decode.rs` are both outside `pg_sink::pgoutput`'s codegen
  unit in a **dev/test** build (no LTO in that profile), which is why the attribute matters even
  though `lto = "thin"` covers release.
- `unwrap`/`expect` are `deny` in production; the benches carry a file-level
  `#![allow(clippy::unwrap_used, clippy::expect_used)]` (`benches/decode.rs:1`) because they are
  `harness = false` targets, not `cfg(test)`. Do not copy that allow into `src/`.
- `clippy::all` and `warnings` are already `deny` workspace-wide, so a stray `#[inline]` on a
  non-existent item fails the build immediately — good.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it.

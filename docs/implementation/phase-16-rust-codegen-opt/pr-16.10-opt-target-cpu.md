# PR 16.10 — Reject target-cpu=native and guard against RUSTFLAGS drift

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** evidence
> **Gates:** fmt,clippy,test · **Test packages:** common

> **Phase:** 16 — Rust compiler optimization · **Crates touched:** `common` *(plus a design note)* ·
> **Est. size:** S · **Depends on:** PR 16.9 · **Unlocks:** PR 16.11

There is no `.cargo/config.toml` in this repo, and
`grep -rn 'target-cpu\|RUSTFLAGS\|rustflags' --include='*.toml' --include='*.yml'
--include='Dockerfile*'` returns **0** — nothing sets a target CPU today. Adopting
`target-cpu=native` here would be structurally wrong, not merely unhelpful: both release binaries
are compiled inside `rust:1.95.0-slim-bookworm` (`deploy/docker/Dockerfile.pg-sink:18`,
`Dockerfile.loader:17`) and shipped on `debian:bookworm-slim`
(`Dockerfile.pg-sink:42`, `Dockerfile.loader:44`), so "native" means *the builder's* ISA baked into
an image that runs somewhere else — a `SIGILL` on any older host. CI runs on `ubuntu-latest` runners
while the `docs/benchmarks.md` reference machine is an Apple M2, so the two would not even agree on
which "native" they mean; and any `RUSTFLAGS` change invalidates the cargo-chef dependency layer
both Dockerfiles are built around (`Dockerfile.loader:38`, `Dockerfile.pg-sink:36`) — the layer that
otherwise avoids a ~15-20 min DuckDB C++ rebuild. After this merges the rejection is recorded in
`docs/implementation/notes/rust-skills/opt-target-cpu.md` **with a re-open trigger**, and
`crates/common/tests/build_profile.rs` keeps the count at 0 mechanically rather than by habit.

## Why — learning objectives

- **`-C target-cpu` and ISA baselines** — the default x86-64 baseline is roughly SSE2-era;
  `target-cpu=native` emits whatever the *build host* supports (AVX2, AVX-512, …). A binary built
  that way is unshippable in a container: the runtime host is not the build host, and the failure
  mode is an illegal-instruction crash, not a slowdown.
- **Where a build flag actually lives** — `.cargo/config.toml`, `RUSTFLAGS`, or a `[target.…]`
  table. Guarding "we set no target CPU" means guarding all three surfaces, not one file.
- **walrus's cargo-chef layered image build** — `cargo chef prepare` distils a `recipe.json`,
  `cargo chef cook` builds only dependencies into a cached layer keyed on it, and *any* change to
  the compilation environment (including `RUSTFLAGS`) busts that layer and re-pays the
  bundled-DuckDB C++ compile.
- **How to decline a rule honestly** — cite the structural reason and the measured zero, then write
  down the exact condition that would reverse the decision, so it can be revisited on evidence.

## Hints & gotchas

- **The test file itself contains the forbidden strings.** That is safe *only* because it scans
  `include_str!`ed files by name, never a directory glob and never itself. Do not "generalise" it
  into a repo-wide walk — it will trip on its own source and on this task file.
- **`include_str!` paths are relative to the file containing the macro**, so from
  `crates/common/tests/` the workspace root is `../../../`. `env!("CARGO_MANIFEST_DIR")` is
  `crates/common`, so the root is `join("../..")`. Two different depths — get them right or the test
  passes vacuously against the wrong file.
- **Only `include_str!` makes CI notice an edit at compile time**; the `.cargo/config.toml` check is
  necessarily a runtime `Path::exists`. Root it at `CARGO_MANIFEST_DIR` (absolute) so it does not
  depend on where `cargo test` was invoked from, and check the **legacy** `.cargo/config` spelling
  too — cargo still honours it.
- **`rustflags` is lower-case in `.cargo/config.toml` and upper-case as an env var.** Check both
  spellings; a case-insensitive match would also fire on prose, which you do not want.
- **There is exactly one workflow file** (`.github/workflows/ci.yml`). If a second one is ever added
  this guard silently stops covering it — say so in the ADR so the next author knows to extend
  `BUILD_SURFACES`.
- **Do not add `justfile` or `scripts/*.sh` to the surface list here.** They are developer
  convenience, not the shipped build, and widening scope makes the guard brittle; PR 16.11 handles
  the script surface for its own (PGO) strings.
- Integration tests under `crates/common/tests/` get `unwrap`/`expect` re-allowed by `clippy.toml`,
  but `clippy --all-targets` still lints them under `deny(warnings)` — keep the file clean (no
  unused import, no dead const).
- **Never adopt "just for local dev".** A `.cargo/config.toml` with `target-cpu=native` would also
  change what `cargo bench` measures, silently invalidating every number in `docs/benchmarks.md`.
- No new dependency, so `cargo deny` is unaffected. Do not touch any `.sql` file or the committed
  `.sqlx` offline cache — there is no Docker on this machine to regenerate it.

# PR 13.2 — Annotate pure accessors with must_use and deny clippy::must_use_candidate

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** common,control,loader,pg-sink,pg-to-arrow

> **Phase:** 13 — Rust API design · **Crates touched:** `common`, `control`, `loader`, `pg-sink`,
> `pg-to-arrow` · **Est. size:** L ·
> **Depends on:** PR 13.1 · **Unlocks:** PR 13.3

There is **not a single `#[must_use]`** in the walrus production tree, while clippy's pedantic
`must_use_candidate` flags **110** unique sites — 104 of them in the five member crates (pg-sink 50,
pg-to-arrow 23, loader 15, common 9, control 7), the rest in the e2e harness lib. The first three on
the list are `Error::is_terminal`, `Error::is_transient` and `Error::exit_code`: pure classifiers
whose *entire* purpose is the value they return, and calling one for effect is always a bug. After
this PR every such function is annotated and `must_use_candidate = "deny"` keeps the next pure
accessor from shipping unannotated.

## Why — learning objectives

- **`#[must_use]` on functions vs on types** — annotating a function warns when *that call's* result
  is dropped; annotating a type warns wherever a value of it is dropped. This ticket does functions
  only, which is the narrower and safer half.
- **Custom `#[must_use]` messages** — `#[must_use = "…"]` replaces the generic compiler note with the
  reason, and the reason is what a reader needs (`"classification is the whole point — calling this
  for effect does nothing"`).
- **Clippy lint levels and groups** — `must_use_candidate` lives in `clippy::pedantic`, *not* in
  `clippy::all`, so promoting it to `deny` in `[workspace.lints.clippy]` needs no group-priority
juggling and turns a 110-item cleanup into a standing gate.
- **Which walrus computations are pure** — `retention_floor`, `is_terminal`, `over_ceiling`,
  `largest_open` compute and return; `add`, `release`, `tick` mutate. Only the first family gets the
  attribute.

  be consistent.

**Explicitly deferred** (do *not* build these here)

- Does **not** add `#[must_use]` to any *type* — only to functions. Marking a type is a much broader
  contract and no walrus type is an RAII guard or a lazy iterator today.
- Does **not** enable `clippy::return_self_not_must_use`: no `-> Self` chained method exists yet, so
  the lint would report 0. That is PR 13.9's job, after PR 13.8 introduces the builder.
- Does **not** touch `clippy::double_must_use`, and does **not** annotate functions returning
  `Result<…>` / `Option<…>` — those types are already `#[must_use]` and a second attribute is exactly
  what `double_must_use` exists to catch.
- No signature, visibility or behaviour changes. An attribute-only diff plus one `Cargo.toml` line.

## Hints & gotchas

- Generate the site list, do not hand-hunt it:
  `cargo clippy --all-targets --all-features -- --force-warn clippy::must_use_candidate`. Clippy
  prints the exact `file:line` and the suggested attribute for each.
- `must_use_candidate` only fires on **public** functions that are side-effect free. If clippy did
  not flag it, do not annotate it — an unwanted `#[must_use]` on a side-effecting API just trains
  people to write `let _ = …`.
- Attribute placement: `#[must_use]` goes **below** the doc comment and above the `pub fn`. Putting
  it above the `///` lines compiles but reads wrong and `cargo fmt` will not move it for you.
- `#[must_use]` on a `-> Result<…>` fn is `clippy::double_must_use` — `Result` and `Option` are
  already `#[must_use]` in std. Check the return type before annotating.
- `must_use_candidate` is `clippy::pedantic`, **not** part of `clippy::all`, so adding it next to
  `all = "deny"` needs no `priority = -1`. (Contrast PR 13.4, where `from_over_into` *is* in
  `clippy::all` and does need it.)
- A `#[must_use]` fn is still callable for effect with `let _ = f();` — that is the escape hatch, and
  if you find yourself writing it in production, the annotation was probably wrong.
- Do **not** touch any `.sql` file or the `.sqlx` offline cache — there is no Docker on this machine
  to regenerate it, and this PR needs neither.
- `unwrap()` / `expect()` are `deny` in production; `clippy::all` and `warnings` are already `deny`.
- Unit tests are Go-style siblings (`foo.rs` → `foo_test.rs`); no test changes are expected here,
  since sibling test modules are `#[cfg(test)]` and the lint targets the public API.

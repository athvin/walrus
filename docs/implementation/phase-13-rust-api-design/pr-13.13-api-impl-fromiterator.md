# PR 13.13 — Make RelationCache a real collection: FromIterator, Extend, IntoIterator

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 13 — Rust API design · **Crates touched:** `pg-sink` · **Est. size:** M ·
> **Depends on:** PR 13.12 · **Unlocks:** PR 13.14

Production contains **zero** `FromIterator` / `Extend` / `IntoIterator` impls. `RelationCache`
(`crates/pg-sink/src/relcache.rs:35`) is nonetheless a genuine collection: it wraps
`HashMap<(u32, i64), Arc<CachedRelation>>` and already exposes `len` (:63) and `is_empty` (:67) —
the two methods the API guidelines pair with the iterator traits. Because those traits are missing,
bootstrap hydration is a hand-rolled `for` loop over an owned `Vec` (`hydrate`, :88) and both
lookup helpers — `latest_for` (:46) and `oid_for` (:56) — reach straight into the private `by_key`
map because there is no iteration API to reach through. This PR implements the full **C-COLLECT**
set (5 impls), rewrites `hydrate` as *fallible decode → infallible `extend`*, and lets the two
lookups iterate through the public surface. `hydrate`'s error type and every rendered message stay
byte-identical.

## Why — learning objectives

- **The C-COLLECT contract** — a collection owes callers `FromIterator<T>` (so `.collect()` works),
  `Extend<T>` (so batch insert is one call, and `collect` can reuse it), and `IntoIterator` for
  **all three** reference forms: `Self`, `&Self`, `&mut Self`.
- **Infallible traits over a fallible source** — `FromIterator`/`Extend` cannot return `Result`, so
  the JSON decode that *can* fail must happen before the trait boundary, not inside it.
- **Deriving the key from the value** — `by_key`'s key `(oid, schema_version)` is a projection of
  `CachedRelation`, which is why `FromIterator<CachedRelation>` (not `FromIterator<(K, V)>`) is the
  honest item type for this cache.
- **Why the relation cache is keyed on `(oid, schema_version)`** — a DDL bump creates a *new* entry
  rather than mutating the old one, so in-flight batches at the previous version still resolve; and
  the whole cache must be rebuildable from `schema_registry` at restart.

**In scope**

- `impl FromIterator<CachedRelation> for RelationCache` — collect into a fresh cache, keying each
  entry by `(relation.oid, schema_version)`.
- `impl Extend<CachedRelation> for RelationCache` — batch insert, with `reserve` on the inner map
  from the iterator's size hint.
- `impl IntoIterator for RelationCache`, `for &RelationCache`, and `for &mut RelationCache` —
  yielding `Arc<CachedRelation>`, `&Arc<CachedRelation>`, `&mut Arc<CachedRelation>` respectively
  (values, not `(key, value)` pairs — the key is a projection of the value).
- An inherent `iter()` delegating to `(&self).into_iter()`. This is the `name-iter-convention`
  pairing **and** it keeps `clippy::into_iter_on_ref` (style, i.e. inside the already-denied
  `clippy::all`) quiet at the new call sites.
- Rewrite `hydrate` as: decode every row into a `Vec<CachedRelation>` via
  `collect::<Result<Vec<_>, RelationError>>()?`, then `self.extend(decoded)`.
- Rewrite `latest_for` and `oid_for` to iterate the public API instead of `self.by_key`.
- New cases in `crates/pg-sink/src/relcache_test.rs` covering `collect`, `extend`, the three
  `IntoIterator` forms, and the unchanged `RelationError::Hydrate` message.

**Explicitly deferred** (do *not* build these here)

- No change to the `(u32, i64)` key type — the `EpochNo`/`SchemaVersion` newtype slices are their
  own PRs, and this ticket must not pre-empt them.
- No `IndexMap`/`ahash` swap. Neither is a dependency, both would need `cargo deny` review, and
  `anti-premature-optimize` applies: there is no benchmark showing the `HashMap` is a problem.
- No iteration API on `BatchRouter` or `StreamDemux` — they are routers keyed by liveness, not
  collections.
- No change to `upsert_from_relation`'s signature or to `is_internal_table`.

**Conflict to resolve explicitly:** `FromIterator` and `Extend` are **infallible** by signature,
but hydration *can* fail — a malformed `columns` snapshot is a real, terminal condition. Do **not**
"resolve" this by panicking inside `extend`, by silently skipping bad rows, or by changing
`hydrate` to return `()`. The required split is: the fallible `serde_json` decode plus
`build_arrow` stay in `hydrate` and produce a `Vec<CachedRelation>`; only the infallible insert is
delegated to `Extend`. `hydrate`'s signature, error type (`RelationError`), and the exact
`RelationError::Hydrate` message must not change.

// crates/pg-sink/src/relcache.rs — `hydrate`, rewritten. The fallible half stays here; only the
// insert is delegated. The `RelationError::Hydrate` string is unchanged, character for character.
pub fn hydrate(&mut self, rows: Vec<control::RegistryRow>) -> Result<(), RelationError> {
    let decoded: Vec<CachedRelation> = rows
        .into_iter()
        .map(|row| {
            let relation: PgRelation = serde_json::from_value(row.columns).map_err(|e| {
                RelationError::Hydrate(format!(
                    "{}.{}: columns snapshot is not a PgRelation: {e}",
                    row.source_schema, row.source_table
                ))
            })?;
            let arrow_schema = build_arrow(&relation)?;
            Ok(CachedRelation {
                arrow_schema,
                descriptors: row.descriptors,
                schema_version: row.schema_version,
                relation,
            })
        })
        .collect::<Result<Vec<_>, RelationError>>()?;
    todo!("self.extend(decoded); Ok(())")
}

## Hints & gotchas

- `HashMap`'s value iterators are the associated types you want:
  `hash_map::IntoValues<K, V>`, `hash_map::Values<'a, K, V>`, `hash_map::ValuesMut<'a, K, V>`.
  Spell them out rather than reaching for `impl Iterator` — `IntoIterator::IntoIter` is an
  associated *type*, so RPITIT does not apply here.
- Yield **values**, not `(key, value)` pairs. The key is `(relation.oid, schema_version)`, both of
  which are already readable off `CachedRelation`, so a pair item would just be redundancy the
  caller has to destructure.
- `clippy::into_iter_on_ref` is a **style** lint, and `clippy::all` is already `deny` at the
  workspace level — so `(&cache).into_iter()` in production code will be flagged once an inherent
  `iter()` exists. Call `self.iter()` inside `latest_for`/`oid_for`; the explicit
  `(&cache).into_iter()` form is fine *in the test*, where it is the thing under test.
- Behaviour change worth calling out in the PR body: `hydrate` is now all-or-nothing. Previously a
  malformed row left the earlier rows already inserted; now the `collect::<Result<Vec<_>, _>>()?`
  bails before any insert. Both are terminal at the call site (`main.rs:238` `?`s it), so no
  caller can observe the difference — but say so rather than leaving a reviewer to work it out.
- `Extend::extend` takes `&mut self`, so `FromIterator::from_iter` can build a
  `RelationCache::default()` and delegate — that is the standard shape, and `RelationCache` already
  derives `Default`.
- `size_hint().0` is a *lower* bound; using it for `reserve` is a hint, never a correctness
  requirement. Do not `unwrap` the upper bound.
- Tests live in the **sibling** `relcache_test.rs` wired by `#[cfg(test)] #[path = …] mod tests;`
  at `relcache.rs:149-151` — never add an inline `mod tests {}`.
- `unwrap`/`expect` are denied in production by `[workspace.lints]`; `clippy.toml` re-allows them
  in tests, which is why the test skeleton above may `.unwrap()` freely.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it. Nothing in this PR should need to.

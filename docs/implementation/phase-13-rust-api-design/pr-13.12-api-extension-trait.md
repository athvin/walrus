# PR 13.12 — Add a DuckDB result extension trait to kill 29 hand-written `map_err` closures

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** loader

> **Phase:** 13 — Rust API design · **Crates touched:** `loader` ·
> **Est. size:** M · **Depends on:** PR 13.11 · **Unlocks:** PR 13.13

walrus defines exactly **2** traits in production — `pg_sink::batch::Clock` (`batch.rs:22`) and the
private `ArrowNumBuilder` — and **zero** extension traits, even though it consumes one heavily:
`anyhow::Context`, at 99 `.context(` call sites. The cost of not having its own shows up in the
loader, where `.map_err(|e| LoaderError::Duck(format!("… {e}")))` is repeated at **29** sites
(`duck.rs` 16, `compaction.rs` 5, `ddl.rs` 4, `phase_b.rs` 3, `transform.rs` 1) — part of 40
`map_err(|e| LoaderError::…)` closures overall. Every one of those 29 renders the same shape,
`"{what}: {e}"`, which is precisely the `Context`/`with_context` pattern the loader already imitates
by hand. This PR introduces `crates/loader/src/duck_ext.rs` with `DuckResultExt`, converts all 29,
and pins the rendered message text with a sibling test so the refactor is provably behaviour-free.

## Why — learning objectives

- **Extension traits and the orphan rule** — you cannot `impl` a foreign trait on a foreign type,
  but a **local** trait on `Result<T, duckdb::Error>` is fine; that asymmetry is the whole idiom.
- **Blanket impls over a foreign `Result`** — `impl<T> DuckResultExt<T> for Result<T, duckdb::Error>`
  covers every `T` at once, so 29 differently-typed call sites need one impl.
- **The `…Ext` naming convention and eager vs lazy context** — `duck(&str)` for constants,
  `duck_with(|| …)` for formatted messages, mirroring `anyhow::Context::context` /
  `with_context` so the closure never runs on the success path.
- **The loader's DuckDB error surface** — every failure must name the table (or URI) it was
  operating on, because a `LoaderError::Duck` is terminal and lands in `kubectl logs` as the only
  clue about which of N per-table `.duckdb` files broke.

## Skeleton

```rust
// crates/loader/src/duck_ext.rs — NEW FILE.
//! `DuckResultExt` — the loader's `anyhow::Context` for `duckdb::Error`.
//!
//! Every DuckDB failure in this crate is terminal and must name *what* it was doing, because a
//! `LoaderError::Duck` in `kubectl logs` is the only clue about which per-table `.duckdb` broke.
//! Before this module that convention lived in 29 copies of the same `map_err` closure; now the
//! rendered shape `"{what}: {e}"` exists exactly once, in [`duck_err`].

use crate::error::LoaderError;

/// The single place the message shape lives. Kept `pub(crate)` for the one site that is a direct
/// `Err(...)` rather than a `map_err` (`compaction::full_rebuild`).
pub(crate) fn duck_err(what: &str, e: &duckdb::Error) -> LoaderError {
    LoaderError::Duck(format!("{what}: {e}"))
}

/// Attach "what we were doing" to a `duckdb::Error`, turning it into a [`LoaderError::Duck`].
pub trait DuckResultExt<T> {
    /// For a constant description: `.duck("configure S3")`.
    fn duck(self, what: &str) -> Result<T, LoaderError>;

    /// For a formatted description; the closure runs only on the error path:
    /// `.duck_with(|| format!("prune {}_raw", t.table()))`.
    fn duck_with(self, what: impl FnOnce() -> String) -> Result<T, LoaderError>;
}

impl<T> DuckResultExt<T> for Result<T, duckdb::Error> {
    fn duck(self, what: &str) -> Result<T, LoaderError> {
        self.map_err(|e| duck_err(what, &e))
    }

    fn duck_with(self, what: impl FnOnce() -> String) -> Result<T, LoaderError> {
        self.map_err(|e| duck_err(&what(), &e))
    }
}
```

```rust
// crates/loader/src/duck_ext_test.rs — NEW FILE.
use super::*;

/// A real `duckdb::Error` — cheap, no filesystem.
fn a_duck_error() -> duckdb::Error {
    let conn = duckdb::Connection::open_in_memory().unwrap();
    conn.execute_batch("SELECT no_such_function();").unwrap_err()
}

#[test]
fn duck_renders_exactly_what_the_hand_written_closure_did() {
    let e = a_duck_error();
    // The 29 replaced closures all rendered `LoaderError::Duck(format!("{what}: {e}"))`.
    let expected = LoaderError::Duck(format!("configure S3: {e}")).to_string();
    let got = Err::<(), duckdb::Error>(e)
        .duck("configure S3")
        .unwrap_err()
        .to_string();
    assert_eq!(got, expected);
}

#[test]
fn duck_with_matches_the_table_scoped_shape() {
    let e = a_duck_error();
    let expected = LoaderError::Duck(format!("prune orders_raw: {e}")).to_string();
    let got = Err::<(), duckdb::Error>(e)
        .duck_with(|| format!("prune {}_raw", "orders"))
        .unwrap_err()
        .to_string();
    assert_eq!(got, expected);
}

#[test]
fn duck_with_does_not_format_on_success() {
    let mut called = false;
    let ok: Result<u8, duckdb::Error> = Ok(7);
    let v = ok
        .duck_with(|| {
            called = true;
            String::from("never rendered")
        })
        .unwrap();
    assert_eq!(v, 7);
    assert!(!called, "the message closure must not run on the Ok path");
}
```

## Hints & gotchas

- **Audit the 29 message strings before converting, not after.** All of them render `"{what}: {e}"`
  today — verify each one really does (`grep -n 'LoaderError::Duck(format!' -A2`). If one has a
  different shape, it cannot go through `duck`/`duck_with` without changing output, and the probe
  will not reach 0 until you find another way to express it.
- **`compaction.rs:51` is not a `map_err`.** It is a `return Err(...)` inside an `if let Err(e)` that
  must roll back and honour the cancellation token first. That is why `duck_err` is a free function
  and not just an inherent helper on the trait — do not try to force that site through `.duck()`.
- An extension trait's methods are only visible where the trait is **in scope**. Each of the five
  consumer modules needs its own `use crate::duck_ext::DuckResultExt;`; `compaction.rs` also needs
  `duck_err`.
- `duck(what: &str)` evaluates its argument eagerly. Use it only for string **literals**; anything
  built with `format!` must go through `duck_with` or you have moved the allocation onto the hot
  success path — which is the opposite of the point.
- The orphan rule is satisfied because the *trait* is local. Do not be tempted to
  `impl From<duckdb::Error> for LoaderError` instead: that would let `?` convert silently and
  **lose the "what" context**, which is exactly the information these 29 messages exist to carry.
- Some sites map a `Result<usize, duckdb::Error>` (`execute`) and some a `Result<(), duckdb::Error>`
  (`execute_batch`); `duck.rs:222-224` maps a `MappedRows` iterator and then its `collect`. The
  blanket impl over `T` covers all of them — if one does not compile, the error type is not
  `duckdb::Error` and that site is out of scope.
- Tests are Go-style siblings: `duck_ext.rs` → `duck_ext_test.rs` via `#[cfg(test)] #[path]`. Never
  an inline `mod tests {}`.
- `unwrap`/`expect` are `deny` in production; `clippy.toml` re-allows them under `#[cfg(test)]`, so
  `duck_ext_test.rs`'s `.unwrap()` calls are fine. `clippy::all` + `warnings` are already `deny`, so
  a leftover unused import in a converted module fails CI.
- `duckdb::Connection::open_in_memory()` is the cheapest way to manufacture a real `duckdb::Error`;
  `Connection::open(":memory:")` works too (and, after PR 13.11, matches how the harnesses call
  `TableDb::open`).
- Do not touch any `.sql` file, the DuckDB templates under `crates/loader/sql/duckdb/templates/`, or
  the `.sqlx` offline cache — there is no Docker locally to regenerate the latter.

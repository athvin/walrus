# PR 13.16 — Mark the error enums non_exhaustive so a new variant is not a cross-crate break

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
> **Gates:** fmt,clippy,test · **Test packages:** common,control,loader,pg-sink,pg-to-arrow

> **Phase:** 13 — Rust API design · **Crates touched:** `common`, `control`, `loader`, `pg-sink`,
> `pg-to-arrow` · **Est. size:** M · **Depends on:** PR 13.15 · **Unlocks:** PR 13.17

Production declares **45 `pub enum`s and 79 `pub struct`s** and carries exactly **one**
`#[non_exhaustive]` — on `pgoutput::Message` (`crates/pg-sink/src/pgoutput/mod.rs:41`), where it was
added because the pgoutput message families landed PR by PR. The failure taxonomy has exactly the
same growth pattern and none of the protection: **14** thiserror enums cross crate boundaries
(`common::Error`, `LoaderError`, `ControlError`, `pg_to_arrow::Error`, `DecodeError`,
`PreflightError`, …) and every one of them has gained variants over the last eight phases. This PR
marks those 14 plus `common::ExitCode` as `#[non_exhaustive]`, so the *next* variant is an additive
change instead of a downstream compile break. It is verifiably free today: no crate matches any of
them exhaustively from outside its defining crate, which `cargo test --workspace` proves.

## Why — learning objectives

- **`#[non_exhaustive]` semantics** — it is a **no-op inside the defining crate** and forces a `_`
  arm only on *out-of-crate* matches. Enum-level, it still permits out-of-crate *construction* of
  existing variants; only variant-level `#[non_exhaustive]` restricts that.
- **The struct half is a different bargain** — on a struct it forbids out-of-crate struct-literal
  construction entirely, including `..Default::default()`. That is why this PR touches zero
  structs.
- **Which walrus enums are open vs closed** — our failure taxonomy is open (still growing, one
  variant per feature PR); the pgoutput/Postgres value domain (`Op`, `Kind`, `TupleValue`, `Tier`,
  `ReplicaIdentity`, `MirrorValue`) is closed by the wire protocol, not by walrus.
- **Forward compatibility vs. exhaustiveness as a tool** — walrus *wants* `Error::is_terminal`'s
  match to break when a variant is added. Understanding why `#[non_exhaustive]` does not weaken
  that is the crux of this ticket.

**Explicitly deferred** (do *not* build these here)

- **No struct gets `#[non_exhaustive]`.** `SinkConfig`, `LoaderConfig`, `CommonConfig`,
  `RegistryRow`, `SinkMeta`, `PgRelation`, … are all constructed with struct-literal syntax from
  outside their defining crate (see `crates/pg-sink/tests/preflight.rs:32`), which
  `#[non_exhaustive]` makes impossible. Marking them would be a self-inflicted break with no
  forward-compat benefit walrus can cash in — it publishes nothing.
- **No `#[non_exhaustive]` on the data enums** — `common::Op`, `common::Kind`,
  `common::TupleValue`, `common::Tier`, `common::ReplicaIdentity`, `loader::plan::MirrorValue`.
- No variant-level `#[non_exhaustive]`, no new variants, no message or classification change, and
  no reordering of `ExitCode`'s numbers (they are a runbook-grepped contract).
- No `#[non_exhaustive]` on the two thiserror **structs** (`common::LsnParseError`,
  `loader::config::ConfigError`) — same reason as the config structs.

**Conflicts to resolve explicitly (do not apply the rule blindly):**

1. **The wildcard-free match is deliberate and must survive.** `Error::is_terminal`
   (`error.rs:69-82`) matches every variant with **no `_` arm** precisely so that adding a variant
   is a compile error until it is classified. `#[non_exhaustive]` does not weaken this: the
   attribute is a no-op *inside* the defining crate, so `is_terminal` and `exit_code` keep
   compiling exactly as they do now, and keep breaking exactly when they should. If you find
   yourself adding a `_ =>` arm to `is_terminal` or `exit_code`, stop — you have misread the
   attribute.
2. **The data enums stay exhaustive.** Their variant sets are closed by the Postgres wire protocol
   and by walrus's own type tiers, not by future feature work, and they *are* matched
   wildcard-free across crate boundaries — `crates/pg-sink/src/batch.rs:224-228` matches
   `common::TupleValue`'s four variants with no `_`. Marking `TupleValue` would break that match
   and gain nothing.

## Skeleton

```rust
// crates/common/src/error.rs — the two attributes, and proof the in-crate matches are untouched.

/// Every way a walrus service can fail a precondition or an operation.
///
/// **Invariant:** whether a variant is terminal or transient is decided by
/// [`Error::is_terminal`] — a method matched exhaustively over the variants — *never* by
/// inspecting the `Display` message string. Classification is modelled as data, not guessed.
///
/// `#[non_exhaustive]`: the taxonomy still grows a variant per feature PR. Downstream crates must
/// carry a `_` arm; **inside `common` the attribute is a no-op**, so `is_terminal`'s wildcard-free
/// match below still fails to compile until a new variant is classified — which is the point.
#[derive(Debug, Error)]
#[non_exhaustive]
pub enum Error {
    #[error("invalid configuration: {0}")]
    Config(String),
    // … all nine variants unchanged …
}

impl Error {
    pub fn is_terminal(&self) -> bool {
        // UNCHANGED. No `_ =>` arm — do not add one.
        match self {
            Error::Config(_)
            | Error::Preflight(_)
            | Error::KeylessTable { .. }
            | Error::LeaseContended(_)
            | Error::Quarantine(_)
            | Error::Internal(_) => true,
            Error::ControlDb(_) | Error::ObjectStore(_) | Error::SourceDb(_) => false,
        }
    }
}

/// Stable, distinct exit statuses. The numbers are a **public contract** … never renumber an
/// existing code, only append new ones.
///
/// `#[non_exhaustive]`: appending a code is exactly the change this contract anticipates.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[repr(i32)]
#[non_exhaustive]
pub enum ExitCode {
    Success = 0,
    // … unchanged …
}
```

## Hints & gotchas

- `#[non_exhaustive]` goes **after** the derives and before `pub enum` (attribute order is free,
  but keep it consistent with `pgoutput/mod.rs:38-41` so the tree reads uniformly).
- Inside the defining crate the attribute does nothing. That is the entire reason this PR is safe,
  and it is also why you cannot "test" it with an in-crate unit test — the only observation point
  is another crate.
- Enum-level `#[non_exhaustive]` does **not** block out-of-crate construction:
  `common::ExitCode::Config.into()` at `crates/loader/src/main.rs:21` and the `assert_eq!` at
  `crates/pg-sink/tests/preflight.rs:139` keep compiling untouched. Only *variant-level*
  `#[non_exhaustive]` would break those — do not add it.
- thiserror is unaffected: `#[error(transparent)]`, `#[from]`, and `#[source]` all still expand
  normally on a `#[non_exhaustive]` enum.
- `clippy::manual_non_exhaustive` (in `clippy::all`, already `deny`) fires on the *old* trick of a
  hidden private unit variant. walrus does not use it; if clippy starts pointing at something, you
  have added a marker variant instead of the attribute.
- `[workspace.lints.rust]` denies `warnings`, so any newly-required wildcard arm shows up as a hard
  error rather than a warning — which is exactly the signal you want. Treat one as a finding, not
  as a chore: it means a downstream crate *was* pattern-matching our taxonomy exhaustively, and the
  PR body should say which.
- `cargo test --workspace` compiles the integration tests under `crates/*/tests/` and `tests/e2e`
  as **separate crates** — that is where an out-of-crate match would break, so `--workspace` (not
  `-p common`) is the real gate here.
- The e2e suite is compose-gated and mostly `#[ignore]`d; `cargo clippy --all-targets` still
  type-checks it, which is enough for this PR.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — no Docker locally to
  regenerate it.

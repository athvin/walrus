# PR 27.5 — Elide the two nameable-but-pointless sqlx encoder lifetimes and deny `elidable_lifetime_names`

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 27 — Rust naming conventions · **Crates touched:** `common` · **Est. size:** S ·
> **Depends on:** PR 27.4 · **Unlocks:** PR 27.6

The headline form of this rule is already satisfied: every declared lifetime in walrus is
conventional — `'_` on 35 items, `'a` on 7, plus `'de` / `'q` / `'r` in trait impls. There is not a
single verbose lifetime name in the tree (the `'pgoutput` / `'failed` hits a naive grep turns up are
SQL string literals, not lifetimes). What *is* wrong is one step past the rule's headline:
`clippy::elidable_lifetime_names` fires on exactly **2** sites — `impl<'q> Encode<'q, Postgres> for
ManifestId` (`crates/common/src/ids.rs:52`) and the identical shape for `Lsn`
(`crates/common/src/lsn.rs:138`) — where `'q` is *bound but never used* in any method signature.
`impl Encode<'_, Postgres>` says the same thing and says it better. This PR elides those two and
pins the lint at `deny` so the shape cannot come back.

## Why — learning objectives

- **Lifetime elision rules, and when a named lifetime carries no information** — a lifetime
  parameter earns its name only if it *relates* two things. `'q` in `Encode<'q, Postgres>` relates
  nothing: no argument, no return, no associated type mentions it. `'_` is the correct spelling for
  "there is a lifetime here and it does not matter".
- **sqlx's `Type` / `Encode` / `Decode` seam for the `Lsn` and `ManifestId` newtypes** — three small
  traits are what let a walrus newtype bind and decode as a native `pg_lsn` / `int8` with no SQL
  cast. Understanding which of the three actually *needs* a lifetime is the whole point of this
  ticket.

## Scope

**In scope**

- `crates/common/src/ids.rs:52`: `impl<'q> Encode<'q, Postgres> for ManifestId` →
  `impl Encode<'_, Postgres> for ManifestId`.
- `crates/common/src/lsn.rs:138`: the same edit for `Lsn`.
- `Cargo.toml`: add `elidable_lifetime_names = "deny"` to `[workspace.lints.clippy]`, with a
  one-line comment saying what it buys (a bound-but-unused lifetime name is noise, and `'_` is the
  spelling that admits it).
- Verify `cargo clippy --all-targets --all-features -- -D warnings` is still green afterwards —
  promoting a lint to `deny` is only done when the tree already passes it.

**Explicitly deferred** (do *not* build these here)

- Do **not** promote the rest of `clippy::nursery` or `clippy::pedantic`. Exactly one lint moves.
- Do **not** touch the 7 `<'a>` items (the pgoutput `Reader<'a>`, `SourcePreflight<'a>`, …). Those
  lifetimes are *used* and correctly named; `'a` is the convention the rule asks for.
- Do **not** touch `'de` in the `serde::Deserialize<'de>` impls — `'de` is serde's own convention and
  is used in `Deserializer<'de>`.

**Conflict — resolve it explicitly, do not apply the rule blindly.**
`impl<'r> Decode<'r, Postgres>` (`crates/common/src/lsn.rs:149`, `crates/common/src/ids.rs:61`) must
**KEEP** its named lifetime. `'r` appears in the method signature —
`fn decode(value: PgValueRef<'r>) -> Result<Self, BoxDynError>` — so it is genuinely relating the
impl to its argument and is *not* elidable. Clippy will not flag it, and neither should you. The
ticket must not blanket-`'_` the `sqlx_support` modules: two impls change, two do not, and the
difference is the lesson.

## Hints & gotchas

- **`'_` is not "no lifetime", it is "an anonymous one".** `impl Encode<'_, Postgres> for Lsn` still
  has a lifetime parameter; you have only declined to name it. That is why the impl keeps compiling
  against sqlx's `Encode<'q, DB>` definition without any other edit.
- The test for elidability is mechanical: **does the name appear anywhere below the `impl` line?**
  For `Encode` the answer is no (the method borrows `&self` and `&mut PgArgumentBuffer`, neither tied
  to `'q`); for `Decode` it is yes (`PgValueRef<'r>`). Apply that test, do not pattern-match on the
  trait name.
- `clippy::elidable_lifetime_names` was split out of `needless_lifetimes`; it is **pedantic**, i.e.
  outside `clippy::all`, so it is currently silent even under `-D warnings`. That is precisely why an
  explicit `deny` in `[workspace.lints.clippy]` is the deliverable here and not a no-op. If your
  toolchain turns out to carry it inside `all`, the explicit entry is still correct and still needs
  no `priority`.
- Promote the lint **after** the two edits, then run clippy across `--all-targets --all-features`.
  The `sqlx` support modules are behind `#[cfg(feature = "sqlx")]`, so a run without `--all-features`
  will not even compile them and will happily tell you nothing is wrong.
- Do **not** reach for `#[derive(sqlx::Type)] #[sqlx(transparent)]` while you are in here.
  `ids.rs:32`'s doc comment explains that these impls are hand-written on purpose, so `common`'s
  `sqlx` dependency need not pull the `macros` feature.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it, and a lifetime elision changes no SQL anyway. Add no dependency;
  anything new must clear `cargo deny`.
- Unit tests are **sibling files** (`lsn.rs` → `lsn_test.rs`, `ids.rs` → `ids_test.rs`), wired by
  `#[cfg(test)] #[path = "..."] mod tests;`. Neither should need an edit.

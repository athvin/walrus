# PR 27.2 — Give the allocating column projections a `to_` cost signal

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** common,loader,pg-sink

> **Phase:** 27 — Rust naming conventions · **Crates touched:** `common`, `loader`, `pg-sink` ·
> **Est. size:** S · **Depends on:** PR 27.1 · **Unlocks:** PR 27.3

Three production methods build a **fresh `Vec<&str>` on every call** but are named like free field
accessors: `PgRelation::key_columns` (`crates/common/src/pg_shape.rs:84`) and `TransformSql::pk_names`
/ `TransformSql::non_key_names` (`crates/loader/src/transform.rs:128` and `:135`). The cost is not
theoretical — `TransformSql::render` calls the latter two on *every* MERGE render
(`transform.rs:180-181`) and `render_rebuild` calls `pk_names` again (`:272`), while `key_columns`'s
one production call site (`crates/pg-sink/src/reload_export.rs:170`) throws the `Vec` straight into a
`BTreeSet`. Where PR 27.1 renamed a lying `as_`, this PR renames three lying *bare* names: `to_` is
the prefix that says "this allocates".

## Why — learning objectives

- **Naming as an API cost contract** — `to_` means allocate/compute. A caller reading
  `self.pk_names()` inside a `for` loop has no reason to suspect a heap allocation per iteration;
  `self.to_pk_names()` gives them the hint without a doc lookup.
- **walrus's composite-PK MERGE renderer and the key-column ordering rule** — `key_columns` and
  `pk_names` both preserve **relation order** rather than sorting, because a composite PK's
  `ON t.a = s.a AND t.b = s.b` join and its `PARTITION BY` list must agree with the source ordering.
  The rename must not perturb that.

- Do **not** convert these into iterator-returning methods. PR 27.6 adds `PgRelation::iter`; the
  `BTreeSet` call site at `reload_export.rs:170` deliberately keeps the allocating `to_key_columns`

- Do **not** hoist or cache the two `render` calls to avoid the per-render allocation. That is a
  `perf-` change and needs a benchmark, not a rename.
- Leave `render`, `render_rebuild` and `chunk_sql` (`crates/pg-sink/src/reload_export.rs:435`)
  alone — they are **verbs that build SQL**, not `T -> U` conversions, so the `to_` prefix would be

## Hints & gotchas

- **Count the call sites before you start.** `key_columns` is `pub` and re-exported through
  `common::PgRelation`, so it is reachable from `pg-sink`'s integration test
  `crates/pg-sink/tests/pgoutput_vectors.rs:746` as well as `common`'s own sibling test. A
  `cargo test -p common` alone will *not* catch that one — run `--workspace`.
- `pk_names`/`non_key_names` are **private** (`fn`, not `pub fn`), so their blast radius really is
  just `transform.rs`. Renaming them is free; renaming `key_columns` is the one that crosses crates.
- `Vec<&str>` is the interesting case for this rule: the `&str`s are borrowed from `self` and cost
  nothing, but `collect()` heap-allocates the `Vec`. `to_` is still correct — the rule is about the
  *call's* cost, not about whether the elements are owned.
- Resist renaming `render`/`render_rebuild`/`chunk_sql` "for consistency". `to_` is for `T -> U`
  conversions; those three take arguments and compose SQL. The rule's own std carve-out (`contains`,
  `starts_with`) is the same idea.
- Unit tests here are **sibling files** — `crates/common/src/pg_shape_test.rs` is wired in by
  `#[cfg(test)] #[path = "pg_shape_test.rs"] mod tests;` at `pg_shape.rs:113`. Do not add an inline
  `mod tests {}`.
- `unwrap`/`expect` are denied in production; `clippy::all` and `warnings` are already `deny`. A
  rename should not need any of them.
- Do not touch any `.sql` file, the `sql/duckdb/templates/transform.sql` template, or the committed
  `.sqlx` offline cache — there is no Docker locally to regenerate it. Add no dependency; anything
  new must clear `cargo deny`.

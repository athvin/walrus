# PR 27.14 — Guard the tree against `get_` getters

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** pg-sink

> **Phase:** 27 — Rust naming conventions · **Crates touched:** *(none — `scripts/check-naming.sh`
> only)* · **Est. size:** S ·
> **Depends on:** PR 27.13 · **Unlocks:** PR 27.15

Production code in walrus contains **zero** `get_`-prefixed functions across all six crates, and it
did not get there by accident: the accessor vocabulary is `InflightMeter::total()` /
`ceiling()` (`crates/pg-sink/src/memory.rs:52,56`), `TableBatcher::committed_rows()` /
`undurable_floor()` (`crates/pg-sink/src/batch.rs:185,193`), `Checkpoint::confirmed_flush()`,
`SlotInfo::start_lsn()`, `HealthState::phase()`. The only three `fn get_` definitions anywhere in the
repo are integration-test helpers — `get_body` (`crates/loader/tests/metrics_scrape.rs:15` and
`crates/pg-sink/tests/metrics_scrape.rs:14`) and `get_status`
(`crates/pg-sink/tests/health.rs:15`) — where `get` names the **HTTP verb** being issued, not a
getter. Nothing enforces any of this: no rustc lint and no clippy lint covers `get_` naming, so the
next PR can add `get_epoch()` and CI will wave it through. This PR appends a `no_get_prefix` check to
the guard script PR 27.9 created, scoped to *definitions in library source* so the legitimate
`.get(…)` call sites and the HTTP helpers stay legal. Nothing is renamed.

## Why — learning objectives

- **Rust's getter convention and why `get` means fallible lookup** — std reserves `get` for the
  *bounds-checked, `Option`-returning* access (`Vec::get`, `HashMap::get`) and uses the bare noun for
  direct access (`len`, `capacity`, `file_name`). So `get_` on an infallible accessor is not merely
  verbose — it mis-signals fallibility.
- **Reading walrus accessors: `undurable_floor`, `committed_rows`, `open_floor`** — these are nouns
  naming a *quantity in the durability model*, not fields with a prefix bolted on. Learning to read
  them as domain vocabulary is what makes the sink's backpressure and slot-advance code legible.

**The conflict this ticket must resolve (do not apply the rule blindly)**

The rule reserves `get` for fallible/computed lookups, so a naive `grep -rn 'get_'` guard is
**wrong twice over**. First, it would hit 46 legitimate `.get(…)` / `.get_mut(…)` call sites in
production (`by_name.get(c.name.as_str())` at `crates/loader/src/plan.rs:93`, `row.get(0)` on sqlx
rows at `crates/pg-sink/src/slot.rs:68`, `new.get(idx)?` at
`crates/pg-sink/src/reload_signal.rs:129`) plus the `env::var`-style lookups — all correct Rust that
the rule explicitly blesses. Second, it would hit the three HTTP helpers. **The guard must match
definition syntax (`fn get_`), not the substring, and must be scoped to library source.** If your
check's count on today's tree is anything other than 0, you have written the wrong pattern.

**Explicitly deferred** (do *not* build these here)

- **Renames nothing.** Production is already at 0; this is pure enforcement.
- Does not rename the three test helpers. `get_body`/`get_status` are correct as they stand — `get`
  is the HTTP method they send. Renaming them to satisfy a grep would be the guard wagging the code.
- No `set_`-prefixed setters and no builder pass — that is the `api-` phase (Phase 13).
- Depends on PR 27.9 having created `scripts/check-naming.sh` and wired it into CI. If it is not
  there, stop and land 27.9 first; do **not** create a second script.

## Skeleton

The exact helper names below are placeholders — **mirror whatever `scripts/check-naming.sh` already
uses.** What must survive verbatim is the pattern, the scope, and the comment.

```bash
# scripts/check-naming.sh — appended alongside the funcs/mods/filenames, types_camel and
# consts_screaming checks.

# --- no_get_prefix (PR 27.14) -------------------------------------------------------------------
# Rust omits `get_` on simple accessors: `total()`, `ceiling()`, `committed_rows()`,
# `undurable_floor()` — never `get_total()`. std reserves the bare `get` for the FALLIBLE,
# Option-returning lookup (`HashMap::get`, `Vec::get`), so a `get_` prefix on an infallible accessor
# mis-signals that the call can miss.
#
# Scope is DEFINITIONS in library source only:
#   * `crates/*/tests/` is excluded — `get_body` / `get_status` there send an HTTP GET; `get` is the
#     verb, not a getter prefix. Same for `crates/*/benches/`.
#   * call sites are never matched — `by_name.get(..)`, `row.get(0)`, `env::var(..)` are all correct
#     and appear ~46 times in production.
check_no_get_prefix() {
  local hits
  hits=$(grep -rn --include='*.rs' -E '\bfn +get_' crates/*/src tests/e2e/src || true)
  local n
  n=$(printf '%s' "$hits" | grep -c . || true)
  if [ "$n" -ne 0 ]; then
    echo "FAIL no_get_prefix: $n getter(s) with a 'get_' prefix — drop the prefix (see"
    echo "     .claude/skills/rust-skills/rules/name-no-get-prefix.md); 'get' is for fallible lookup."
    printf '%s\n' "$hits"
    return 1
  fi
  echo "  ok no_get_prefix: 0 'fn get_' definitions under crates/*/src + tests/e2e/src"
  return 0
}
```

## Hints & gotchas

- **Read the script before you write.** Five PRs in this phase (27.9, 27.10, 27.12, 27.14, 27.15,
  27.16) all append to one file. If each invents its own helper shape the script becomes unreadable
  by 27.16. Copy the existing check's structure exactly.
- **`grep -c` inside `$( )` with `set -euo pipefail` will kill your script.** `grep` exits `1` when
  it matches nothing — which is the *success* case here. Terminate every grep with `|| true` (as the
  skeleton does) or the guard fails on a clean tree, which is the most embarrassing possible bug in a
  guard.
- **Match `\bfn +get_`, not `get_`.** The substring form hits 46 legitimate `.get(` call sites, the
  `env::var` lookups, and even the string `"get_body"` in a comment. The `fn ` anchor is what makes
  this check a naming rule rather than a search.
- **`--exclude='*_test.rs'` is deliberately absent here.** Sibling unit tests live *inside*
  `crates/*/src` and are exactly as bound by the convention as the code they test — unlike
  `crates/*/tests/`, which is out of scope for the HTTP-verb reason. Be explicit about that
  asymmetry in the comment.
- **`crates/*/src` needs shell globbing, not `find`.** With `crates/*/src tests/e2e/src` as literal
  arguments the script must run from the repo root; PR 27.9's script already does
  `cd "$(git rev-parse --show-toplevel)"` (the pattern `scripts/k8s-validate.sh:10` established).
  Do not add a second `cd`.
- **Do not add a clippy lint for this.** There isn't one. `clippy::wrong_self_convention` polices
  `as_`/`to_`/`into_`/`is_` receivers, not `get_`; searching for a lint to lean on here is a dead end
  and the reason this ticket is a script check rather than a `[workspace.lints]` line.
- `unwrap`/`expect` are denied in production and `clippy::all` + `warnings` are already `deny` — but
  none of that applies to a shell script. What *does* apply: `shellcheck`-clean habits (quote your
  expansions) so the script survives review.
- Unit tests in walrus are **sibling files** (`src/foo.rs` → `src/foo_test.rs`), never inline
  `mod tests {}`. This PR adds no Rust; the script's isolated `--self-test` fixture is the negative
  proof.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it. No new dependency, so nothing new for `cargo deny` to clear.

# PR 27.3 — Rename `BatchBuilder::finish` to `into_record_batch` to signal the move

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Readiness:** audited · **Outcome:** change
>
> **Gates:** fmt,clippy,test · **Test packages:** pg-to-arrow

> **Phase:** 27 — Rust naming conventions · **Crates touched:** `pg-to-arrow`, `pg-sink`
> (`loader` benches) · **Est. size:** M · **Depends on:** PR 27.2 · **Unlocks:** PR 27.4

At the clean task predecessor `24b31582ec05437d4a234e11b0b4e318c24b0fdc`, production has exactly
**five** `into_*` definitions: `UtcTimestamp::into_inner`, `SnapshotConn::into_stream`, and the
owned / `&` / `&mut` `IntoIterator::into_iter` implementations for `RelationCache`. The two borrowed
`RelationCache` implementations consume a reference value rather than the cache, but the trait fixes
their spelling; all five are conforming, classified baseline rather than rename targets.

Meanwhile `BatchBuilder::finish(mut self) -> Result<RecordBatch, Error>`
(`crates/pg-to-arrow/src/batch.rs:270`) consumes `self` while wearing arrow-rs's `finish` name — and
arrow's own `ArrayBuilder::finish` takes `&mut self`. Same word, opposite ownership. That mismatch is
exactly why the single production caller has to write
`std::mem::replace(&mut self.builder, BatchBuilder::new(&self.rel.relation)?)` in
`TableBatcher::seal` (`crates/pg-sink/src/batch.rs:269`) before it can call `finish`: the surrounding
`seal(&mut self)` only has a mutable borrow, and the by-value receiver is invisible from the call.
Renaming it to `into_record_batch` makes the move a caller-visible fact.

The exact old-name baseline is **1 definition + 25 calls = 26 occurrences**. The original audit
counted 23 calls; PR 10.9 commit `c9c4cb67` added the binary-column sibling test and PR 17.5 commit
`af0d59b0` added the non-finite-float sibling test. Both build a `BatchBuilder` and call `finish`, so
`batch_test.rs` now contributes **16**, not 14. The remaining calls are unchanged: parquet unit test
**1**, conformance **3**, `pg-to-arrow` bench **1**, loader bench **1**, `pg-sink` production **1**,
and `pg-sink` integration tests **2**. After the rename the exact census remains 26 occurrences:
**1 new definition + the same 25 calls**.

## Why — learning objectives

- **`self` vs `&mut self` receivers, and why `into_` is the caller-visible move marker** — a method
  taking `self` ends the receiver's life. Rust will tell you at the *use-after-move*, which may be
  far from the call; the name tells you at the call.
- **How the sink seals one Arrow `RecordBatch` per micro-batch at a commit boundary** —
  `TableBatcher::seal` refuses to split an open transaction, swaps in a fresh `BatchBuilder`, turns
  the old one into a `RecordBatch`, and resets the row/byte/LSN counters. The `mem::replace` is the
  physical shape of "the builder is spent".

**Conflict — resolve it explicitly, do not apply the rule blindly.** arrow-rs spells this operation
`finish`, so at first read the rename looks like fighting the ecosystem. It is not: **arrow's
`ArrayBuilder::finish` takes `&mut self` and leaves the builder reusable; walrus's takes `mut self`
and destroys it.** The names must differ *precisely because* the semantics differ — and
`batch.rs:273-275` calls arrow's `finish` twice inside the very method being renamed, so after this
PR the file contains both spellings side by side, which is the point. Write that reasoning into the
doc comment so the next reader does not "fix" it back.

## Hints & gotchas

- **The old audit is short by two calls, for a known reason.** `git show c9c4cb67 --
  crates/pg-to-arrow/src/batch_test.rs` shows PR 10.9's binary-column test; `git show af0d59b0 --
  crates/pg-to-arrow/src/batch_test.rs` shows PR 17.5's non-finite-float test. Each added one
  `BatchBuilder::finish` call, taking the sibling-file count from 14 to 16 and the workspace call
  count from 23 to 25. Migrate both; do not remove or consolidate either regression.
- **The compiler will not find every call site for you unless you build every target.** `cargo test
  -p pg-to-arrow` misses `crates/loader/benches/append.rs:105` and the two `pg-sink` integration
  tests. Use `cargo clippy --all-targets --all-features -- -D warnings` as the search: it compiles
  lib, bins, tests, examples and benches.
- There are **three** `finish` families in the allowed files. arrow's `ArrayBuilder::finish` /
  `StringBuilder::finish` (`&mut self`), Criterion's `BenchmarkGroup::finish` (`g.finish()`), and
  walrus's consuming `BatchBuilder::finish` are unrelated. The exact call probe selects only the
  latter because its 24 test/bench calls immediately use `.unwrap()` and its one production call
  uses `?`; it deliberately leaves inner `builder.finish()`, `self.meta.finish()`, `sb.finish()`,
  and every `g.finish()` alone.
- The production census excludes sibling `*_test.rs` files on purpose, so the test-only
  `DynError::into_error` does not masquerade as API surface. Its five baseline matches are all
  classified: `UtcTimestamp::into_inner` and `SnapshotConn::into_stream` genuinely consume owned
  values; owned `RelationCache::into_iter` consumes the cache; the `&RelationCache` and
  `&mut RelationCache` variants consume only their reference values but must use the
  `IntoIterator` trait's fixed method name.
- `TableBatcher::seal` must keep the `mem::replace`. It is not a workaround to delete — it is the
  correct way to move a value out of a `&mut self` field, and `BatchBuilder::new(&self.rel.relation)?`
  is what re-arms the batcher for the next micro-batch.
- The benchmark's two direct API doc references move to `into_record_batch()`, but `bench_finish`
  and `arrow/finish` stay stable so Criterion history remains comparable. Likewise, do not rewrite
  historical mentions in `docs/benchmarks.md` or earlier completed roadmap tasks; they describe the
  API and measurements at the time those PRs landed and are outside the nine-path allowlist.
- Do not rename `seal` itself. It is a verb with side effects (it resets six counters and returns a
  `SealedBatch`), not a `T -> U` conversion.
- `unwrap`/`expect` are denied in production by `[workspace.lints.clippy]`; `clippy.toml` re-allows
  them under `#[cfg(test)]` and in integration `tests/`, and the benches carry a file-level allow —
  so the `.into_record_batch().unwrap()` you write in tests and benches is fine, but never in `src`.
- Unit tests are **sibling files** (`batch.rs` → `batch_test.rs`), wired via
  `#[cfg(test)] #[path = "..."] mod tests;`. Do not add an inline `mod tests {}`.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache (no Docker locally to
  regenerate it). Add no dependency — anything new must clear `cargo deny`.

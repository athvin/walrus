# PR 27.8 — Name the `PgRelation` iterator types `Iter`, `IterMut`, `IntoIter`

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 27 — Rust naming conventions · **Crates touched:** `common` ·
> **Est. size:** M · **Depends on:** PR 27.7 · **Unlocks:** PR 27.9

The repo has **zero** types named `Iter`/`IterMut`/`IntoIter` and **zero** hand-written `Iterator`
implementations. After PRs 27.6 and 27.7, `PgRelation::iter()` returns an anonymous
`impl Iterator<Item = &PgColumn>` and `<&PgRelation as IntoIterator>::IntoIter` is literally
`std::slice::Iter<'_, PgColumn>` — so `common`'s public signature names a foreign type, and a caller
cannot store the iterator in a struct field or write its type in a `where` clause without naming
`std::slice::Iter` itself. This PR introduces the three walrus-owned newtype wrappers, names them
after the methods that produce them exactly as the standard library does (`Vec::iter → slice::Iter`,
`Vec::into_iter → vec::IntoIter`), and re-exports them from `common`'s lib root next to `PgRelation`.

## Why — learning objectives

- **Writing a manual `Iterator` newtype wrapper** — a `pub struct Iter<'a> { inner:
  std::slice::Iter<'a, PgColumn> }` plus a three-line `impl Iterator` is the whole pattern. The
  method-name → type-name convention (`iter()` → `Iter`, `iter_mut()` → `IterMut`, `into_iter()` →
  `IntoIter`) is what makes the API guessable without reading the docs.
- **Keeping `common`'s public surface free of leaked upstream types** — `impl Trait` in return
  position hides the type from callers entirely; a named associated type like `std::vec::IntoIter`
  hard-codes *someone else's* type into walrus's contract. The wrapper gives the third option: a
  name walrus owns, whose internals can change without a breaking signature.

## Scope

**In scope**

- Add `pub struct Iter<'a>`, `pub struct IterMut<'a>` and `pub struct IntoIter` to
  `crates/common/src/pg_shape.rs`, each a newtype over the corresponding `std` iterator, with a
  `impl Iterator for …` that forwards `next` **and** `size_hint` to the inner iterator.
- Change `PgRelation::iter()` to return `Iter<'_>` and `iter_mut()` to return `IterMut<'_>` — no
  more `impl Iterator` in either signature.
- Retarget the three `IntoIterator` impls from PR 27.7 onto the new types: `IntoIter` for the owned
  form, `Iter<'a>` for `&'a PgRelation`, `IterMut<'a>` for `&'a mut PgRelation`.
- Re-export `Iter`, `IterMut`, `IntoIter` from `crates/common/src/lib.rs` alongside the other
  `pg_shape` types.
- Extend `crates/common/src/pg_shape_test.rs` with a test that **names** the type — e.g. binds
  `let it: common::pg_shape::Iter<'_> = rel.iter();` — which is precisely what an
  `impl Iterator` return type made impossible.

**Explicitly deferred** (do *not* build these here)

- No `DoubleEndedIterator`, `ExactSizeIterator` or `FusedIterator` impls. Add one only when a call
  site actually needs `.rev()` or `.len()`; today none does (`BatchBuilder::new` still uses
  `rel.columns.len()` directly). `size_hint` is part of `Iterator` itself and is the one exception.
- No `Keys`/`Values`-style named iterators for the loader's `SchemaDiff`
  (`crates/loader/src/ddl.rs:95`) or anything else. One type gets the treatment.
- Do not make `PgRelation::columns` private, and do not change any call site outside `common` —
  swapping `impl Iterator` for a concrete `Iter<'_>` is source-compatible for every existing caller.

## Skeleton

// crates/common/src/pg_shape.rs — new types, placed directly after `impl PgRelation { .. }`.

/// Borrowing iterator over a relation's columns — the return type of [`PgRelation::iter`].
///
/// A newtype rather than a bare `std::slice::Iter`: the concrete inner type is an implementation
/// detail, and a caller that wants to store this iterator needs a name `common` owns.
#[derive(Debug, Clone)]
pub struct Iter<'a> {
    inner: std::slice::Iter<'a, PgColumn>,
}

/// Mutable iterator over a relation's columns — the return type of [`PgRelation::iter_mut`].
#[derive(Debug)]
pub struct IterMut<'a> {
    inner: std::slice::IterMut<'a, PgColumn>,
}

/// Consuming iterator over a relation's columns — `<PgRelation as IntoIterator>::IntoIter`.
#[derive(Debug)]
pub struct IntoIter {
    inner: std::vec::IntoIter<PgColumn>,
}

impl<'a> Iterator for Iter<'a> {
    type Item = &'a PgColumn;

        todo!("self.inner.next()")
    }

    // Forwarded so `collect()` still preallocates exactly.
    fn size_hint(&self) -> (usize, Option<usize>) {
        todo!("self.inner.size_hint()")
    }
}

## Hints & gotchas

- `IntoIter` takes **no** lifetime parameter — it owns its `PgColumn`s. Only `Iter`/`IterMut` are
  borrow-parameterised, and their `'a` is used in `Item`, so `clippy::elidable_lifetime_names`
  (denied by PR 27.5) will not fire on `impl<'a> Iterator for Iter<'a>`.
- `IterMut` cannot be `Clone` — `std::slice::IterMut` is not (two live mutable iterators over the
  same slice would alias). `Iter` can and should derive `Clone`; `IntoIter` cannot be `Copy`.
- Keep the `inner` field **private**. The whole point is that `std::slice::Iter` stops being part of
  `common`'s contract; a `pub inner` puts it straight back.
- `Iter`/`IterMut`/`IntoIter` at the lib root are deliberately bare names, which is safe only because
  `common` has exactly one iterable type. If a second one ever appears, the new pair goes in its own
  module (`schema_diff::Iter`) rather than being suffixed — that is what the std pattern does.
- Do not add `#[must_use]`. The tree has zero of them today, and `Iterator` is already
  `#[must_use]` at the trait level — annotating the struct adds noise, not signal.
- Sibling test files, not inline `mod tests {}`: the wiring is the `#[cfg(test)] #[path =
  "pg_shape_test.rs"] mod tests;` at the bottom of `pg_shape.rs`. The test file starts with
  `use super::*;`, so `Iter`/`IterMut`/`IntoIter` resolve without an extra import.
- `unwrap`/`expect` are denied in production by `[workspace.lints.clippy]`; `clippy::all` and
  `warnings` are already `deny`. `clippy.toml` re-allows both under `#[cfg(test)]`.
- Add no dependency — this is pure `std` — and touch no `.sql` file or the committed `.sqlx` offline
  cache (there is no Docker on this machine to regenerate it).

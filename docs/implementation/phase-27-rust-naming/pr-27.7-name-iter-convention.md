# PR 27.7 — Implement `IntoIterator` for `PgRelation` and its two reference forms

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 27 — Rust naming conventions · **Crates touched:** `common`, `pg-to-arrow`, `loader` ·
> **Est. size:** M · **Depends on:** PR 27.6 · **Unlocks:** PR 27.8

There is not a single `IntoIterator` implementation anywhere in walrus — a whole-repo grep for the
identifier returns **0** hits across `crates/` and `tests/`. PR 27.6 gave `PgRelation` the borrowing
half of the trio (`iter()` / `iter_mut()`), but `for c in &rel` still does not compile, so every
traversal has to spell out `rel.iter()` and the only way to consume a relation's columns is to move
its public `columns` field out by hand. This PR closes the trio: three `IntoIterator` impls on
`PgRelation`, `&PgRelation` and `&mut PgRelation`, so `for c in rel` / `for c in &mut rel` /
`for c in rel` (owned) all work, and the four remaining `for c in rel.iter()` loops in the loader
planner and the Arrow schema/batch builders collapse to the `for` form the language already knows.

## Why — learning objectives

- **`IntoIterator` for `T` / `&T` / `&mut T`** — `for x in expr` desugars to
  `IntoIterator::into_iter(expr)`; which of the three impls the compiler picks is decided purely by
  whether you wrote `rel`, `&rel` or `&mut rel`. Only the owned impl is named `into_iter` on the
  type itself; the other two are what makes `&rel` iterable at all.
- **Owned-vs-borrowed column traversal** — `pg-to-arrow`'s `build_schema`/`BatchBuilder::new` and the
  loader's `TablePlan` builders all take `&PgRelation` and only ever *read* columns, so they want the
  `&PgRelation` impl. Nothing in production consumes a relation today; the owned impl exists so that
  a future move-based builder has the idiomatic door, not because a caller is waiting for it.

## Scope

**In scope**

- Add three impls in `crates/common/src/pg_shape.rs`, next to the existing `impl PgRelation`:
  `IntoIterator for PgRelation` (`Item = PgColumn`), `for &'a PgRelation` (`Item = &'a PgColumn`),
  and `for &'a mut PgRelation` (`Item = &'a mut PgColumn`).
- Migrate the four plain `for` loops that PR 27.6 left as `for c in rel.iter()` to `for c in rel`:
  `loader/src/plan.rs:63`, `loader/src/plan.rs:92`, `pg-to-arrow/src/schema.rs:29`,
  `pg-to-arrow/src/batch.rs:97`.
- Extend `crates/common/src/pg_shape_test.rs` with a test that exercises all three forms:
  `for c in &rel`, `for c in &mut rel` (mutating a column and observing it), and `for c in rel`
  (owned, collecting `Vec<PgColumn>`).

**Explicitly deferred** (do *not* build these here)

- The owned `IntoIter` associated type stays `std::vec::IntoIter<PgColumn>`. Wrapping it (and the
  two borrowed ones) in walrus-named `Iter`/`IterMut`/`IntoIter` structs is **PR 27.8** — that PR
  edits these same three impls, so do not pre-empt it.
- No other collection type gets the treatment: `SchemaDiff` (`crates/loader/src/ddl.rs:95`),
  `RelationCache` (`crates/pg-sink/src/relcache.rs:35`) and `BatchRouter`
  (`crates/pg-sink/src/consume.rs:406`) stay as they are.
- Do **not** make `PgRelation::columns` private. It is still `pub` and still read directly by
  `.columns.len()` and by the `.iter().position(..)` / `.iter().map(..)` chains — those chains need
  a method call and cannot use `for`-loop sugar. Visibility is a later `proj-`/`api-` change.
- Do not promote `clippy::iter_without_into_iter` / `clippy::into_iter_without_iter` in
  `[workspace.lints]`. Satisfying the pairing by hand is this PR; pinning a lint for it is not.

## Hints & gotchas

- The reference impls need a **named** lifetime: `impl<'a> IntoIterator for &'a PgRelation` — `'a`
  appears in `type Item = &'a PgColumn` and in `type IntoIter = std::slice::Iter<'a, PgColumn>`, so
  it is *not* elidable and `clippy::elidable_lifetime_names` (denied by PR 27.5) will not complain.
  Do not try to write `impl IntoIterator for &'_ PgRelation`; it will not compile.
- `PgColumn` is `Clone`, not `Copy`. The owned impl genuinely moves `self.columns`, so a test that
  uses `for c in rel` cannot touch `rel` afterwards — assert on the collected `Vec` instead.
- `for c in rel` inside `tier1(rel: &PgRelation)` iterates *through* the reference — `rel` is already
  a `&PgRelation`, so no extra `&` is needed and `rel.name.clone()` on the line after the loop still
  works because the borrow ends with the loop.
- `.iter().position(..)` in `pg-sink/src/ddl.rs:41`, `reload_signal.rs:128`, `heartbeat.rs:85` and
  `.iter().map(..)` in `pg-to-arrow/src/descriptor.rs:44` are **method chains**, not `for` loops.
  They keep calling `iter()`; `IntoIterator` buys them nothing. Do not "convert" them.
- Adding an impl to `common` re-checks every downstream crate. Run `cargo test --workspace`, not
  just `-p common` — `pg-to-arrow`, `pg-sink` and `loader` all consume `PgRelation`.
- Unit tests here are **sibling files** (`pg_shape_test.rs` wired in by `#[cfg(test)] #[path = ...]
  mod tests;` at the bottom of `pg_shape.rs`), never inline `mod tests {}`.
- `unwrap`/`expect` are denied in production by `[workspace.lints.clippy]`, and `clippy::all` +
  `warnings` are already `deny`. `clippy.toml` re-allows unwrap/expect under `#[cfg(test)]`, so the
  sibling test may use them.
- Add no dependency (everything here is `std`), and touch no `.sql` file or the committed `.sqlx`
  offline cache — there is no Docker on this machine to regenerate it.

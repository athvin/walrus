# PR 27.6 — Give `PgRelation` `iter()` and `iter_mut()` over its columns

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 27 — Rust naming conventions · **Crates touched:** `common`, `pg-to-arrow`, `pg-sink`,
> `loader` · **Est. size:** M · **Depends on:** PR 27.5 · **Unlocks:** PR 27.7

The tree defines **zero** `iter` / `iter_mut` / `into_iter` methods anywhere in production.
`PgRelation` (`crates/common/src/pg_shape.rs:73`) is the shared shape type every crate reads — the
decoder produces it, `pg-to-arrow` consumes it, `control` persists it, `loader` reads it back — and
**8** production sites reach straight through its `pub columns: Vec<PgColumn>` field to iterate:
`for c in &rel.columns` in the loader planner (`plan.rs:63`, `:92`),
`.columns.iter().position(..)` in the sink (`ddl.rs:41`, `reload_signal.rs:128`, `heartbeat.rs:85`),
`.columns.iter().map(..)` in `pg-to-arrow` (`descriptor.rs:44`, plus `schema.rs:29` and
`batch.rs:97`). Every one of those locks the public field into the API. This PR adds the standard
`iter()` / `iter_mut()` pair and routes all 8 through it, so the field stops being the interface.

## Why — learning objectives

- **`impl Iterator` return types and the iter / iter_mut / into_iter naming trio** — `iter()` on
  `&self` yields `&T`, `iter_mut()` on `&mut self` yields `&mut T`, `into_iter()` on `self` yields
  `T`. Returning `impl Iterator<Item = &PgColumn>` keeps the concrete `slice::Iter` out of the
  signature — which is *also* why PR 27.8 later has to name it.
- **`PgRelation` as the decoder → Arrow → loader decoupling seam** — this one struct is why
  `pg-to-arrow` is unit-testable without a decoder and why no crate depends on a binary. Adding a
  method to it is a four-crate change, which is exactly the kind of blast radius a public field
  creates and a method hides.

## Scope

**In scope**

- Add two methods to `impl PgRelation` in `crates/common/src/pg_shape.rs`:
  - `pub fn iter(&self) -> impl Iterator<Item = &PgColumn>`
  - `pub fn iter_mut(&mut self) -> impl Iterator<Item = &mut PgColumn>`
  Both delegate to `self.columns`; both get a doc comment saying they walk the columns **in relation
  order** (the same ordering guarantee `to_key_columns` documents).
- Convert all **8** production reach-through sites to `rel.iter()`. `for c in &rel.columns` becomes
  `for c in rel.iter()`; `rel.columns.iter().position(..)` becomes `rel.iter().position(..)`.
- Add a sibling test in `crates/common/src/pg_shape_test.rs` asserting
  `rel.iter().count() == rel.columns.len()`, that `iter()` yields columns in declaration order, and
  that `iter_mut()` can mutate through (e.g. flip an `is_key` and observe it).

**Explicitly deferred** (do *not* build these here)

- **No `IntoIterator`.** `for c in &rel` must still fail to compile after this PR — that is PR 27.7's
  probe. Adding it here steals the next ticket's evidence.
- **No named iterator structs.** `Iter` / `IterMut` / `IntoIter` types are PR 27.8; here the return
  type stays `impl Iterator`.
- **Do not make `columns` private.** Field visibility is a `proj-` / `api-` change and would break
  `serde` round-tripping of the registry snapshot in one step too many.
- Leave `to_key_columns` (from PR 27.2) exactly as it is — its one production call site collects into
  a `BTreeSet`, so it still wants an allocating projection. Rewriting its *body* to use `self.iter()`
  is optional polish, not required.
- Do not add `len()` / `is_empty()` to `PgRelation`. `rel.columns.len()` at
  `crates/pg-to-arrow/src/batch.rs:96` and `crates/pg-to-arrow/src/schema.rs:28` stays as-is; the
  probe counts *iteration* reach-through, not field reads.

## Hints & gotchas

- **`iter()` is an inherent method here, not a trait one.** Nothing implements `Iterator` in this PR
  and nothing implements `IntoIterator`; `for c in &rel` will still be a compile error, and that is
  correct — PR 27.7 fixes it and PR 27.8 names the types. Do not get ahead of them.
- `clippy::iter_without_into_iter` exists and says exactly what PR 27.7 will do. It is **pedantic**
  (outside `clippy::all`), so it stays silent under the workspace's `-D warnings` — but if you see
  it, the answer is "PR 27.7", not an `#[allow]` and not an early `IntoIterator` impl.
- `impl Iterator<Item = &PgColumn>` captures the `&self` borrow through Rust 2021's RPIT capture
  rules; `impl Iterator<Item = &mut PgColumn>` captures `&mut self`. That means `rel.iter_mut()`
  cannot be alive at the same time as any `rel.iter()` — fine for the tests above, and worth knowing
  before you try to write a clever one.
- Three of the eight sites live inside a **closure** — `let text = |name: &str| { … }` — that
  captures `rel` by shared reference. `iter()` takes `&self`, so nothing about the capture changes;
  just do not reorder the closure relative to a `&mut` borrow while editing.
- `crates/pg-sink/src/heartbeat.rs:85` uses the binding name `relation`, not `rel`. Grep for
  `.columns.iter()`, not for `rel.`.
- `PgRelation` derives `Serialize`/`Deserialize` and is persisted as the `schema_registry` columns
  snapshot. Adding **methods** does not change that JSON; adding or reordering *fields* would. Add no
  fields.
- Unit tests are **sibling files** — put the new tests in `crates/common/src/pg_shape_test.rs`, which
  is already wired via `#[cfg(test)] #[path = "pg_shape_test.rs"] mod tests;` at `pg_shape.rs:113`.
  Never an inline `mod tests {}`.
- `unwrap`/`expect` are denied in production by `[workspace.lints.clippy]` (re-allowed under
  `#[cfg(test)]` by `clippy.toml`); `clippy::all` and `warnings` are already `deny`.
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it. Add no dependency; anything new must clear `cargo deny`.

# PR 19.5 — Dispatch the sink clock statically and document why the remaining dyn stays dyn

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 19 — Rust traits & generics · **Crates touched:** `pg-sink` · **Est. size:** L ·
> **Depends on:** PR 19.4 · **Unlocks:** PR 19.6

`dyn Clock` appears at exactly **7 production sites and 0 test sites**, yet `Clock` has **one**
production impl (`SystemClock`) and one test fake — the rule's Bad case, *"unnecessary boxing when
only one concrete type is used"*, sitting on a per-row hot path (`should_flush` runs at every commit
boundary). Four structs carry the vtable: `TableBatcher` (`batch.rs:60`), `BatchRouter`
(`consume.rs:409`), `Backfill` (`snapshot.rs:107`, which hardcodes `Arc::new(SystemClock)` at
`:139`) and `StreamDemux` (`stream_txn.rs:99`). This PR threads a `C` type parameter through all
four, taking `dyn Clock` **7 → 0**. By contrast the other **20** `dyn` uses are *correct* and stay:
`Arc<dyn ObjectStore>` (the backend is chosen from config at runtime) and `Box<dyn ArrayBuilder>`
(one heterogeneous builder per column) — this PR records a decision table saying so, so the next
reader does not "clean them up" too.

## Why — learning objectives

- **Monomorphisation vs vtable dispatch** — a generic `C: Clock` gets one specialised copy per
  concrete clock the binary actually uses (exactly one, in production), inlinable to nothing;
  `Arc<dyn Clock>` is a fat pointer with an indirect call per `now()`. The trade is binary size,
  which is negligible at one instantiation.
- **Threading a generic parameter through owning structs** — the mechanical part: the field type,
  the struct header, every `impl` block, and every free function that *names* the struct. Getting
  the bound placement right (`impl<C: Clock>`, not on the struct) is the idiomatic form.
- **`impl Trait` in argument position** — already used 20+ times in `control` as
  `impl PgExecutor<'_>`; it is the same monomorphisation as a named `C`, and it is what you reach
  for when the parameter appears exactly once.
- **The pg-sink batching hot path** — per-table batchers, commit-boundary sealing, and the
  `max_fill` cadence trigger: the only thing the clock is *for*.

## Scope

**In scope**

- `TableBatcher` → generic over the clock: field `clock: C`, header
  `pub struct TableBatcher<C> { … }`, and `impl<C: Clock> TableBatcher<C> { … }`.
- `BatchRouter` → `pub struct BatchRouter<C>` with `batchers: HashMap<u32, TableBatcher<C>>` and
  `clock: C`; `impl<C: Clock + Clone> BatchRouter<C>`.
- `Backfill` → `pub struct Backfill<C>` with `clock: C`. Keep `connect` in an
  `impl Backfill<std::sync::Arc<SystemClock>>` block so `main.rs:304` calls it unchanged.
- `StreamDemux` → `pub struct StreamDemux<C>` with `clock: C`;
  `impl<C: Clock + Clone> StreamDemux<C>`.
- Thread the parameter through the two free functions that name those types:
  `consume::run_decode_loop<C: Clock + Clone>(…, router: &mut BatchRouter<C>, …, demux: &mut StreamDemux<C>, …)`
  and `shutdown::drain<C: Clock + Clone>(…, router: &mut BatchRouter<C>, …)`.
- Rewrite the `Clock` doc comment at `batch.rs:19-21` (see the conflict note) and add a short
  **decision table** to the `batch.rs` module doc recording which `dyn` in `pg-sink` is deliberate
  and why.
- Leave every construction site alone: `Arc::new(SystemClock)` infers `C = Arc<SystemClock>` and
  `FakeClock::new()` infers `C = Arc<FakeClock>`, both thanks to PR 19.4's delegating impls.

**Explicitly deferred** (do *not* build these here)

- `Arc<dyn ObjectStore>` and `Box<dyn ArrayBuilder>` — **20 sites, all correct**. The object-store
  backend is chosen from config at runtime (plugin case) and the Arrow builders are a genuinely
  heterogeneous per-column collection. They get a row in the decision table and nothing else.
- Benchmarks or any speedup claim. The criterion baseline is a separate, bench-gated concern; do
  **not** write "faster" in the PR body without a measurement.
- `impl Trait` in return position anywhere (there are 0 today) and any change to `Clock`'s method
  set — that is PR 19.6.
- Removing the `Clock` trait or `FakeClock`. The test seam is the reason the trait exists.

**Conflict — read before applying the rule.** `crates/pg-sink/src/batch.rs:19-21` records an
explicit PR 8.5 audit: *"the single production impl is deliberate — the trait exists for that test
seam, not as dead generality (kept by design)."* Honour it. **Keep the trait and keep the seam;
change only the dispatch.** Update that comment so it says (a) the seam is still why `Clock` exists,
(b) dispatch is now static because there is exactly one production impl on a per-commit path, and
(c) which `dyn` sites in this crate are intentionally left alone. Deleting the comment, or deleting
the trait "because there's only one impl", both fail this PR.

// crates/pg-sink/src/batch.rs:19 — the rewritten audit note (conflict resolution) + the trait.

/// Injectable clock so `max_fill` is testable without sleeping. Production has exactly one impl
/// ([`SystemClock`]); the trait exists **for that test seam**, not as dead generality (audited
/// PR 8.5, kept by design). Since PR 19.5 the seam is **statically dispatched**: every owner is
/// generic over `C: Clock`, so the one production instantiation inlines and no vtable rides the
/// per-commit path. `Arc<SystemClock>` / `Arc<FakeClock>` satisfy the bound via the delegating
/// impls below (PR 19.4).
pub trait Clock: Send + Sync {
    fn now(&self) -> Instant;
}

## Hints & gotchas

- **Do this in dependency order or you will fight the compiler:** `TableBatcher` first, then
  `BatchRouter` and `StreamDemux` (both hold or create batchers), then `Backfill`, then the two free
  functions, then `main.rs`. Each step is compilable on its own.
- **Bounds belong on the `impl`, not the `struct`.** `pub struct TableBatcher<C>` + `impl<C: Clock>
  TableBatcher<C>` means every *other* place that merely names the type
  (`HashMap<u32, TableBatcher<C>>`, a `&mut BatchRouter<C>` parameter) does not have to repeat the
  bound. Putting `C: Clock` in the struct header forces the repetition everywhere.
- `BatchRouter`, `StreamDemux` and `Backfill` need `C: Clone` because they hand a clock to each new
  `TableBatcher` (`consume.rs:532`, `stream_txn.rs:220` and `:393`, `snapshot.rs:166`).
  `Arc<SystemClock>` is `Clone`; that is the whole reason PR 19.4 blanket-impls `Arc<T>` rather than
  `Box<T>`.
- `Backfill::connect` must stay in an `impl Backfill<Arc<SystemClock>>` block (**not** a defaulted
  type parameter). Rust does not use type-parameter defaults for inference in an expression path, so
  `Backfill::connect(…)` at `main.rs:304` resolves only because that inherent impl pins `C`.
- `run_decode_loop` already carries `#[allow(clippy::too_many_arguments)]` (`consume.rs:30`) — keep
  it; adding a type parameter does not change the arity.
- Sharing one `C` between `router` and `demux` in `run_decode_loop` is correct: `main.rs` passes
  `Arc::new(SystemClock)` to both. Two parameters would be noise.
- The 25 files under `crates/pg-sink/tests/` are **integration** tests: they see only the public
  API, so any type you make generic must stay `pub` with a `pub` constructor. Several are
  compose-gated behind the `integration` feature — run
  `cargo clippy --all-targets --all-features` to compile them all.
- Do not "simplify" `Arc<CachedRelation>` or `Arc<dyn ObjectStore>` while you are in there. The
  first is real sharing; the second is the decision table's dynamic row.
- `unwrap`/`expect` are denied in production by `[workspace.lints]`; `clippy::all` + `warnings` are
  `deny` workspace-wide, so an unconstrained or unused `C` is a hard error.
- No new dependency is needed; anything added must clear `cargo deny` (advisories, 8-license
  allow-list, bans). Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is
  no Docker on this machine to regenerate it.

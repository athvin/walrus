# PR 19.2 — Model terminal-vs-transient as a FailureClass trait with defaulted methods

> **Status:** 📋 Planned <!-- flip to "✅ Done — <PR url>" when it merges -->

> **Phase:** 19 — Rust traits & generics · **Crates touched:** `common`, `control`, `loader` ·
> **Est. size:** M · **Depends on:** PR 19.1 · **Unlocks:** PR 19.3

Two production error enums hand-write the **same** defaulted-method body: `common::Error::is_transient`
(`crates/common/src/error.rs:85`) and `ControlError::is_transient` (`crates/control/src/db.rs:58`)
are both literally `!self.is_terminal()`, with near-identical doc comments. `LoaderError`
(`crates/loader/src/error.rs:61`) has `exit_code()` delegating through `as_common()` but no
`is_terminal`/`is_transient` at all. There are **13 error enums in production and only 3 carry any
classification** — the terminal-vs-transient contract lives in prose, not in a trait. This PR
introduces `common::FailureClass`: **one required method** (`is_terminal`) plus **defaulted**
`is_transient` and `exit_code`. Afterwards
`grep -rn 'fn is_transient' crates/*/src | grep -v _test.rs` drops **2 → 0** and three impls
(`common::Error`, `ControlError`, `LoaderError`) share one contract.

## Why — learning objectives

- **Required vs defaulted trait methods** — keep the required set to the minimum orthogonal core
  (`is_terminal`); everything derivable from it gets a default body. `std::iter::Iterator` builds
  dozens of methods on one required `next`; this is the same shape at three-method scale.
- **Overriding a default without changing observable semantics** — `common::Error` and
  `LoaderError` override `exit_code()`; both keep the exact numbers they emit today. An override is
  allowed to be *more specific*, never *different*.
- **Trait-based reuse across crates** — `FailureClass` is defined in `common` and implemented for
  `ControlError` (in `control`) and `LoaderError` (in `loader`). Local type + foreign trait is fine
  under the orphan rule; that is why the trait must live in the shared crate, not be copied.
- **walrus's failure taxonomy and the exit-code contract** — `is_terminal` decides whether
  `retry_transient` (`crates/pg-sink/src/bootstrap.rs:145-172`) keeps backing off; `ExitCode`'s
  `#[repr(i32)]` numbers are greppable in `kubectl logs` and are a runbook contract.

## Scope

**In scope**

- New `crates/common/src/failure_class.rs` declaring:
  - **required** `fn is_terminal(&self) -> bool`,
  - **defaulted** `fn is_transient(&self) -> bool { !self.is_terminal() }`,
  - **defaulted** `fn exit_code(&self) -> ExitCode { ExitCode::Internal }`,
  with a module doc that names which methods are required and which are defaulted.
- Re-export `FailureClass` from `crates/common/src/lib.rs` next to `Error` / `ExitCode`.
- `impl FailureClass for common::Error` in `error.rs`: move the existing exhaustive `is_terminal`
  match in as the required method, **override** `exit_code` with the existing exhaustive match,
  and **delete** the inherent `is_transient` (it becomes the default).
- `impl FailureClass for ControlError` in `control/src/db.rs`: move `is_terminal` in, delete the
  duplicated `is_transient`, and take the defaulted `exit_code` — with a one-line doc recording
  *why* (a `ControlError` is always wrapped before it reaches a `main`, so its own exit code is
  never surfaced by a running process).
- `impl FailureClass for LoaderError` in `loader/src/error.rs`: add the required `is_terminal` as an
  exhaustive `match` with **no `_` arm** (`Control(e) => e.is_terminal()`, every other variant
  `true`), and move the existing `exit_code` body in as the sanctioned **override**
  (`self.as_common().exit_code()` — same numbers, unchanged).
- Add `use common::FailureClass;` (or `use crate::FailureClass;`) wherever a call site now needs the
  trait in scope. The full list is in *Files to create / modify*.
- New sibling test `crates/common/src/failure_class_test.rs` proving the default `is_transient` is
  the exact complement on a local test enum, and that a type which overrides `exit_code` still gets
  the defaulted `is_transient`.

**Explicitly deferred** (do *not* build these here)

- Retrofitting the other **10** error enums: pg-sink's `ConfigError`, `BatchError`, `SinkError`,
  `DdlError`, `ManifestError`, `RelationError`, `PreflightError`, `HeartbeatError`, `DecodeError`,
  and pg-to-arrow's `Error`. They get classified in a later phase; adding a half-guessed
  classification now would bake in wrong retry behaviour.
- Changing **any** exit-code number, adding a new `ExitCode` variant, or renumbering. They are a
  runbook contract (`error.rs:105-107`).
- Making `FailureClass` sealed, generic, or object-safe-by-guard — nothing stores a
  `dyn FailureClass`, and sealing is `api-sealed-trait`'s job in Phase 13.

**Conflict — read before applying the rule.** `common::Error::is_terminal`'s exhaustive,
**no-`_`-arm** match is a documented walrus contract: adding a variant without classifying it must
stay a **compile error**. So `is_terminal` must remain the single **required** method — do *not*
give it a default body (e.g. `fn is_terminal(&self) -> bool { true }`), and do *not* collapse the
`exit_code` match into a `_ => ExitCode::Internal` arm. The rule's "keep required methods to the
minimum" is satisfied by exactly one required method; the minimum is not zero.

## Skeleton

```rust
// crates/common/src/failure_class.rs — NEW.
//! `FailureClass` — the terminal-vs-transient contract every walrus error enum implements.
//!
//! **Required:** [`FailureClass::is_terminal`] — the one thing an implementor must decide, and
//! deliberately the only one: an exhaustive `match` with no `_` arm makes an unclassified new
//! variant a compile error.
//!
//! **Defaulted:** [`FailureClass::is_transient`] is the exact complement of `is_terminal` and
//! should never be overridden. [`FailureClass::exit_code`] answers `Internal` (70) for an
//! unclassified failure; every error type whose values reach a `main` overrides it with the
//! documented per-variant code.

use crate::ExitCode;

pub trait FailureClass {
    /// REQUIRED. True when retrying under the startup deadline can never help — die now, non-zero.
    fn is_terminal(&self) -> bool;

    /// DEFAULTED. The exact complement of [`Self::is_terminal`]: a dependency that may still be
    /// coming up, so the bootstrap retries it with backoff. Do not override.
    fn is_transient(&self) -> bool {
        todo!("!self.is_terminal()")
    }

    /// DEFAULTED. The process exit status for this failure. The default is the unclassified
    /// fallback; override it wherever the values can reach `std::process::ExitCode`.
    fn exit_code(&self) -> ExitCode {
        todo!("ExitCode::Internal")
    }
}
```

## Hints & gotchas

- **Trait methods need the trait in scope.** Every `err.is_terminal()` / `err.is_transient()` /
  `err.exit_code()` call site now needs `use common::FailureClass;` (or `use crate::FailureClass;`
  inside `common`). The compiler's error is E0599 "items from traits can only be used if the trait
  is in scope" — it tells you exactly which file. Work the list in *Files to create / modify*.
- `crates/pg-sink/src/main.rs:48` uses the **path form** `.map(common::Error::exit_code)`. That
  still resolves once `FailureClass` is imported in that file — path-qualified trait methods obey
  the same in-scope rule as `.method()` calls.
- Sibling test files start with `use super::*;`, which pulls in the *parent module*, not the crate
  root. `error_test.rs` therefore needs an explicit `use crate::FailureClass;`.
- `impl FailureClass for ControlError` in the `control` crate is legal under the orphan rule —
  `ControlError` is local. Do **not** copy the trait into `control`; that would create two
  incompatible traits with the same name.
- Do not give `is_terminal` a default. The whole no-`_`-arm contract (`error.rs:66-68`) depends on
  a missing classification being a compile error.
- `unwrap`/`expect` are denied in production by `[workspace.lints]`; `clippy.toml` re-allows them in
  `*_test.rs` only. Nothing here should need either.
- `clippy::all` and `warnings` are already `deny` workspace-wide, so a now-unused `use` line from a
  deleted inherent method is a hard error — delete imports you orphan.
- Unit tests are **Go-style sibling files** wired with `#[cfg(test)] #[path = "foo_test.rs"] mod
  tests;` — add that stanza at the bottom of `failure_class.rs`, never an inline `mod tests {}`.
- No new dependency is needed; anything you add must clear `cargo deny` (advisories, 8-license
  allow-list, bans).
- Do not touch any `.sql` file or the committed `.sqlx` offline cache — there is no Docker on this
  machine to regenerate it.
